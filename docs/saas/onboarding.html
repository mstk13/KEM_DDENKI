建設業SaaS — チーム開発ガイド

3人チームで「日報から粗利が見えるシステム」を100社に届けるための、開発の進め方と約束事

KEM_DDENKI → マルチテナントSaaS
目的 全体像 環境構築 開発フロー 絶対ルール テナント分離 データモデル ロードマップ 学習リソース

1このプロジェクトの目的

何を、なぜ、誰のために作るのかを全員が同じ言葉で説明できることがスタートライン。

🏗️ 解決する課題

建設業の中小企業では日報は紙、原価はExcel、材料は発注台帳とバラバラ。事務員が月30時間以上かけて転記・集計し、現場ごとの粗利は工事完了まで見えない。

💡 作るもの

日報を入力するだけで、現場ごとの粗利がリアルタイムに見えるシステム。これを月額SaaSとして100社に提供する。

🔄 KEM_DDENKIとの関係

KEM_DDENKI（Streamlit版）は「課題が本物であることの検証」。SaaS版は「100社に売れる製品」として Django で再設計する。

KEM_DDENKI がそのまま売れない理由

問題具体的に何が起きるか
データが分離できない1社専用のDB。他社に売るなら会社ごとにシステムをコピーする必要がある
Streamlit の限界ログイン・権限管理・スマホ対応が弱い。職人がスマホで使えない
固有名詞がハードコード「電工」「事務」「シニア」等がコードに埋まっている。別の会社では使えない

3開発環境のセットアップ

初回のみ。15分で完了する。

前提条件

  • Python 3.12 以上がインストール済み
  • Git がインストール済み
  • GitHub アカウントで KEM_DDENKI リポジトリにアクセスできる

手順

# 1. リポジトリをクローン
git clone https://github.com/mstk13/KEM_DDENKI.git
cd KEM_DDENKI

# 2. developer ブランチに移動
git checkout developer

# 3. SaaS ディレクトリに移動して仮想環境を作成
cd saas
python -m venv .venv

# 4. 仮想環境を有効化
# (Linux / Mac)
source .venv/bin/activate
# (Windows)
.venv\Scripts\activate

# 5. 依存パッケージをインストール
pip install -e ".[dev]"

# 6. マイグレーション実行（SQLite でローカル開発）
USE_SQLITE=true python manage.py migrate

# 7. 初期データ投入（原価区分4つ + グループ3つ）
USE_SQLITE=true python manage.py seed

# 8. テスト実行 — 15件全部通れば OK
USE_SQLITE=true python -m pytest tests/ -v
💡 ヒント

ローカル開発は USE_SQLITE=true で SQLite を使う。PostgreSQL のセットアップは不要。本番・ステージングのみ PostgreSQL を使う。

4開発フロー

全員が同じやり方で進めることで、事故を防ぎ、レビューしやすくなる。

Git ブランチ戦略

main          ← 本番リリース用。直接コミット禁止
 ↑ PR + レビュー
developer     ← 開発統合ブランチ
 ↑ PR + CI green
feature/*     ← 個人の作業ブランチ（ここで作業する）

日々の作業フロー

1. feature ブランチを切る

git checkout developer && git pull && git checkout -b feature/add-site-model
ブランチ名は feature/やること の形式。英語で短く。

2. コードを書く

モデル変更時は必ず makemigrations を実行。
テストも同じPRに含める（特に越境テスト）。

3. ローカルで確認

ruff check . で lint 通過を確認。
USE_SQLITE=true python -m pytest tests/ -v で全テスト合格を確認。

4. Push して PR を作成

git push -u origin feature/add-site-model
GitHub で developer 向けの Pull Request を作成。変更内容を簡潔に書く。

5. CI 通過 + レビュー

GitHub Actions が自動で lint・テストを実行。
最低1人のレビューが通ったらマージ。

6. feature ブランチを削除

マージ後は feature ブランチを削除して完了。

コミットメッセージの書き方

接頭辞意味例
feat:新機能の追加feat: Site モデルと工程管理を追加
fix:バグ修正fix: WorkType の表示順が効かない問題を修正
refactor:動作を変えないコード改善refactor: CompanyScopedManager のフィルタロジックを整理
test:テストの追加・修正test: Site の越境テストを追加
docs:ドキュメントの変更docs: ADR-0004 を追加

5絶対ルール（9つの約束）

全員が守る。破ると他のメンバーの作業が壊れるか、将来100社のデータ移行が発生する。

⛔ 1. 業種名をコードに書かない

「電気」「内装」「解体」等の業種名が if 文やクラス名に現れたら設計ミス。業種の違いは WorkType マスタの行で表現する。コードを変えずに業種を追加できることがSaaSの生命線。

⛔ 2. テナント帰属モデルは TenantModel を継承する

会社に紐づくデータを持つモデルは全て TenantModel を継承すること。company_id が無いテーブル = テナントデータが混ざる = 情報漏洩。

⛔ 3. 金額計算は Decimal のみ。float 禁止

float は丸め誤差が出る。0.1 + 0.2 = 0.30000000000000004 になる世界で原価計算はできない。

⛔ 4. 工種 × 原価区分の粒度を崩さない

予算も実績も必ず「どの工種の、どの原価区分か」を記録する。この粒度が揃わないと予実対比もAI分析も成立しない。粒度を落とす変更は禁止。

⚠️ 5. main へ直接コミットしない

必ず feature ブランチ → PR → CI green → レビュー1名 の手順を踏む。

⚠️ 6. 新規モデルの PR には4点セットを含める

❶ simple-history の設定   ❷ admin 登録   ❸ テナント越境テスト   ❹ マイグレーション

⚠️ 7. マイグレーションは expand / contract

カラム追加 → 両対応デプロイ → データ移行 → 次リリースで削除。破壊的変更（カラム改名・NOT NULL 追加）を1回のリリースでやらない。

📝 8. USE_TZ=True — 日時は aware datetime のみ

タイムゾーンなしの datetime を使わない。timezone.now() を使う。

📝 9. 設計判断をしたら ADR を書く

docs/saas/adr/ に ADR-NNNN-タイトル.md を追加。なぜその選択をしたかを未来の自分たちに残す。

6テナント分離の仕組み

SaaS開発で最も重要な概念。ここを理解しないとコードを書けない。

マンションの例え

🏠 一戸建て（今のKEM_DDENKI）

1社ごとにシステムを丸ごとコピーする。100社なら100個管理。無理。

🏢 マンション（SaaS版）

建物（アプリ）は1つ。部屋（データ）は鍵で完全に分離。100社でも管理は1つ。

行レベル分離の仕組み

全テーブルの全行に「どの会社のデータか」を示す company_id を持たせる。

# モデルの定義 — TenantModel を継承するだけ
from apps.core.models import TenantModel

class Site(TenantModel):
    name = models.CharField("現場名", max_length=200)
    # company は TenantModel が自動的に持つ。書かなくてOK


# データの取得 — 自動フィルタされる
Site.objects.all()
# → ログイン中のユーザーが属する会社のデータのみ返る
# → 裏で自動的に .filter(company=現在のテナント) がかかる


# 全社のデータを見たい場合（管理者用途のみ。理由をコメントで明記）
# unscoped: 全テナントのデータ集計に使用
Site.unscoped.all()
⛔ フィルタ漏れ = 情報漏洩

TenantModel を継承せずに会社データを持つテーブルを作ると、他社のデータが見える致命的なセキュリティ事故になる。だから「越境テスト」を CI で毎回自動実行する。

越境テストの考え方

# テスト: A社ユーザーがB社データに到達できないことを検証

def test_site_isolation(company_a, company_b):
    # A社とB社にそれぞれ現場を作成
    Site.unscoped.create(company=company_a, name="A社の現場")
    Site.unscoped.create(company=company_b, name="B社の現場")

    # A社のコンテキストで取得 → A社のデータのみ見える
    set_current_company(company_a)
    assert Site.objects.count() == 1
    assert Site.objects.first().name == "A社の現場"

    # B社のコンテキストで取得 → B社のデータのみ見える
    set_current_company(company_b)
    assert Site.objects.count() == 1
    assert Site.objects.first().name == "B社の現場"

7核心のデータモデル

出口（データモデル）から設計する。入口（UI）は後で変えられるが、テーブル構造の変更は100社のデータ移行を伴う。

CostTransaction — 原価データの統一テーブル

建設業の原価を4区分に分け、全原価を1つのテーブルに同じ粒度で格納する。これが本プロダクトの核心。

原価区分何か自動生成のタイミング
労務費人件費日報が承認されたとき（work_hours × hourly_cost）
材料費資材購入費発注が検収されたとき（quantity × unit_price）
外注費下請け支払い手入力
経費交通費等手入力
 
粗利 = 受注金額 − Σ CostTransaction.amount

例: 受注額 500万 − 原価合計 320万 = 粗利 180万（36%）

CostTransaction は書き換えない（追記のみ）

間違えた場合:

1. 元の金額を打ち消す行を追加（逆仕訳: −24,000円）
2. 正しい金額の行を追加（再仕訳: +27,000円）

→ 「いつ・誰が・何を修正したか」が全部追跡できる（監査可能性）

WorkType — 業種の違いをマスタデータで吸収

電気工事会社の WorkType:      内装工事会社の WorkType:
  電気 > 幹線・動力              内装仕上 > 軽鉄・ボード
  電気 > 弱電                    内装仕上 > クロス
  電気 > 受変電                  内装仕上 > 床仕上

→ コードは一切変更不要。マスタデータの行が違うだけ。

分析ダッシュボード
