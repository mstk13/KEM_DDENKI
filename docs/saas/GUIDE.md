## 1. 何を作るのか（一言）

> **日報を入力するだけで、現場ごとの粗利がリアルタイムに見えるシステム**

これを「100社に売れる製品」として作る。1社専用の KEM_DDENKI とは設計思想が根本的に違う。

## 2. なぜ Django に変えるのか

### Streamlit の限界（KEM_DDENKI で体験済み）

| 困ったこと | Django だとどうなるか |
|---|---|
| ログイン機能を自作した | `django.contrib.auth` が標準で持っている |
| 権限管理が貧弱 | Group + Permission で細かく制御できる |
| スマホで使いにくい | HTML/CSS で自由に UI を設計できる |
| DB変更が怖い（手動SQL） | `makemigrations` で安全に管理 |
| 複数会社のデータを分けられない | ミドルウェアで自動的にフィルタ |

### Django の仕組み（超ざっくり）

```
ユーザーがブラウザでアクセス
  ↓
URL振り分け (urls.py)    … どの画面を出すか
  ↓
ミドルウェア              … ログイン済みか？どの会社のユーザーか？
  ↓
ビュー (views.py)        … DBからデータを取って加工
  ↓
テンプレート (.html)      … HTMLを組み立てて返す
  ↓
ブラウザに画面表示
```

Django は URL振り分け・ミドルウェア・DB操作・管理画面を**全部標準で持っている**。
KEM_DDENKI では `auth.py`, `database.py`, `admin_app.py` 等を自作していた部分が不要になる。

## 3. マルチテナントとは

### マンションの例え

- **今の KEM_DDENKI** = 一戸建て。1社ごとにシステムを丸ごとコピーする → 100社なら100個管理。無理
- **SaaS版** = マンション。建物（アプリ）は1つ、部屋（データ）は鍵で分離

### 行レベル分離の仕組み

全テーブルの全行に「どの会社のデータか」を示す `company_id` 列を持たせる。

```
# 悪い例（company_id なし）
Worker.objects.all()
→ 全社の社員データが見える！（情報漏洩）

# 正しい例
Worker.objects.filter(company=現在のテナント)
→ 自社の社員だけ見える

# SaaS版の仕組み（自動フィルタ）
Worker.objects.all()  ← 書くのはこれだけ
→ CompanyScopedManager が裏で .filter(company=現在のテナント) を自動追加
→ 自社の社員だけ見える
```

**絶対に忘れてはいけないこと**: フィルタ漏れ = 他社のデータが見える = 致命的なセキュリティ事故。
だから「越境テスト」（A社ユーザーがB社データに触れないことの確認）を CI で毎回自動実行する。

## 4. データモデル解説

### 4.1 全体像

```
Company（会社）──────────────────────────────┐
  │                                          │
  ├── User（ユーザー）                        │ すべてのテーブルが
  ├── Department（部署）                      │ company_id を持つ
  ├── WorkType（工種）                        │
  ├── Customer（得意先）                      │
  ├── Supplier（仕入先）                      │
  │                                          │
  ├── Site（現場）───┐                        │
  │    ├── Process（工程）                    │
  │    ├── BudgetItem（実行予算）             │
  │    ├── DailyReport（日報）──→ CostTransaction（原価）
  │    ├── PurchaseOrder（発注）──→ CostTransaction
  │    └── CostTransaction（原価）           │
  │         ↑ 全原価がここに集まる            │
  │                                          │
  └── Worker（作業員）                        │
       ├── JobTitle（職種）                   │
       └── Position（役職）                  ─┘
```

### 4.2 CostTransaction（原価データ）が核心

建設業の原価は4種類:

| 原価区分 | 何か | 自動生成のタイミング |
|---|---|---|
| 労務費 | 人件費 | 日報が承認されたとき |
| 材料費 | 資材購入費 | 発注が検収されたとき |
| 外注費 | 下請け支払い | 手入力 |
| 経費 | その他 | 手入力 |

全原価が **CostTransaction** という1つのテーブルに、**同じ粒度（工種 × 原価区分）** で入る。

```
粗利 = 受注金額 − Σ CostTransaction.amount
```

この「粒度を揃える」が仕様書で最も強調されているルール。
予算も実績も「どの工種の、どの原価区分か」を必ず記録する。
粒度が揃わないと予算と実績の比較（予実対比）ができない。

### 4.3 CostTransaction は書き換えない（追記のみ）

間違えた場合:
1. 元の金額を打ち消す行を追加（逆仕訳: −24,000円）
2. 正しい金額の行を追加（再仕訳: +27,000円）

→ 「いつ・誰が・何を修正したか」が追跡できる（監査可能性）

### 4.4 WorkType（工種マスタ）が業種の違いを吸収する

KEM_DDENKI では「電工」「配管」等がコードにハードコードされていた。
SaaS版では WorkType マスタに行を追加するだけで、どんな業種にも対応できる:

```
電気工事会社の WorkType:
  電気 > 幹線・動力
  電気 > 弱電
  電気 > 受変電

内装工事会社の WorkType:
  内装仕上 > 軽鉄・ボード
  内装仕上 > クロス
  内装仕上 > 床仕上

→ コードは一切変更不要。マスタデータの違いだけ。
```

## 5. テナントごとの機能制御

各会社が使えるアプリは `CompanyApp` テーブルで管理する:

```
CompanyApp:
  company = ケンモチ電機, app_code = "nippou",  is_enabled = True
  company = ケンモチ電機, app_code = "zairyo",  is_enabled = True
  company = ケンモチ電機, app_code = "genka",   is_enabled = False  ← 未契約
  company = A社内装,      app_code = "nippou",  is_enabled = True
  ...
```

- `is_enabled = False` のアプリの URL にアクセスすると 404 になる
- 課金の判定もこのテーブルを見る（単一情報源）

## 6. 権限の仕組み

Django 標準の Group + Permission を使う（独自テーブルは作らない）:

| グループ | できること |
|---|---|
| admin | テナント内の全操作（ユーザー管理・マスタ管理含む） |
| manager | 日報承認・全現場閲覧・全レポート閲覧 |
| worker | 自分の日報入力・自分の現場閲覧 |

Django admin（`/admin/`）は SaaS 運営者（自社）専用。テナントには見せない。

## 7. 開発ルール（全員必読）

1. **業種名をコードに書かない** — 「電気」「内装」等の文字列が `if` 文に現れたら設計ミス
2. **テナント帰属モデルは TenantModel を継承** — `company_id` の付け忘れを防ぐ
3. **金額は Decimal のみ** — `float` は丸め誤差が出るので禁止
4. **main に直接コミットしない** — 必ず PR → CI green → レビュー
5. **新しいモデルを作ったら同じ PR に含めるもの**:
   - simple-history の設定
   - admin 登録
   - テナント越境テスト
   - マイグレーション

## 8. 用語集

| 用語 | 意味 |
|---|---|
| テナント | SaaS を利用する1社のこと |
| マルチテナント | 1つのシステムで複数社のデータを分離して管理する仕組み |
| MRR | Monthly Recurring Revenue（月次経常収益） |
| 解約率 (Churn) | 月に何%の顧客が解約するか |
| LTV | Life Time Value（1社が生涯で支払う総額） |
| ORM | Object-Relational Mapping（Python のコードで DB を操作する仕組み） |
| マイグレーション | DB のテーブル構造を安全に変更する仕組み |
| ADR | Architecture Decision Record（設計判断の記録） |
| CI | Continuous Integration（コードを push するたびに自動テスト） |
| 予実対比 | 予算と実績を比較すること |
| 工種 | 工事の種類（電気幹線、弱電、etc.） |
| 原価区分 | 原価の種類（労務費・材料費・外注費・経費の4つ） |
| 逆仕訳 | 間違った原価を打ち消すためのマイナス行 |
