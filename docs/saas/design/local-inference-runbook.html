ネットワークとアクセス制御

Ollama には認証機構がない。0.0.0.0 で待ち受けると LAN（192.168.1.3）と Tailscale（100.76.219.49）にも露出するため、Windows ファイアウォールで WSLサブネットからのみ許可している。Windows の受信既定は拒否なので、 この許可規則だけでLAN・Tailscale側は塞がったままになる。 

# 適用済みの規則
New-NetFirewallRule -DisplayName "Ollama (WSL/Docker only)" `
  -Direction Inbound -Protocol TCP -LocalPort 11434 `
  -RemoteAddress 172.23.16.0/20 -Action Allow -Profile Any

コンテナからの到達先は host.docker.internal。 検証時は IPv6 の fdc4:f303:9324::254 に解決されたため、 待受を ::（デュアルスタック）にしてある。0.0.0.0 のIPv4単独では届かない場合がある。

モデル詳細

2つのモデルの中身

Qwen3-8B — 層B 構造化・抽出

総パラメータ8.2B（うち埋め込み層を除くと 6.95B）
層数 / Attention36層、GQA構成で Query 32ヘッド / Key-Value 8ヘッド
コンテキスト長ネイティブ 32,768 トークン（YaRN 拡張で最大 131,072）
量子化Q4_K_M — 配布サイズ 5.2GB
ライセンスApache 2.0（商用利用可）
言語100以上の言語・方言
特徴thinking / non-thinking モードを1モデル内で切替可能。ツール呼び出し対応

仕組み — 押さえておくべき3点

  • Q4_K_M 量子化 … 重みを約4.5bitに圧縮したもの。FP16なら16GB超で3060には載らないが、 品質劣化を抑えつつ5.2GBまで落としている。Kは重要度に応じてビット幅を変える手法、 Mはそのバランス設定（S/M/L のうち中間）
  • GQA（Grouped Query Attention） … Query 32ヘッドに対し Key-Value を8ヘッドに集約する構造。 KVキャッシュが 1/4 で済むため、長文を入れてもVRAMが急激に膨らまない。 labor_pdf のような長い入力を扱ううえで効く
  • thinking モード … 既定では <think>...</think> に囲まれた推論過程を出力してから答える。 JSON構造化では邪魔になるので明示的に切る（後述）

一次情報: huggingface.co/Qwen/Qwen3-8B · ollama.com/library/qwen3:8b · github.com/QwenLM/Qwen3

BGE-M3 — 層A 埋め込み照合

ベースモデルXLM-RoBERTa（8,192トークンまで拡張）
埋め込み次元1,024（実測で確認済み）
最大系列長8,192 トークン
検索モードDense / Sparse（語彙マッチ）/ Multi-Vector（ColBERT型）の3方式
ライセンスMIT
配布サイズ1.2GB（Ollama bge-m3）

仕組み — なぜ品目マッチングに向くのか

  • 文字列を1,024次元のベクトルに変換する。意味が近い文字列はベクトル空間上で近い位置に来るため、 表記ゆれを吸収した照合ができる。「VVFケーブル 1.6mm 2芯」と「VVF 1.6×2C」は 文字列一致では0点だが、ベクトルでは近くなる
  • 生成モデルと違い出力がベクトル1本なので、推論が1パスで終わり圧倒的に速い。 LLMのように何百トークンも生成しない
  • Ollama の /api/embed は Dense モードのみを返す。 Sparse や Multi-Vector を使いたい場合は FlagEmbedding 等の別実装が必要

一次情報: huggingface.co/BAAI/bge-m3 · ollama.com/library/bge-m3 · github.com/FlagOpen/FlagEmbedding

実装

正しい呼び方

層B — JSONスキーマで構造化する

format にJSON Schema そのものを渡すのが正解。format:"json" という文字列指定だけでは 「JSONらしきもの」しか保証されず、キー名も構造も守られない（実測で確認済み）。 think:false で推論過程の出力を止める。 

import requests

SCHEMA = {
    "type": "object",
    "properties": {
        "rates": {"type": "array", "items": {
            "type": "object",
            "properties": {
                "prefecture": {"type": "string"},
                "job":        {"type": "string"},
                "rate":       {"type": "integer"},
            },
            "required": ["prefecture", "job", "rate"],
        }},
    },
    "required": ["rates"],
}

r = requests.post(
    "http://host.docker.internal:11434/api/generate",
    json={
        "model": "qwen3:8b",
        "prompt": prompt,
        "stream": False,
        "think": False,          # <think> ブロックを抑止
        "format": SCHEMA,        # スキーマそのものを渡す
        "keep_alive": "10m",    # バッチ中は保持。単発なら 0
        "options": {"temperature": 0.7, "top_p": 0.8, "top_k": 20},
    },
    timeout=600,
)
data = json.loads(r.json()["response"])

サンプリング設定は Qwen 公式の推奨値。non-thinking は temperature 0.7 / top_p 0.8 / top_k 20、 thinking 時は 0.6 / 0.95 / 20。greedy decoding（temperature 0）は非推奨とされている。

踏んだ落とし穴

1. 類似度のマージンが狭い — 単一しきい値は危険

「VVFケーブル 1.6mm 2芯 100m巻」を基準に実測した結果がこれ。 同一品目の略記（0.768）と、別種ケーブル（0.668）の差がわずか0.10しかない。 閾値を1本引いて自動確定させると、CVケーブルをVVFとして誤マッチする。

対処 … 埋め込みは候補生成に使い、確定判断はしない。 0.85以上のみ自動確定、0.65〜0.85は上位k件をLLMに渡して選ばせる、0.65未満は不一致。 ADR-0010 で設計した「閾値未満は _match_by_llm にフォールバック」は、 この実測により具体的な数値が入った。

2. PowerShell 5.1 は日本語プロンプトを化けさせる

検証中、モデルが入力を無視して「北海道 / 正社員」などを捏造する現象が出た。 原因はモデルではなく Invoke-RestMethod -Body が UTF-8 で送っていなかったこと。 バイト列に変換して送ったら 3/3 正答になった。 

# NG — 日本語が化ける
Invoke-RestMethod -Body ($body|ConvertTo-Json) -ContentType 'application/json'

# OK
$bytes = [Text.Encoding]::UTF8.GetBytes(($body|ConvertTo-Json -Depth 12))
Invoke-RestMethod -Body $bytes -ContentType 'application/json; charset=utf-8'

Python の requests（json= 引数）は自動でUTF-8にするため、 アプリ本体では発生しない。検証スクリプトを書くときだけ注意。

3. format:"json" だけではスキーマが守られない

文字列指定だと {"key1": "string", "key2": 24500, ...} のような 構造だけJSONの無意味な出力になった。 JSON Schema オブジェクトを渡すと構造・キー名・型がすべて守られる。 さらに出力トークン数が 1,550 → 111 に激減し、27秒が2秒になる副次効果もある。

4. thinking を切っても抽出精度は落ちない

think:false と think:true で正答率は同じ 3/3。 スキーマ付き構造化タスクでは推論過程を出す意味がなく、 切ったほうが速くトークンも減る。ただし判断を伴うタスクでは別途検証が必要。

つまずいたときの確認順

  • コンテナから届かない … OLLAMA_HOST が 0.0.0.0 か、 ファイアウォール規則が有効か、待受が :: になっているか
  • 応答が異常に遅い … ollama ps で 100% GPU か確認。 CPU と出ていればVRAMが足りずCPUに落ちている
  • JSONパース失敗 … think:false が入っているか。 <think> が混ざっていないか
  • 日本語が化ける … リクエストボディがUTF-8で送られているか
  • 出力が入力を無視する … 上と同じ。プロンプトが届いていない可能性を先に疑う

モデルの更新

# 更新（既存タグを上書き）
ollama pull qwen3:8b

# 別バージョンを併存させて比較する場合はタグを指定
ollama pull qwen3:14b   # 9.2GB。bge-m3 との同時常駐は不可

# 不要になったら削除
ollama rm qwen3:14b

更新したら必ず labor_pdf のサンプルで再検証すること。 量子化やテンプレートが変わると出力が変わりうる。
