ADR-0010 · 設計判断の記録

AI推論の3層分割

KEM_DDENKI のAI機能を、埋め込み・ローカルLLM・Claude API の3層に分けて振り分ける。 判断の根拠は「品質が価値の中核になるタスクだけAPIに残す」の一点で、 コスト削減はその副次効果として扱う。

対象 apps/ai · apps/estimation 実行環境 DESKTOP-RMSK0VG (本番8000 / 開発8001) GPU RTX 3060 12GB 作成 2026-08-14
判断の土台

実測から出発する

設計の前に ai_ailog を集計した。推定値ではなく、実際に走った3件のトークン数と課金額が根拠になっている。

前提の訂正。 当初「本番は別サーバー」と想定して設計したが、 ~/kem-ops/autodeploy.conf と hostname の確認により、 本番・開発の2スタックとも同一のこのPCが実体だと判明した。 これによりローカル推論は本番コストに直接効き、リモート推論エンドポイントを介する構成は不要になった。 代わりに「同一PCの前景利用とGPUを取り合う」制約が新たに発生する。

損益分岐はどこか

ローカル側の費用はほぼ電気代の固定費で、呼び出し回数にほとんど比例しない。 APIは完全な従量制。この形の違いが分岐点を決める。前提は31円/kWh、GPUアイドル増分8W、推論時140W。

30秒 × 140W = 0.00117kWh × 31円/kWh = 0.036円。電力単価だけを見ればローカルが負ける場面はない。

keep_alive はリクエスト単位で使い分ける

環境変数で一律 OLLAMA_KEEP_ALIVE=0 にすると固定費は消えるが、 毎回3〜5秒のロードが乗る。50ページのバッチで毎回解放すると約3分がロードだけで消える。

  • 単発呼び出し … "keep_alive": 0（固定費ゼロ）
  • バッチ処理中 … "keep_alive": "10m"（保持電力は1時間で約0.25円）
この設計の狙い

削減額よりも、止まらないこと

正直なところ削減額は年間5,000円前後にすぎず、AI_MONTHLY_BUDGET_JPY=4000 の上限が効くため 青天井にもならない。費用削減だけを目的にするなら投資対効果は薄い。実際の価値は次の2点にある。

予算上限でAI機能が止まらなくなる

現在 check_budget_and_notify() は上限到達時にAI機能を丸ごと停止する （llm_advisor.py:161-169）。層A・層Bをローカルへ逃がせば、 上限に当たるのは層Cだけになり、業務が止まる範囲が狭まる。

bulk_match を気兼ねなく回せる

従量課金では数千件の一括マッチングを躊躇するが、電気代なら実行を我慢する理由がなくなる。 使える機能を実際に使える状態にする、という効果のほうが大きい。

機能は一つも削らない。 品質が価値の中核でないタスクだけ実行先を変える。 コスト最適化はその結果であって、目的ではない。
図4

なぜ 8B なのか

VRAM 12,288MiB のうち617MiBはデスクトップ描画が使用中。残り約11GBの収まり方でモデルサイズが決まる。 labor_pdf は本文3,000字＋テーブルJSONを入力し4,000トークンを出力するため、 コンテキスト用の余白を確保できるかが選定の分かれ目になる。

14Bは品質で勝るが、50ページのPDFで1.8時間かかり、埋め込みモデルとの同時常駐で余白が消える。 20B級（gpt-oss-20b等）はコンテキストを伸ばした時点で確実に溢れるため対象外とした。

実装詳細

コードに落とすとどうなるか

層A  埋め込み照合の挿入

apps/estimation/services/matching.py

  • _match_by_embedding() を新設し、_match_by_spec の後・_match_by_llm の前に挿入
  • EstimationItem にベクトル列を追加。件数規模ならpgvector不要、numpyの総当たりで足りる
  • 閾値未満のときだけ既存の _match_by_llm にフォールバック
  • CPU実行で完結するためGPU競合の影響を受けない

層B  プロバイダ抽象の追加

apps/ai/services/llm_advisor.py

  • MODEL_CONFIG（L42-59）に "local" キーを追加。display には既存の AILog.ModelType.CUSTOM を割り当てる
  • _call_claude() をディスパッチャに分離し、local時はOllamaの /api/chat を叩く
  • _calculate_cost() はlocal時に Decimal("0") を返す。AILogの記録経路は共通のまま維持
  • 既存の _parse_json_response() はそのまま流用できる

フォールバック

  • ローカル側がVRAM不足・タイムアウト・接続失敗のいずれかなら、その場でClaude APIに切り替える
  • 機能を落とすのではなく、コストを払って動く方に倒す。業務システムとして可用性を優先する
  • 切り替え発生は AILog.model_used の分布で事後に追える

運用設定

  • OllamaはWindowsネイティブで稼働。WSL内に置くと memory=12GB 制限を食い、GPUパススルーの損失も乗る
  • コンテナからは host.docker.internal:11434 で到達
  • OLLAMA_NUM_THREAD=4。6コアのうち2つをDjango/Postgres用に残す
  • keep_alive は環境変数で固定せず、リクエスト単位で指定する（単発は 0、バッチ中は "10m"）
  • バッチは既存の12:30自動バックアップと同じ夜間スケジュールに寄せる

前景利用との競合

リスク影響対処
VRAMの取り合い本番AI機能がロード失敗・タイムアウトAPI自動フォールバック（実装済み前提）＋ KEEP_ALIVE=0
連続推論中の発熱アイドル56℃。推論時70〜80℃でファン音定格運用で許容する。ファン音は問題にならないため電力制限はかけない。LLM推論はメモリ帯域律速で実消費は140W前後に収まり、上限を絞っても費用はほぼ変わらず速度だけ約10%落ちる
ローカル出力のJSON崩れパース失敗が増える既存 _parse_json_response() の失敗時にAPIへ再試行。Claude結果との突き合わせ検証を導入前に実施
単一障害点このPC停止で本番停止新規リスクではない。既に本番がこのPCで動いており、LLM追加で増える依存はない
導入順序

効果の大きい順に進める

  1. 層A — 埋め込みマッチングの導入

    GPU不要・CPUで完結。本番のAPI呼び出しが実際に減る唯一の即効施策で、品質リスクを伴わない。ここから着手する。

  2. Ollama + Qwen3-8B の検証

    labor_pdf の構造化をローカルに切り替え、既存のClaude出力と突き合わせて精度を確認する。合格するまで本番へは入れない。

  3. プロバイダ抽象とフォールバックの実装

    llm_advisor.py にlocalプロバイダとAPI退避を追加。AILogの記録形式は変えず、既存のコスト監視をそのまま活かす。

  4. 層Cは触らない

    分析・提案系はClaude Sonnetのまま据え置く。ここを削ると機能の価値そのものが落ちる。
