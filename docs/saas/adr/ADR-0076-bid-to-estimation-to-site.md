# ADR-0076: 入札案件を積算案件へ引っ越し、受注・失注・日程を積算側で扱う

## ステータス

採用（2026-09-16）

## コンテキスト

プロダクトオーナーの依頼（2026-09-16）:

1. 入札案件で積算を始めたものを「見積案件」に移動させたい
2. 積算案件が受注したら現場管理へ、失注したら原因（競合の金額など）を記録したい
3. 積算案件の日程をガントチャートで管理したい
4. 現場管理の画面と同じように手修正を入れられるようにしたい

今の状態を確かめたところ、認識とのズレが2つあった。

- 入札案件の「積算開始」ボタンは既にあるが、**作るのは積算中の現場（Site）だけ**で、
  積算案件（`EstimationProject`）は作られない。ステータスも「積算中」ではなく**「検討中」**になる
- `EstimationProject` は `bid_project` FK を持っているが、**この経路では埋まらない**。
  積算案件は `estimation:project_create` から手で作るしかなく、入札案件と繋がっていなかった

つまり「入札 → 積算 → 現場」は、モデルの上では繋がる形になっているのに、
画面の操作では繋がっていなかった。事務員は入札案件で積算を始めたあと、
積算案件を手で作り直していたことになる。

あわせて、既にあるものを確認した。

| あるもの | 場所 | 内容 |
|---|---|---|
| 公告の手続きスケジュール | `BidProject.bid_schedule` | 公告PDFの別表から抽出した期限（申請期限・入札書受領期限・開札日） |
| 入札案件のガント | `apps/bids/gantt.py` | 締切をバーに引き延ばし、`schedule_overrides` で手直しを保持（ADR 済み） |
| 現場のガント | `apps/schedules` | frappe-gantt 0.6.1 で表示、下の一覧のフォームで工程を追加・編集・削除 |
| 入札の競合 | `BidCompetitor` | 入札案件にぶら下がる競合名・金額 |
| 現場の一本化 | ADR-0031 | 積算開始・落札で作る現場は1つ。何度押しても増やさない |

## 決定

### 0. 「積算中」という言葉を3つのモデルで揃える

入札案件・積算案件・現場の3つが、それぞれ積算段階の状態を持つ。**値も表示も揃える。**

| モデル | 値 | 表示 |
|---|---|---|
| `bids.BidProject.Status.ESTIMATING` | `estimating` | 積算中（今回追加） |
| `estimation.EstimationProject.Status.ESTIMATING` | `estimating` | 積算中（既存のまま） |
| `sites.Site.Status.ESTIMATING` | `estimating` | 積算中（**「見積中」から変更**） |

同じ1件の案件が、画面をまたぐと呼び名が変わっていた。現場は「見積中」、
積算案件は「積算中」。指しているのは同じ段階で、呼び分ける理由が無い。
**呼び分けると、同じ案件が2つあるように見える。**

値は `estimating` のままなので、**既存データの書き換えは不要**。変えたのは表示だけ。

### 1. 「移動」は状態で表す。レコードは消さない

`BidProject.Status` に **`estimating`（積算中）** を足し、積算開始でこの状態にする。
入札案件一覧は、絞り込みを指定していないとき **`MOVED_STATUSES`（＝積算中）を除外**する。

引っ越したように見えるが、レコードは入札案件として残る。公告・参加要件・提出書類・
入札スケジュールは入札案件の画面にしか無く、積算中も開札まで参照し続けるため。
絞り込みで「積算中」を選べば追える。

あわせて、`estimating` を既存の2箇所にも通す。**新しい状態を足すと、状態を列挙している
既存のコードが黙ってその案件を落とす**ためで、どちらも実際に落ちていた。

| 箇所 | 落ちていたこと | 直し方 |
|---|---|---|
| 入札案件一覧の期限切れ除外（`settled`） | 積算中の案件が入札期限を過ぎると、絞り込みで「積算中」を選んでも消える | `settled` に `estimating` を加える |
| 入札期限アラート（`check_bid_deadline_alerts`） | 積算に着手した案件の入札書提出期限が通知されなくなる | 対象の状態に `estimating` を加える |

入札ダッシュボードの受注率は、決定5の書き戻しで保たれるため変更しない。

### 2. 積算開始で積算案件を作る

`bids.services.start_estimation()` が、積算中の現場に加えて
`EstimationProject`（`status=estimating`, `bid_project=` 入札案件, `site=` 積算中の現場）を作る。
何度押しても1つ（ADR-0031 と同じ方針）。積算開始後は**積算案件の画面へ遷移**する。

`EstimationProject.orderer` は必須（PROTECT）なので、引っ越しのたびに人手でマスタを
選ばせると積算を始められない。**公告の発注者名で `Orderer` を引き当て、無ければ作る**
（`unique_together = (company, name)` なので同名は1件に寄る）。
種別・積算体系は既定値のままにし、備考に「確認してください」と残す。
発注者名が空の公告は「発注者未設定」で作る。積算を止めないことを優先する。

### 3. 積算案件の日程は公告の期限から起こす

`EstimationPhase` を新設し、積算開始時に**公告の手続き期限を工程として取り込む**。
日付の解釈（締切をバーに引き延ばす、案件ごとの手直しを当てる）は
`apps/bids/gantt.py` に既にあるので、**その出力を借りて二重に実装しない**。

取り込み済みかどうかは `source_label`（公告側の項目名）で判定し、
**同じ項目は二度取り込まない**（部分ユニーク制約で担保）。
公告を取り込み直しても、手で直した日付・工程名は戻らない。

### 4. 失注は競合ごとに記録し、差額は保存しない

`EstimationCompetitor` を新設（社名・金額・落札者フラグ・メモ）。
`EstimationProject` に `lost_reason`（選択肢）・`lost_note`・`decided_on` を足す。

**差額・差率は列に持たず、表示のたびに引き算する。**
自社の応札額は積算のやり直しで動く。差額を保存すると、応札額を直したときに
競合側の更新を忘れて食い違う。引き算1回なので持つ理由がない。

失注原因を自由記述にせず選択肢にするのは、後から「価格で負けた件」を数えるため。

### 5. 受注は現場を作り直さず、状態を進める

現場は積算開始の時点で積算中として作ってある。受注時は**それを受注済にする**（ADR-0031）。
入札を経ない積算案件（民間の相対見積）で現場が無い場合だけ、ここで作る。

失注したときは、積算中の現場を**中止**にする。受注していない現場が施工の一覧に
残り続けると、稼働中の現場を数えるときに紛れ込むため。

受注・失注はどちらも**入札案件のステータスにも書き戻す**。
入札案件は「積算中」のまま残っているので、書き戻さないと
入札ダッシュボードの受注率が、積算に移した案件を数え落とす。

### 6. 手修正は現場管理と同じ作りにする

現場管理の工期画面は「frappe-gantt で表示 ＋ 下の一覧のフォームで追加・編集・削除」であり、
バーのドラッグでは直さない。**積算案件も同じ作りに揃える**。見る側が覚え直すことがない。

## 捨てた選択肢

- **入札案件のレコードを積算案件へ移して消す**: 公告・参加要件・提出書類・入札スケジュールが
  入札案件にしか無く、開札まで参照し続ける。消すと積算中に公告を見られなくなる
- **`schedules.Phase` を積算案件でも使う**: `site` FK が必須なので nullable にする破壊的変更が要る
  （規律7の expand/contract に反する）。また現場の工程（施工の工種）と積算の日程（手続き）は
  並べるものが違い、受注後に現場へ引き継ぐときに混ざる
- **積算案件にも必ず現場を持たせて現場のガントを使い回す**: 入札を経ない相対見積でも
  現場ができてしまい、受注していない現場が施工の一覧に増える
- **差額を列として保存する**: 応札額を直したときに更新を忘れて食い違う（決定4のとおり）
- **失注原因を自由記述だけにする**: 集計できず「価格で負け続けている」ことに気づけない
- **`BidCompetitor` を積算案件からも使い回す**: あちらは公告段階で見込みの競合を並べるもの、
  こちらは開札結果を書き写すもの。入札を経ない民間案件では `BidProject` が無く使えない
- **ガントのバーをドラッグして日付を直す**: 現場管理がフォーム方式で、操作が2つに割れる。
  入札案件のガントはドラッグ式だが、あちらは公告の期限を動かす別の操作
- **現場だけ「見積中」の呼び名を残す**: 同じ段階を画面ごとに呼び分けることになる。
  既存の表示を変えない利点より、同じ案件が2つあるように見える害のほうが大きい
- **値（`estimating`）ごと変える**: 既存データの書き換えが要る。表示を揃えるだけで足りる

## 影響

### 追加したモデル

| モデル | 内容 |
|---|---|
| `estimation.EstimationCompetitor` | 積算案件の競合。差額はプロパティで都度計算 |
| `estimation.EstimationPhase` | 積算案件の日程。`source_label` で公告からの取り込みを識別 |

`EstimationProject` に `lost_reason` / `lost_note` / `decided_on` を追加。
`BidProject.Status` に `estimating` を追加。**いずれも追加のみで、削除・改名はない**（規律7）。
`sites.Site.Status.ESTIMATING` は表示名だけを「見積中」→「積算中」に変更（値は据え置き）。

### 既存データへの影響

- 既に「検討中」になっている案件はそのまま。過去に積算開始した案件は入札案件一覧に出続ける。
  積算案件へ移したい場合は、その案件でもう一度「積算開始」を押す
- 既存の `EstimationProject` は `bid_project` が空のまま。受注・失注は使えるが、
  公告からの日程取り込みは入札案件が紐付いているものだけ

### 追加した画面

- 積算案件 詳細: 日程（ガント＋工程一覧）、受注・失注ボタン、競合の一覧
- 積算工程 追加・編集、受注の確定、失注の記録

### 変えた既存の挙動

- 入札案件一覧の「見積もりへ」ボタンは「積算へ移す」に変わり、押すと**積算案件の画面へ遷移**する
  （従来は入札案件一覧に戻っていた）。一覧から消えるため、戻り先が一覧だと押した結果が見えない
- 入札期限アラートの対象に「積算中」を追加（上表のとおり）

### テスト

- `tests/test_estimation_pipeline.py`（29件、新規）。引っ越し・二度押し・取り込み直し・
  受注・失注・差額計算・画面操作、およびテナント越境（他社の積算案件を開けない、
  工程・競合を足せない、受注にできない）
- `tests/test_notifications_alert_filters.py` の期待値を更新（積算中も期限アラートの対象）
