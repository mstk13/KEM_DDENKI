# ADR-0044: DB をまるごとクラウドのマネージド PostgreSQL へ、アップロードファイルをクラウドのストレージへ移す（アプリは社内PCに残す）

## ステータス

採用（2026-09-11）。**ベンダーは選定中**（計画: `docs/design/cloud_db_migration_plan.md`）

## コンテキスト

今後、現場の画像や個人情報（資格証の画像・健康診断の結果など）の登録が増える。
現在はアプリ・DB・アップロードファイル・バックアップがすべて社内の1台のPC（`DESKTOP-RMSK0VG`）にある。

| 項目 | 現状 |
|---|---|
| DB | Docker の `postgres:16-alpine`（ボリューム `pgdata`、DB名 `kensetsu_saas`） |
| アップロードファイル | Docker ボリューム `media_data`（`/app/media`） |
| バックアップ | 毎日 12:30 に `pg_dump` と media の tar を同じPCの `D:\backup\kem_ddenki` へ（14日保存） |
| 本番と開発 | 同じPCの2スタック（ADR-0010） |

盗難・故障・火災・ランサムウェアでは、本体とバックアップが一緒に失われる。
健康診断の結果は個人情報保護法の「要配慮個人情報」に当たり、保管の安全性を上げる必要がある。

プロダクトオーナーの判断（2026-09-11）:

1. アプリの機能は社内PCに入れたままにする
2. 取り込んだデータ、特に現場の画像・個人情報・会社の数字はクラウドに移す
3. 「日報は社内PCにあってもよい」が、DB を分けると作り直しが大きいと説明したうえで **DB はまるごとクラウドへ** 移すと決めた
4. ネットが切れたときも本当は社内で動き続けてほしい。**その仕様は別途決める**

## 決定

1. **DB はまるごと** クラウドのマネージド PostgreSQL（国内リージョン）へ移す。日報も含め、DB は分割しない
2. **アップロードファイル**（`FileField` / `ImageField` の保存先 = `STORAGES["default"]`）は、クラウドの S3 互換オブジェクトストレージ（国内リージョン・非公開）へ移す
3. **アプリ（Django・cron・Redis）と社内AI（Ollama）は社内PCに残す**。社内PCからクラウドの DB・ストレージへ暗号化した通信でつなぐ
4. ベンダーは `docs/design/cloud_db_migration_plan.md` の流れ（要件 → 候補 → 同じ条件の見積 → 評価表 → 開発環境での試験移行 → 承認）で選ぶ
5. ネット切断時は、日報などの入力だけ社内PCに一時保存し、復旧後にクラウドへ送る方向とする（2026-09-11 回答、計画書の O1）。
   どの入力を対象にするか・どの状況を想定するかは別途決める（計画書の O6）

## 捨てた選択肢

- **DB を分割する（日報は社内、数字と個人情報はクラウド）**: 今の DB は互いに参照している。
  日報は作業員（氏名・電話番号・生年月日・時給）と現場（受注金額）を外部キーで参照し、
  日報の承認では同じトランザクションで労務費（`CostTransaction` = 作業時間 × 時給）を作る（`apps/reports/services.py` → `apps/costs/services.py`）。
  Django は DB をまたぐ外部キーとトランザクションを扱えないため、日報・原価・月次サマリ・ホームなど多くの画面の作り直しになり、
  ネット切断時に「承認済みなのに原価が無い」食い違いも起きる
- **社内PCのまま、暗号化したバックアップだけクラウドへ送る**: 最も安く早いが、本体の保管場所は変わらず、要望（データをクラウドに置く）を満たさない。
  移行が終わるまでのつなぎとしては検討の余地がある
- **アプリごとクラウドへ移す**: 可用性は最も高いが、プロダクトオーナーはアプリを社内に残すと判断した。社内GPUでの推論（ADR-0010・ADR-0042）とも相性が悪い

## 影響

- **ネットへの依存**: 社内PCからクラウドの DB へ届かないと、日報を含むアプリ全体が使えない（オフライン仕様は未決）
- **表示の遅さ**: 1画面で DB への問い合わせが多い画面は、ネット越しで遅くなりうる。試験移行で測り、必要なら問い合わせを減らす
- **費用**: DB・ストレージの月額に加え、クラウドからのダウンロード量（画面表示・社内AIでの画像処理）に料金がかかりうる
- **PostgreSQL 拡張**: 現在は拡張（pgvector など）を使っていないため、一般的なマネージド PostgreSQL で動く見込み
- **コード変更（実装時）**: DB 接続の TLS 必須化・接続の再利用設定、ファイル保存先の切り替え（S3 互換の保存ライブラリの追加が必要。追加する PR でこの ADR の影響欄を更新する）
- **バックアップ運用**: `scripts/backup.sh`（同じPCへの保存）は、クラウド側の自動バックアップと別アカウント・別拠点への定期エクスポートに置き換える。手順は `docs/server_operations.md` を移行時に更新する
- **既存資料の前提変更**: `docs/design/設計判断の根拠書.md` 3.7「なぜセルフホストか」と TM 向け Q&A の「データは完全に自社管理」は、移行後に書き換えが必要
- この ADR の時点ではコード・設定の変更なし
