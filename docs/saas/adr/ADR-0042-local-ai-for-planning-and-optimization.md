# ADR-0042: 社内の実績データを使う AI（工程提案・予算とリソースの最適化）は社内のローカルAIで行う

## ステータス

採用（2026-09-11）。**実装は品質評価のあと**。ADR-0010 の層C と「ローカル失敗時の API 自動フォールバック」を、対象タスクについて置き換える

## コンテキスト

ADR-0010 で AI 推論を3層に分け、分析・提案（層C: 工程提案 / 工程リスク / コスト最適化、`apps/ai/services/llm_advisor.py`）は
Claude API のままとし、ローカル推論に失敗したら API へ自動で戻すと決めた。現状の画面の既定モデルも `haiku`（API）である。

ADR-0041 で DB とアップロードファイルをクラウドへ移すと決めた。そのうえでプロダクトオーナーから次の要望があった（2026-09-11）。

> できればローカルのAIで、過去の現場の施工実績から工程提案や予算及びリソースの最適化まで行ってほしい。

社内PCの推論環境（ADR-0010・`docs/saas/design/local-inference-runbook.html`）:

| 項目 | 値 |
|---|---|
| GPU | RTX 3060 12GB（Windows ネイティブの Ollama） |
| 生成モデル | Qwen3-8B Q4_K_M（約 58 tok/s、VRAM 約 6GB） |
| 埋め込みモデル | bge-m3 |
| 既存の実績集計 | `apps/ai/services/data_collector.py`（`find_similar_completed_sites` など）、`ml_predictor.py`（`CostPredictor`） |

## 決定

1. **社内の実績データ**（現場・工程・原価・予算・日報・出社予定・作業員）を使う AI 機能は、社内PCのローカルAI（Ollama）で行う。
   対象: 工程提案・工程リスク分析・コスト最適化、および今後の予算とリソース（人員配置）の最適化
2. これらのタスクでは、**ローカル推論に失敗しても Claude API へ自動で戻さない**。失敗したら「今は使えない」と表示する
   （黙って社外へ送らないため。ADR-0010 決定4 を対象タスクについて置き換える）
3. **数字はLLMに計算させない**。予算・工数・人員の数値は、過去の完工現場の集計・予測（`CostPredictor`・類似現場の抽出）と
   計算（制約つきの割り当てなど）で出し、ローカルLLMは「根拠の説明」と「提案文」に使う。8B モデルは計算と最適化の正確さが足りないため
4. **切り替え前に品質を評価する**。過去の完工現場を使い、ローカルの出力と現行の出力を並べて、プロダクトオーナーが採否を決める
5. データはクラウドの DB から社内PCのアプリが読み、ローカルAIに渡す。AI の結果は DB（AILog など）に保存し、
   社内PCのディスクに実績データの写しを残さない
6. 社内の実績データを含まない処理（公開資料である労務単価PDFの構造化、品目名マッチングの一部）は ADR-0010 のまま。
   これもローカルに寄せるかは未決（`docs/design/cloud_db_migration_plan.md` の O5）

## 捨てた選択肢

- **現行どおり API（層C）を使う**: 提案の質は高いが、会社の数字と個人情報を社外の API に送る。プロダクトオーナーの方針に合わない
- **個人名や金額を伏せて API に送る**: 伏せる処理の作り込みと漏れの確認が要り、金額そのものが提案の材料なので伏せると質が落ちる
- **クラウドの GPU で推論する**: 月額が大きく、データを社内の外で処理することになる

## 影響

- 提案の質が API より下がる可能性がある。決定4の評価で確認する
- GPU は社内PCの画面表示・品目名マッチング（層A・B）と取り合う。重い処理は夜間にまとめる
- 12GB の VRAM では 14B 以上のモデルが載らない（ADR-0010）。質が足りなければ GPU の増強が選択肢になる
- ネットが切れていると、クラウドの DB を読めないため AI も使えない（ADR-0041 のオフライン仕様に従う）
- 実装時の変更: `apps/ai/views.py` の既定モデルをローカルに、`llm_advisor.py` の対象タスクで API へのフォールバックを止める、最適化の計算を追加
- この ADR の時点ではコードの変更なし
