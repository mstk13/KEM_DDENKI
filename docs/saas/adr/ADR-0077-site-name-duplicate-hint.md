# ADR-0077: 現場名の重複に、登録する前に気づけるようにする

## ステータス

採用（2026-09-16）

## コンテキスト

プロダクトオーナーの依頼（2026-09-16）:

1. 入札案件の**編集画面**で状態を「積算中」にした案件が、積算案件に移動していない
2. 現場名が重複しているものが出ている。似た名前が入力されたら、既存のデータを候補として出したい

### 1 について

ADR-0076 で「積算中にしたら積算案件へ引っ越す」を入れたが、通したのは
**「積算へ移す」ボタンと一覧のインライン編集**の2経路だけだった。

状態は他からも変えられる。**編集画面のフォーム**と**新規登録**がそれで、
どちらも素の `form.save()` を通る。その経路では積算案件が作られないまま
入札案件一覧の既定の絞り込みから外れ、**行き先の無い迷子の案件**になる。

ADR-0076 の時点で「新しい状態を足すと、状態を列挙している既存のコードが
黙ってその案件を落とす」ことには気づいていたが、**状態を書き込む側**の
洗い出しが足りていなかった。

### 2 について

同じ現場が別々に登録される原因は、名前そのものではなく**表記のゆれ**にある。

    七沢自然ふれあいセンター改修工事
    七沢自然ふれあいセンター　改修工事      ← 全角スペース
    七沢自然ふれあいｾﾝﾀｰ改修工事           ← 半角カナ
    （仮）七沢自然ふれあいセンター改修工事   ← 頭の注記
    七沢自然ふれあいセンター改修            ← 「工事」なし

顧客名には既に `<datalist>` の入力候補があるが（`_customer_datalist.html`）、
**現場名には無い**。加えて `<datalist>` はブラウザが入力文字を前方・部分一致で
拾うだけなので、上のような1文字のゆれで候補から外れる。

## 決定

### 1. 状態を書き込む経路を1つの関数に集める

`bids.services.sync_estimation_move(bid_project, created_by)` を作り、
**状態を保存しうるすべての経路の直後に通す**。

| 経路 | 場所 |
|---|---|
| 「積算へ移す」ボタン | `bid_start_estimation`（`start_estimation` を直接呼ぶ） |
| 一覧・詳細のインライン編集 | `bids.inline_edit._after_save` |
| 編集画面のフォーム | `bids.views.project_edit` |
| 新規登録のフォーム | `bids.views.project_create` |
| Django admin | `bids.admin.BidProjectAdmin.save_model` |

「積算中」でなければ何もしないので、他の状態への変更を邪魔しない。
`start_estimation` は何度呼んでも現場・積算案件をそれぞれ1つしか作らない
（ADR-0031）ため、引っ越し済みの案件に対して呼んでも増えない。

**判断をビューに書かない。** 経路ごとに `if status == ...` を書くと、
次に経路が増えたときにまた1つだけ抜ける。抜けたことは画面に出ないので、
今回と同じく「一覧から消えた」と言われて初めて分かる。

編集画面・新規登録でも、引っ越したときは**積算案件の画面へ遷移**する。
入札案件一覧に戻すと、その案件はもう既定では出ないため結果が見えない。

### 2. 現場名は「均してから」似ているものを探す

`apps/sites/name_match.py` に、比べるための正規化と類似度を置く。

1. **正規化** — NFKC（全角英数・半角カナを寄せる）→ 括弧の注記を落とす →
   定型語（工事・その1・株式会社…）を落とす → 区切り文字を落とす
2. **類似度** — 正規化後に `difflib.SequenceMatcher`。
   ただし**片方がもう片方を丸ごと含むときは 1.0** とする
   （「○○改修」と「○○改修工事（その2）」は文字数差で比率が落ちるため）
3. **しきい値 0.72** — 「その1／その2」の違いだけの2件が拾える程度。
   下げすぎると同じ市の別現場が並び、かえって見落とす

画面は2段構えにする。

- **`<datalist>`**（`site-name-options`）— 顧客名と同じ形。JavaScript が
  動かなくても候補は出る
- **「似た現場」欄** — 入力が止まってから `/sites/name-suggestions/` に1回聞き、
  似た現場を現場コード・状態・工期つきで並べる。リンクで開ける

### 3. 重複は**弾かない**

同じ建物の別年度の工事が同じ名前になることは正当にある
（「○○小学校電気設備改修工事」が毎年ある）。

**気づかせるところまでが機械の仕事**で、分けるか一つにするかは人が決める。
バリデーションエラーにすると、正当な同名を登録するために名前を捻じ曲げることになり、
かえって表記が荒れる。

## 捨てた選択肢

- **`<datalist>` だけで済ませる**: 前方・部分一致しか効かず、全角スペース1つで
  候補から外れる。今回の重複はまさにそれで起きている
- **同じ名前を保存時に弾く**: 別年度の同名工事が正当にある（決定3のとおり）
- **1文字打つたびに問い合わせる**: 現場が増えるほど無駄が増える。
  入力が止まってから 400ms 後に1回だけ聞き、3文字未満では聞かない
- **類似度の計算を SQL に寄せる**: PostgreSQL の `pg_trgm` なら速いが、
  テストは SQLite で動かしており両対応が要る。現場は数千件の規模で、
  Python 側で回しても待たされない
- **状態の同期を `post_save` シグナルでやる**: `start_estimation` が同じ行を
  保存し直すので再入する。取り込み・マイグレーション・テストでも発火し、
  どこから呼ばれたのか追えなくなる
- **既存の重複データを自動で統合する**: どれを残すかは日報・原価・写真の
  ぶら下がり方を見て決めることで、名前だけでは決められない

## 影響

### モデル・マイグレーション

**なし。** 追加したのは照合モジュール・ビュー・画面と、サービス層の関数1つ。

### 既存データ

**既に登録されている重複は、そのまま残る。** この変更が効くのは
これから登録・編集するときだけで、過去分を自動で統合することはしない。

登録済みの重複を片付けるときは、現場の編集画面で名前を直すと
「似た現場」欄に相手が出るので、どちらに寄せるかを見ながら進められる。

### 追加した画面・API

| 場所 | 内容 |
|---|---|
| `/sites/new/`・`/sites/<pk>/edit/` | 現場名の候補（datalist）と「似た現場」欄 |
| `/sites/name-suggestions/` | 似た現場を返す（ログイン必須・自社のみ） |

### テスト

- `tests/test_sites_similar_names.py`（25件、新規）。表記のゆれ5通りを拾うこと、
  関係のない現場を拾わないこと、候補が登録を止めないこと、テナント越境
- `tests/test_estimation_pipeline.py` に編集画面・新規登録からの引っ越し4件を追加
