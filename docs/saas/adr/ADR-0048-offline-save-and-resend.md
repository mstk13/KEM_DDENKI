# ADR-0048: 圏外で入力を端末に保存し、電波が戻ったら送り直す（まず写真・書類を含む入力）

## ステータス

採用（2026-09-12）。第1段（基盤＋資格証・健康診断・納品の記録）

## コンテキスト

プロダクトオーナーの回答（2026-09-12、`docs/design/cloud_db_migration_plan.md` の O6・O10）:

- スマホが圏外のときは、圏内に戻ったときにデータを送る
- 対象は **現場で使う入力すべて**。**健康診断（要配慮個人情報）も対象**にする
- 出す順番は **写真付きの入力から**（そのあと日報・安全確認・出社予定）

アプリは社内PCにあり、利用者は Tailscale 経由の HTTPS（`…ts.net`）で開く。今は Service Worker が無く、
圏外で送信するとブラウザのエラー画面になり、入力（撮った写真を含む）が失われる。

## 決定

### 1. 仕組み

```
 入力画面（data-offline-form）
   │ 送信
   ├─ 電波あり → ふつうに送る（端末の識別番号 client_request_id を付ける）
   │              └ 通信エラー → Service Worker が入力を端末に保存
   └─ 電波なし → 送らずに端末に保存
                    │
 端末の置き場（IndexedDB）──── 電波が戻る・画面を開く・1分ごと ───▶ 送り直し（X-Offline-Resend: 1）
                                                                     │
 サーバー: offline_resendable が識別番号で2回目を見分け、登録を二重にしない ◀─┘
```

| 部品 | 場所 | 役割 |
|---|---|---|
| Service Worker | `/sw.js`（`apps/offline/views.py` がテンプレート `offline/sw.js` から配る） | 圏外で開ける入力画面を控える・送信の通信エラーで入力を保存する・静的ファイルを控える |
| 端末の置き場 | `static/js/offline-db.js`（画面と Service Worker で共有） | 入力を IndexedDB に入れる。写真・書類はファイルのまま入れる。CSRF トークンは入れない |
| 画面側 | `static/js/offline.js`（ログイン後の全画面） | 識別番号を付けて送る・圏外なら保存・送り直し・「未送信 N」の表示・ログアウト前の確認 |
| 未送信の一覧 | `/offline/`（`offline/outbox.html`） | 端末に残っている入力と状態（未送信・ログインが必要・送れなかった）。「送る」「削除」 |
| 二重登録の防止 | `apps/offline/decorators.py` の `offline_resendable`、モデル `OfflineSubmission` | 識別番号ごとに1回だけ受け付ける。送り直しには JSON で結果を返す |
| 対象画面の一覧 | `apps/offline/pages.py` の `OFFLINE_FORM_PATTERNS` | Service Worker が扱う画面の URL の形。ビューに `offline_resendable` を付けたものだけを載せる（テストで確かめる） |

### 2. 二重登録の防ぎ方

電波の弱い場所では「サーバーには届いたが応答が端末に戻らない」ことがあり、同じ入力が2回届く。

- 端末が送信ごとに識別番号（UUID）を付ける。送り直しでも同じ番号を使う
- サーバーは（会社・ユーザー・識別番号）で一意の記録を作ってからビューを実行する。登録できた（リダイレクトが返った）ら記録を残し、
  入力に誤りがあった（画面が返った）ら記録ごと取り消す（直して同じ番号で送り直せる）
- 2回目は実行せず、1回目の移動先を返す。同時に届いても一意制約で片方を止める
- 識別番号が無い・読めない送信は、今までどおり実行する（既存の画面・テストに影響しない）

### 3. 送り直しの結果

| 結果 | 端末の扱い |
|---|---|
| 登録できた・登録済みだった（JSON `ok: true`） | 端末から消し、「送信しました」と出す |
| ログインが切れていた（ログイン画面へ飛ばされた・403） | 残して「ログインが必要」。ログインし直すと自動で送る。残りの送り直しも止める |
| 入力に誤りがあった（422） | 残して「送れませんでした」と理由を出す。一覧から削除するか、画面を開いて入れ直す |
| 通信できない | 残して次の機会に送る |

### 4. 端末に置く情報の守り方（健康診断を対象にしたため）

- 端末の置き場はブラウザの領域で、アプリ側では暗号化しない。**端末の画面ロックを必須**にする（一覧画面に明記）
- 送り終えたらすぐ消す
- ログアウトのときに、未送信の入力と画面の控えを消す。未送信があれば先に確かめる
- Service Worker が控える画面は、対象の入力画面と一覧画面だけ（ほかの画面の中身は控えない）

### 5. 使える条件

- Service Worker は HTTPS のときだけ動く。**IP を直接打つ http の URL では、圏外で画面を開けない**（圏外での保存と送り直しは動く）
- 圏外で開けるのは、**電波のあるときに一度開いた入力画面**だけ
- iPhone はバックグラウンドでの自動送信（Background Sync）が無いので、**アプリを開いたとき・電波が戻ったとき**に送る

## 捨てた選択肢

- **バックグラウンド同期（Background Sync API）だけに頼る**: iPhone の Safari に無い
- **送り直しを Service Worker だけで行う**: 結果（ログイン切れ・入力の誤り）を画面に出しにくい。画面側で送り、Service Worker は保存に専念させる
- **画面ごとに JSON の API を作る**: 既存のフォーム（ファイルを含む）とビューをそのまま使えるよう、同じ POST を送り直す形にした
- **健康診断を対象外にする**: プロダクトオーナーが対象にすると決めた。上の4の守り方を条件にする

## 影響

- 追加: `apps/offline`（モデル・デコレータ・ビュー・管理画面・マイグレーション）、`templates/offline/`、
  `static/js/offline-db.js`・`offline.js`、`tests/test_offline_outbox.py`
- 変更: `config/settings.py`（INSTALLED_APPS）、`config/urls.py`（`/sw.js`・`/offline/`）、`templates/base.html`（未送信の表示・スクリプト・ログアウトの印）、
  資格・健康診断・納品の記録の画面とビュー（`offline_resendable` と `data-offline-form`）、`static/css/style.css`
- マイグレーション: `offline/0001_initial`（新しいテーブルの追加のみ）
- 新規依存なし
- **次の段**: 日報・安全確認・出社予定（出社予定は JavaScript の送信なので、同じ置き場に入れる別の入口が要る）。
