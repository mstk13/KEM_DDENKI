# ADR-0102: 他人の日報・勤怠に誰が触れるか（修正はログで、削除と勤怠は権限で抑える）

## ステータス

採用（2026-09-19）。**同日に改訂**（「日報の修正」を元に戻し、抑止をログに移した。下記 §改訂）

## コンテキスト

プロダクトオーナーの指示（2026-09-19）:
「日報および勤務時間の管理で、他人の日報や勤務時間などは社長および IT の人のみが
管理できるようにしてください。また、アクセス権限を IT の人が管理できるようにして、
アプリや機能ごとに IT と社長がアクセス権限を管理できる機能を作成してください」。

調べたところ、**穴は実在した。** 一方で後半の「機能ごとの権限管理画面」は
ADR-0082 で既に作られており、足りないのは入口だけだった。

### 塞ぐ前の状態

| 経路 | 塞ぐ前 |
|---|---|
| 日報の**承認** | ✅ 既に社長と IT のみ（ADR-0007 / ADR-0039） |
| 日報の**編集** | ❌ `get_object_or_404` のみ。**pk が分かれば他人の日報を直せた** |
| 日報の**削除** | ❌ docstring に「ログインしていれば誰でも削除できる」と明記 |
| 勤怠のマス塗り・ダイアログ保存 | ❌ 本人確認なし。他人の予定を書き換えられた |
| 勤怠の**一括埋め** | ❌ 同上。`worker` を空にすると**在籍中の全員**が対象 |
| 勤怠の**日まとめ消し** | ❌ 権限チェックなし。**全員の予定をその日ぶん消せた** |

最後の1つが最も重い。ログインできる人なら誰でも、会社全体の勤務予定を1回の
POST で消せた。

### IT の判定が2つに分かれていた

| 既存の判定 | IT の印 |
|---|---|
| `can_approve_report`（ADR-0039） | `developer` ロール **または役職（Position）「Developer」** |
| `can_manage_documents`（ADR-0092） | **職種（JobTitle）に「IT」を含む** |

役職と職種という別の項目を見ている。片方だけで新しい判定を書くと、
**実際の IT 担当が締め出される**恐れがあった。

## 決定

### 1. 絞るのは「直す・消す」だけ。閲覧は今までどおり

同日のやり取りで確定した。他人の日報を**見られなく**すると、現場担当が現場の
日報を見る・事務員が集計する・原価や月次集計や PDF が読む、という経路が全部
止まる。今回は書き込みだけを絞る。

### 2. 他人の分を触れるのは社長・IT・事務員

`can_manage_others_work_records(user)` に集める。事務員を含めるのは同日の判断で、
日報の取りまとめや打ち直しをしているため。

**自分の分は誰でも直せる。** 本人かどうかは `can_edit_report` /
`can_edit_attendance_of` が見る。

### 3. IT の判定は3つの印の和集合にする

`is_it_staff(user)` を作り、`developer` ロール・役職「Developer」・職種に「IT」の
**どれかが立っていれば IT** とする。締め出しを避けるため。

**既存の `can_approve_report` と `can_manage_documents` はそのままにした。**
そちらを寄せると承認できる人が黙って増えるため、この PR では触らない。

### 4. 権限管理の画面を社長と IT に開ける

`settings_admin_required` を作り、`settings` の admin 権限に加えて社長と IT を
通す。従来は `module_permission_required("settings", "admin")` だけで、
`developer` ロールが本番で0件のため **IT は権限画面に入れなかった**
（ADR-0039 に同じ問題が日報承認で起きたと書いてある）。おそらくこれが
「IT がアクセス権限を管理できるように」という指示の発端。

## 捨てた選択肢

- **閲覧も他人の分を隠す**: 指示の文面には近いが、現場・事務・原価の各経路が
  同時に止まる。影響範囲が広すぎるため、書き込みだけを先に塞いだ
- **各ビューに個別の判定を書く**: 勤怠だけで書き込みの入口が4つあり、
  `plan_fill` は「全員」も取れる。1か所に集めないと必ず漏れる
- **事務員を外す**（指示の文面どおり社長と IT のみ）: 事務員が代行入力して
  いる運用が止まる。同日に確認して含めることにした
- **IT の判定を役職か職種の片方に決める**: どちらが本番の実態か分からないまま
  選ぶと担当者を締め出す。和集合なら取りこぼさない
- **新しい権限管理画面を作る**: ADR-0082 の「作業員 × 機能」のチェック表が既に
  あり、印は `AppAccess`（履歴つき）と `Worker.allowed_apps` の両方に書かれる。
  作り直す理由がない

## 影響

- モデル・マイグレーションの変更なし。判定とビューのガードのみ
- **勤怠は一括操作の入口が塞がる。** 全員ぶんの「日まとめ消し」「一括埋め」は
  社長・IT・事務員だけになる。一般の作業員は自分の分だけ
- `tests/test_others_work_records_permission.py` で、経路ごとに
  「本人は通る／他人は 403／社長・IT・事務員は通る」を固定した

## 残っている宿題（この ADR の範囲外）

- **機能ごとのチェック表で、勤怠の印がまだ効かない。** `access_matrix.py` の
  `UNMIRRORED_APPS` に `attendance` が入っており、印は `AppAccess` に残るが
  入口（`Worker.allowed_apps` → ミドルウェア）は変わらない。
  `estimation` / `ai` / `document_alerts` も同じ
- **IT の判定が3通りのまま。** `is_it_staff` に寄せるかは、承認できる人が
  増える影響を確認してから決める
- **`AppAccess` はまだミドルウェアから読まれていない**（ADR-0030 の expand 段階）。
  切り替えは後続の PR

## 改訂（2026-09-19、同日）

プロダクトオーナーからの追加の指示:
「日報の登録は現場ごとに複数人まとめてできるようにしてほしくて、変更修正も同様
なのですが、他社による書き換えが嫌なので、書き換えた人のログをとるなど、
アプリケーション内で誰がどのような変更を行ったかログをとれるようにしておいてください」。

### なぜ戻したか

**上の決定と衝突していた。** 日報は現場ごとに複数人ぶんをまとめて登録・修正できる
（ADR-0056）。他人の日報の修正を社長・IT・事務員に絞ると、**現場担当が現場の
全員ぶんを直せなくなり、まとめて直す機能の意味が無くなる。**

### 改訂後の決定

| 操作 | 他人の分 | 理由 |
|---|---|---|
| 日報の**登録**（複数人まとめて） | 誰でも | 元からできた。ADR-0056 |
| 日報の**修正** | **誰でも**（戻した） | まとめて修正を残すため。**抑止はログで行う** |
| 日報の**削除** | 社長・IT・事務員 | **戻せない操作**なので残す |
| **勤怠**の書き換え | 社長・IT・事務員 | 今回の指示の対象外。全員の予定の一括削除は特に危険 |

### 抑止をログに移す

権限で止めない代わりに、**誰がいつ何を直したかを追えること**が前提になる。
調べたところ記録自体は既に揃っていた。

- `simple_history.middleware.HistoryRequestMiddleware` が有効で、**変更者が毎回記録される**
- 日報の**全項目が履歴に残る**ため、版どうしの差分を復元できる
- `/audit-log/` で全モデル横断の検索ができる

足りなかったのは**読む導線**なので、2つ足した。

1. **日報の詳細画面に「変更履歴」欄。** `/audit-log/` は全モデル横断で、
   1件を追うには向かない
2. **直前の版との差分。** 「作業内容: 配線 → 配線と結線」の形で出す。
   項目名は画面の言葉（`verbose_name`）に直し、選択肢のある項目は表示用の値にする

`apps/core/change_log.py` に汎用で書いたので、現場や勤怠にも同じ欄を足せる。

### この改訂で崩れてはいけないもの

**変更者が記録されなくなったら、緩めた判断の前提が消える。**
`tests/test_report_change_log.py` で、画面から直したときに `history_user` が
入ることと、詳細画面に誰が・いつ・何をが出ることを固定した。

### 「他社による書き換え」について

指示の文面は「他社」だが、**他社のデータには元から到達できない**
（`TenantModel` と `CompanyScopedManager`、越境テストあり）。
「他者」の意味であれば、上記のログで追える。
