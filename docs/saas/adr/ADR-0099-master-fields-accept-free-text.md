# ADR-0099: 現場・積算のマスタ欄は、候補を出しつつ手入力も受け付ける

## ステータス

採用（2026-09-18）

## コンテキスト

プロダクトオーナーの依頼（2026-09-18）:

> このアプリの現場や積算の登録時のインターフェスは、すべて候補をだして、
> もしその候補の中に選びたいものがないときはこちらで手入力できるようにしてください。

**プルダウンだけの欄は、マスタに無いものを選ぼうとした時点で作業が止まる。**
「先にマスタ画面へ行って登録し、戻ってきて選び直す」という2画面の往復が要る。
現場や積算のように**外の書類を見ながら入れる**画面では、そこで手が止まり、
「あとで直す」になって結局入らない。

発注機関を自由入力にしたとき（ADR-0080）と同じ問題が、他の欄にも残っていた。

| 欄 | 今まで | 起きること |
|---|---|---|
| 現場の工程 > 工種 | プルダウン | 新しい工種の工程を入れられない |
| 積算品目 > 材料・工種 | プルダウン | 品目の登録が材料マスタ待ちになる |
| 発注機関 > 顧客 | プルダウン | 発注機関の登録が顧客マスタ待ちになる |
| 仕入実績 > 発注先 | プルダウン | 初めての業者からの仕入を記録できない |
| 内訳明細 > 積算品目 | プルダウン | 内訳書を打ちながら品目を足せない |
| 積算案件 > 現場 | プルダウン | 現場の登録待ちで積算を始められない |

## 決定

### 1. マスタを指す欄は、文字入力 + `<datalist>` にする

入力欄は文字にし、登録済みのものを `<datalist>` で候補に出す。
候補に無い値もそのまま送れて、保存時にマスタへ登録する。

対象は上の6か所。引き当てと登録は `apps.core.master_input` の1か所にまとめた。
日報が現場・工種を名前で自動登録していた仕組み（`reports.forms`）も、同じ場所へ寄せた。
**同じことを2通りに書くと、いつか結果が食い違う。**

### 2. 引き当ては完全一致だけ。似た名前は寄せない

表記ゆれを正規化して寄せることは**しない**（ADR-0080 と同じ）。
「厚木市」と「厚木市教育委員会」は似ていて別物で、寄せると積算基準を取り違える。

**二重登録を防ぐのは候補の一覧の役目。** 打ちかけの文字で既存のものが出てくるので、
同じものを作ってしまう手前で気づける。ここで機械が寄せると、
別物を1つにしてしまう事故のほうが重い。

### 3. コードは自動で採番する

マスタの多くは (company, code) が一意でコードが要る。人に考えさせるとそこで止まるので、
使われていない連番（`W0001` `C0001` …）を振る。

### 4. 必須項目は、呼び出し元の欄から埋める

材料・積算品目は**単位**が必須。品目の登録画面なら品目の単位、内訳明細なら明細の単位を
そのまま使い、分からなければ「式」にする。**人に聞き直すと、そこで入力が止まる。**

### 5. 必須の欄は、自由入力にしても必須のまま

現場の工程の工種（`Process.work_type`）は NOT NULL なので、欄も必須のままにする。
**自由入力にすることと、空で保存できることは別の話。**

### 6. 現場の欄は、既存の現場名を候補に出す

積算案件の現場欄は、既にある現場名を候補に出す（ADR-0077 と同じ考え方）。

現場の二重登録は実際に起きている（2026-09-17 の「高橋住宅／高橋アパート」
「厚木あゆ祭り／あゆ祭り／厚木鮎まつり」）。**自由入力を広げるなら、
同時に気づける仕組みが要る。** 打ちかけで「高橋ア…」と入れれば
「高橋アパート」が候補に出るので、別名で作る手前で止まる。

## 自由入力に「しない」欄

| 欄 | 理由 |
|---|---|
| 現場 > 現場担当者・積算担当者（`User`） | **ログインできるアカウントを、入力欄から作ってはいけない** |
| 積算案件 > 入札案件 | 台帳の行。名前から作るものではない |
| 積算案件 > 積算基準 | 発注機関と適用開始日が要る。名前だけでは作れない |
| 内訳明細 > 歩掛 | 積算基準に属する計算データ。マスタではない |
| 内訳明細 > 親明細 | 同じ内訳書の行。他現場の明細にぶら下げられては困る |
| 名寄せレビュー > 紐付先品目 | **寄せ先を選ぶ画面**。ここで新規作成できたら名寄せにならない |
| 写真登録 > 現場 | 写真を登録する画面で現場を新設しない |

**「すべて」の依頼だが、選ぶ対象がマスタでない欄は外した。** そこを自由入力にすると、
台帳や計算データが入力欄から増えて、かえって辻褄が合わなくなる。

## 捨てた選択肢

- **プルダウンに「その他」を足して別欄に書かせる**: マスタに入らないので次も打つことになり、
  表記ゆれが増える（ADR-0080 で既に捨てている）
- **入力した名前を似た名前に寄せる**: 別物を1つにする事故のほうが重い（決定2）
- **単位や区分を後から聞くダイアログを出す**: 止めたくないのに止まる。既定値で作って、
  必要なら後からマスタ画面で直すほうが早い
- **マスタ登録を管理者だけに許す**: 現場で入力する人が止まる。
  誰が作ったかは `created_by` に残るので、後から辿れる
- **欄ごとに個別の引き当て関数を書く**: 既に日報（`reports.forms`）と積算
  （`resolve_or_create_orderer`）で2通りある。3通り目を作らず1か所へ寄せた

## 影響

### モデル・マイグレーション

**無し。** フォームと画面だけの変更で、モデルの形は変えていない。

### 変わる画面

| 場所 | 変わり方 |
|---|---|
| 現場 > 工程の追加・編集 | 工種がプルダウン → 候補つきの文字入力（必須のまま） |
| 積算 > 品目の登録・編集 | 材料・工種が候補つきの文字入力 |
| 積算 > 発注機関の登録・編集 | 顧客が候補つきの文字入力 |
| 積算 > 仕入実績の登録 | 発注先が候補つきの文字入力（画面の名前も「仕入先」→「発注先」に統一） |
| 積算 > 内訳明細の追加・編集 | 積算品目が候補つきの文字入力 |
| 積算 > 案件の登録・編集 | 現場が候補つきの文字入力 |

送信する項目名が変わる（`work_type` → `work_type_name` など）。
同じ画面を叩いていた既存のテストも合わせて直した。

### 運用への影響

**マスタが今までより増えやすくなる。** 打ち間違いがそのままマスタになる経路ができる。
これは候補の一覧で減らす方針で、**寄せる処理は入れない**（決定2）。
増えすぎた場合は、現場については名寄せの画面（ADR-0084・ADR-0090）で後からまとめられる。
他のマスタに同じ仕組みが要るかは、実際に荒れてから決める。

### テスト

`tests/test_free_text_masters.py`（28件、新規）。
6か所それぞれで候補に無い名前がマスタに登録されること、既にある名前を引き当てて
二重に作らないこと、似た名前を寄せないこと、コードの採番、単位の引き継ぎ、
必須の欄が空にできないこと、候補が画面に出ること、テナント越境。
