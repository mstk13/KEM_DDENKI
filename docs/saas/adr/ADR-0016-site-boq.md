# ADR-0016: 内訳書・内訳明細書を現場に持たせる

## ステータス

採用（2026-08-21）

## コンテキスト

現場詳細に「内訳書」と「内訳明細書」を記載する枠が無い、という指摘を受けた。
実装を確認したところ、器そのものは既にあったが**現場から辿れなかった**。

### 既にあったもの

`estimation.BoqLine` が公共建築工事内訳書標準書式の4階層を持っている。

| 階層 | 一般的な呼び方 |
|---|---|
| 種目別内訳書 / 科目別内訳書 / 中科目別内訳書 | **内訳書** |
| 細目別内訳書 | **内訳明細書** |

項目も名称・仕様・単位・数量・単価・金額・備考が揃っており、
`ADR-0008` の積算アプリで作った CRUD と Excel 出力（`boq_export.py`）もある。

### 何が足りなかったか

1. **表示・入力が積算案件詳細（`estimation:project_detail`）にしか無い。**
   現場詳細からは一切見えない
2. **`BoqLine` は `EstimationProject` にしかぶら下がらない。**
   `EstimationProject.orderer` は必須（PROTECT）なので、
   **発注機関を持たない民間工事の現場では内訳書を作れない**
3. 現場詳細にある「見積内訳」は取り込んだ見積書の明細（`materials.QuotationItem`）で、
   内訳書とは別物。ここを内訳書だと誤解しやすい

## 決定

### 1. `BoqLine` の持ち主を「積算案件 **または** 現場」にする

```
BoqLine
  ├ project FK (EstimationProject) … null 許容に変更
  └ site    FK (sites.Site)        … 新設・null 許容
```

どちらか一方が必ず入る。DB の `CheckConstraint`（`boqline_owner_required`）で担保する。
両方に入れるのも禁じる——どちらの内訳書に出すべきか決まらなくなるため。

**モデルは階層で分けない。** 内訳書と内訳明細書は同じツリーの深さの違いに過ぎず、
別モデルにすると親子を跨いだ集計と並べ替えが二重管理になる。
表示側で `is_meisai`（細目別か）を見て呼び分ける。

### 2. 内訳明細書の判定は「数量×単価があるか」で行う

取込時の階層判定は次の順にする。

1. 「階層」列があればそれに従う（自社が出力した Excel の読み戻し）
2. **数量と単価がそろっている行は細目別（内訳明細書）**
3. 名称のインデントの深さ＝見出しの深さ（中科目別まで）
4. どれも無ければ、金額などを持つ行を細目別、持たない行を科目別

当初はインデントの段数だけで決めていたが、実ファイルのインデントは
2段だったり4段だったりばらつくため、**最下層が細目別にならなかった**。
内訳明細書とは「数量×単価で金額を積む階層」のことなので、そこで判定するのが実態に合う。

インデントを使う様式かどうかは**表全体で**決める。行ごとに判断すると、
インデント0の最上位行だけが別の規則で判定され、金額を持つ種目行が細目別になってしまう。

### 3. 取込は決定論的に読み、LLM は保険に留める

`ADR-0010` の層B（労務単価PDF）で得た教訓をそのまま適用する。
内訳書は列を持つ表なので、見出し行さえ見つかれば座標から直接読める。

- Excel（.xlsx）… `openpyxl` で全シートを走査
- PDF … `pdfplumber` の表抽出。**表として取れなかったページだけ**
  層Bのローカル推論に回す（届かなければ静かに諦める）

PDF のローカル推論失敗時に **Claude API へは自動フォールバックしない。**
内訳書1ページは入力が大きく、自動で API に上げると取込1回のコストが読めなくなる。
層Aの埋め込みや戦略5のような小さな呼び出しとは性質が違う。

### 4. 親子は「並び順と階層」から組み立て直す

表形式で編集したあと `rebuild_tree()` で作り直す。
表の中に「親明細」のセレクトを置くと、行を1つ挿すたびに人が選び直すことになり、
まず維持できない。

## 理由

### なぜ現場に直接ぶら下げるのか

積算案件経由のままにすると、内訳書を作るのに**先に発注機関の登録が要る**。
民間工事にはそもそも発注機関が無く、「内訳書を書きたいだけ」の利用者に
積算案件という別概念を先に理解させることになる。

`site` FK の追加はマイグレーション1本で済み、既存の積算案件経由の経路は
そのまま動く（`project` を null 許容にしただけ）。

### なぜ小計・合計行を捨てるのか

取り込むと二重計上になる。合計は最上位（親を持たない）行の金額から計算する。
「種目別だけを足す」にすると、種目を立てずに細目だけ並べた内訳書
——現場から直接作る場合はこれが普通——で合計が0円になる。

### なぜ読めない値を 0 にしないのか

「一式」計上のように数量・単価が読めない行がある。0 を入れると
**読めた 0 と区別できなくなる**。None のまま持ち、画面には `-` と出す。
`calc_amount()` も数量・単価が揃っていなければ金額を上書きしない
（取り込んだ内訳書には金額だけが入っている行が普通にある）。

## 影響

### コード変更

- `apps/estimation/models.py` … `BoqLine` に `site` を追加、`project` を任意化、
  `CheckConstraint`、`is_meisai` / `indent_depth`、`calc_amount` の説明追記
- `apps/estimation/migrations/0005_...` … 上記＋ `HistoricalBoqLine`
- `apps/estimation/services/boq_import.py` … **新設。** Excel / PDF の取込
- `apps/estimation/services/boq_export.py` … 現場からの出力に対応、
  合計を「最上位行の合計」に修正
- `apps/estimation/forms.py` … `BoqLineRowForm` / `BoqLineRowFormSet` /
  `BoqImportForm` を追加。`BoqLineForm` に `parent` を追加
  （作成ビューが `initial` で渡していたが fields に無く、反映されていなかった）
- `apps/estimation/admin.py` … 一覧に `site` を追加
- `apps/sites/views.py` `urls.py` … `boq_edit` / `boq_import` / `boq_export`
- `templates/sites/detail.html` … 内訳書カード（表・合計・明細だけ表示）
- `templates/sites/boq_edit.html` `boq_import.html` … 新設
- `tests/test_sites_boq.py` … 新設

### 運用

- 依存追加なし（`openpyxl` / `pdfplumber` とも導入済み）
- **スキャン画像のPDFは読めない。** 文字が取れないため。画面にその旨を出す
- 取込は既定で「既存を置き換える」。外すと追記になり、同じファイルを
  2回読むと行が重複する

## 残課題

- 発注者ごとの内訳書様式差（列見出しの揺れ）は代表的な別名だけ吸収している。
  読めない様式が出たら `COLUMN_ALIASES` に足す
- 積算案件と現場の両方に内訳書がある場合の突合（同じ工事の見積と実行）は未対応
