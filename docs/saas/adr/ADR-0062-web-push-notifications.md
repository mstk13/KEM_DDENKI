# ADR-0062: スマホへのプッシュ通知（Web Push）を、新しい依存を足さずに送る

## ステータス

採用（2026-09-15）。ADR-0061（現場の安全書類と朝8時の知らせ）の第2段

## コンテキスト

- ADR-0061 で、朝8時にその日その現場に出る人へ KY 用紙の知らせをベル（アプリ内の通知）に出すようにした。アプリを開かないと気づかない
- ADR-0061 の回答で、通知の出し方は「アプリ内の通知＋スマホのプッシュ通知」
- 追加の回答（2026-09-15）:

| 項目 | 回答 |
|---|---|
| スマホに送る知らせ | **アプリ内の通知を全部**（朝の KY、資格の期限、原価、工期など） |
| 受け取りをオンにするボタン | **ホームと通知の画面の両方** |

- ADR-0061 では `pywebpush` を足す予定だった。pywebpush 2.x は `aiohttp`・`http-ece`・`py-vapid` を連れてくる

## 決定

### 1. 送り方（依存は足さない）

- Web Push（Push API）。Service Worker（`/sw.js`、ADR-0048）に `push`（通知を出す）と `notificationclick`（押したら画面を開く）を足す
- 中身の暗号化（**RFC 8291** の aes128gcm）と送り手の証明（**RFC 8292** の VAPID）は `apps/notifications/push.py` に、すでに入っている `cryptography` と `requests` で書く
  - 必要なのは ECDH・HKDF・AES-GCM・ECDSA の組み合わせだけで、どれも `cryptography` にある。本番のイメージに `aiohttp` などを足さずに済む
  - 正しさはテストで固定する: **RFC 8291 の例の値**（鍵・salt・平文）から同じ暗号文ができる、その暗号文を端末の鍵で解ける、VAPID の署名を公開鍵で確かめられる
- 鍵は **`WEBPUSH_VAPID_PRIVATE_KEY` の1つだけ**をサーバーの `.env` に置く。公開鍵は秘密鍵から計算する（2つを別々に置いて食い違うことが無い）
  - `python manage.py generate_vapid_keys` で作る。本番と開発で別の鍵。コミットしない
  - 送り手の連絡先 `WEBPUSH_VAPID_SUBJECT` は、未設定なら `mailto:{DEFAULT_FROM_EMAIL}`（Apple は mailto: か https: でないと受け付けない）
  - `docker-compose.yml` の **web**（画面に公開鍵を渡す・テスト通知）と **cron**（送り出し）の両方に渡す
- 鍵が無い・形が違うときは送らない。画面には「まだ使えません」と出し、ほかは今までどおり動く。形が違うときは送り出しのコマンドが失敗としてログに残す

### 2. 何を・いつ送るか

- **ベルに届く通知を全部**。どこで作られた通知でも拾えるよう、作る側（`notify`・`notify_multiple`・AI の直接作成）には手を入れず、`Notification.pushed_at` が空のものを cron が **1分ごと**に送る（`send_push_notifications`、`scripts/scheduler.sh`）
  - 画面の操作中にプッシュサービスとの通信を待たせない
  - 遅れは最大1分ほど。朝の知らせ（`send_safety_reminders`）の後ろに置き、同じ周のうちに送る。長いジョブ（`scrape_bids` など）の間は止まる
  - 鍵が無ければ python を起動しない。送ったときと失敗したときだけログに出す
- 送らないもの:
  - **既読**の知らせ
  - **6時間より古い**知らせ（cron が止まっていた後や、使い始めた日に古い知らせが一度に届かないように）
  - その端末で**オンにする前**の知らせ
- 1人に **4件以上**溜まっていたら「新しい通知がN件あります」の1通にまとめる（押すと通知の一覧）
- 先に `pushed_at`（その回だけの時刻）を付けてから送る。**二重には送らない**（届かなかった知らせを送り直すこともしない。ベルには残っている）
- 緊急（`level=error`）は `Urgency: high`。TTL は12時間（朝の知らせが翌日に届いても意味が無いため）
- 押すと `/notifications/<id>/open/` で**既読にして知らせの画面へ**移る。移り先はこのサイトの中だけ

### 3. 送り先の登録（`PushSubscription`）

| 項目 | 内容 |
|---|---|
| 1件の単位 | 端末（ブラウザ）1つ。`endpoint` は会社をまたいで一意 |
| 別の人が同じ端末でオンにした | 前の人の登録を消して付け替える（前の人あての通知が届かないように） |
| ログアウト | 端末側の購読をやめ、サーバーの登録も消す（`offline.js` のログアウト処理から呼ぶ） |
| 登録し直し | 受け取っている端末は、ログインした人が変わったとき・サーバーの鍵が変わったとき・1日1回 |
| 届かなくなった | 404・410（端末で通知をやめた・アプリを消した）はすぐ消す。ほかの失敗が5回続いたら消す |

- 端末から届いた URL へサーバーが POST するので、送り先は **Google（`fcm.googleapis.com`）・Apple（`push.apple.com`）・Mozilla（`push.services.mozilla.com`）・Microsoft（`notify.windows.com`）の https だけ**受け付ける（社内のアドレスへ送らされないように）。リダイレクトは追わない
- 端末の鍵（`p256dh`・`auth`）の形も確かめる（P-256 の点・16バイト）
- `TenantModel`・変更履歴・管理画面あり。届けた日時と失敗の回数は `update()` で書き、届けるたびに変更履歴を増やさない

### 4. 画面

- 通知の画面に「📱 スマホへの通知」の欄: 「この端末で通知を受け取る」「テスト通知を送る」「この端末では受け取らない」と、使えない理由（鍵が無い・端末が対応していない・ブロックされている・iPhone はホーム画面に追加が要る）
- ホームに、まだ受け取っていない人への案内（閉じられる。閉じても通知の画面からオンにできる）
- 通知の許可は**ボタンを押したときだけ**求める（iPhone はボタンの操作の中でないと断られる。画面を開いただけで聞くと断られやすく、一度断られると端末の設定からしか戻せない）

## 本番に出すときの手順

1. サーバーの本番・開発それぞれのスタックで `docker compose exec web python manage.py generate_vapid_keys`
2. 出てきた `WEBPUSH_VAPID_PRIVATE_KEY=...` の行を、それぞれの `.env` に足す
3. `docker compose up -d`（web と cron を作り直して鍵を渡す）
4. スマホでアプリを開き、通知の画面で「この端末で通知を受け取る」→「テスト通知を送る」

## 捨てた選択肢

- **`pywebpush` を足す**: 標準的だが `aiohttp` などを本番に足すことになる。必要な処理は `cryptography` で書け、RFC の例の値で確かめられる
- **通知を作ったその場で送る**（`notify` の中やスレッド）: 画面の応答が遅くなる。`notify` を通らない通知（AI）を取りこぼす。gunicorn の再起動で送りかけが消える
- **送り出し専用のコンテナを足す**: 1分ごとで足りる。コンテナが増えるとメモリと運用の手間が増える
- **中身を送らず、端末がサーバーへ取りに行く**: 暗号化は要らないが、ログインが切れていると中身を出せない
- **知らせの種類ごとにオン・オフ**: 回答が「全部」。必要になったら `PushSubscription` か利用者の設定に種類を足す

## 影響

- マイグレーション `notifications/0004_push_subscription`: `Notification.pushed_at`（null 可の列を足すだけ）と `PushSubscription` の追加
- iPhone・iPad は iOS 16.4 以降で、ホーム画面に追加したアプリでだけ受け取れる
- 通知の題名（現場名など）がプッシュサービスを通るが、端末の鍵で暗号化しているのでサービス側には読めない
