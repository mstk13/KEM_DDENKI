# ADR-0045: 機能別の利用者リスト（AppAccess）の移行データを、今の判定をそのまま通して作る

## ステータス

採用（2026-09-12）。ADR-0030「後続の段階」のうち **データ移行** にあたる。判定の切り替えは別の PR

## コンテキスト

ADR-0030 で、アクセス管理を機能別の利用者リスト（`AppAccess`）に一本化すると決め、モデルと判定関数を入れた（expand）。
次の段階の移行データについて、プロダクトオーナーが D2 を決めた（2026-09-12）。

> 切り替えのときは、今の実効権限をそのまま再現する（役員の原価閲覧・`/costs/access/` の登録・日報の承認者も今のまま）。

今「その機能に入れるか」を決めている判定は、次のように散らばっている。

| 段 | 判定 | 場所 |
|---|---|---|
| ミドルウェア | superuser・社員番号 Y 始まりは素通し | `AppPermissionMiddleware` |
| ミドルウェア | 役職による制限（人事評価は社長・役員・Developer） | `can_use_app`（ADR-0022） |
| ミドルウェア | `Worker.allowed_apps`（空なら無制限。IT 担当の作成時に `devkanri` だけが入る） | 同上 |
| ビュー | 原価: 社長ロール・役員/開発者ロール・`User.employee_no` の G 始まり・個別許可 | `has_module_permission("costs", "read")` |
| ビュー | 設定（権限管理）・変更ログ | `has_module_permission("settings", "admin")` |
| ビュー | 書類アラート: Y 始まり・superuser・事務員ロール | `workers.views.document_alert_dashboard` |
| 承認 | 日報: 社長（ロール・役職）・開発者ロール・役職 Developer | `can_approve_report`（ADR-0039） |

誰に原価の個別許可があるか、誰の `allowed_apps` に何が入っているかは本番のデータにしか無いので、
コードから一覧を手で書くことはできない。

## 決定

1. **今の判定関数をそのまま呼んで、作業員 × 機能ごとに「使えるか」「承認できるか」を出す**（`apps/permissions/legacy_access.py`）。
   規則を写し直すと、いつか元の判定と食い違うため
2. **ログインユーザーの無い作業員**は、判定関数に渡すユーザーが無い。作業員の項目（役職・社員番号・`allowed_apps`）だけで同じ規則を当て、
   ユーザーに付く権限（ロール・原価の個別許可・`User.employee_no`）は持たない扱いにする
3. 承認フラグは、日報は `can_approve_report` の結果。**原価には今「承認」が無いので立てない**
4. 対象は**在籍中の作業員**。機能の中の一部の画面だけを絞る判定（作業員の編集など）は機能の入口ではないので対象外にし、切り替え後もビューに残す
5. 管理コマンド `plan_app_access` を置く

   | 実行 | 内容 |
   |---|---|
   | `plan_app_access` | 機能ごとの人数と「使えない人／使える人」（少ないほう）、承認できる人、今の AppAccess との差分。**書き込まない** |
   | `plan_app_access --matrix` | 作業員 × 機能 の表を CSV で出す。書き込まない |
   | `plan_app_access --apply` | AppAccess を案と同じ状態にする（足りない行を作る・承認を合わせる・案に無い行を消す） |

6. 手順: 本番で `plan_app_access` と `--matrix` を実行 → **プロダクトオーナーが「誰に何が開くか」を確認** → 判定を切り替える PR のリリース直前に `--apply`。
   切り替えた後は流さない（画面で直した利用者リストを今の判定で上書きしてしまう）
7. **案と今の判定の一致をテストで固定する**。権限の分かれ目を1つずつ持つ作業員を作り、全機能の画面を実際に開いて、403 になるかどうかが案と一致することを確かめる

## 捨てた選択肢

- **今すぐデータマイグレーションで AppAccess を投入する**: プロダクトオーナーが一覧を確かめる前に本番へ入る。
  切り替えまでの間に作業員の追加・異動があると、投入した行が古くなる
- **規則を読み解いて一覧を手で作る**: 本番のデータ（個別許可・`allowed_apps`）が読めないうえ、判定の食い違いに気づけない
- **全員に全機能を開く**: D2（今の権限をそのまま再現）に反する

## 影響

- 追加: `apps/permissions/legacy_access.py`、`apps/permissions/management/commands/plan_app_access.py`、`tests/test_app_access_legacy_plan.py`
- 画面・判定・データへの影響なし（コマンドを `--apply` で流すまで AppAccess は変わらない。流しても判定はまだ AppAccess を見ていない）
- **切り替えの PR で決めること**
  - 原価の書き込み・管理（`has_module_permission("costs", "write"/"admin")`）は AppAccess の「使える／承認」の2値に収まらない。承認フラグで表すか、別の判定を残すか
  - 切り替え後に新しく登録・ログインを付けた作業員に、最初にどの機能を開けるか（今は `allowed_apps` が空なら全機能）
  - `--apply` をリリース手順で流すか、切り替えのマイグレーションで流すか
