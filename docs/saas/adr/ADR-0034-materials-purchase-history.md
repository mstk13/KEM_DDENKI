# ADR-0034: 材料ごとの過去の取引を発注明細から引く画面を足す

## ステータス

採用（2026-09-10）

## コンテキスト

仕入先（発注先）は `masters` の画面、材料と発注書は `materials` の画面にあり、
「この材料をいつ・どこから・いくらで買ったか」を横断して見る画面が無かった。
発注書一覧は発注書単位、材料仕入先（`MaterialSupplier`）は標準単価の登録だけで、
実際の取引の単価の推移は発注書を1枚ずつ開かないと分からない。

プロダクトオーナーの決定（2026-09-10）: サイドバーに「発注」を置き、その画面で
**材料ごとの過去の取引**を、材料・仕入先（加えて現場・期間）で検索できるようにする。

取引の記録は2か所にある。

| | `PurchaseOrderItem`（+ `PurchaseOrder`） | `ProcurementRecord` |
|---|---|---|
| できる時 | 発注書に明細を足した時 | 検収の時（`_create_procurement_records`） |
| 材料 | マスタ FK（空可）+ 自由入力の材料名 | マスタ FK 必須 |
| 持っている値 | 仕入先・現場・発注日・状態・数量・単位・単価 | 納品日・実リードタイム・納品数量 |
| 漏れるもの | 納品の情報 | 未検収の発注、自由入力の明細 |

## 決定

1. **発注明細を土台にする**。`materials.purchase_history.search_purchase_history(company, ...)` が
   発注明細を読み、材料ごとにまとめて返す。画面は `materials:purchase_history`（`/materials/history/`）
2. **検収済みの分は調達実績から納品日と実リードタイムを足す**。発注書 × 材料で突き合わせる。
   調達実績は1クエリで読み、Python で引き当てる（明細ごとに問い合わせない）
3. **下書きと取消は含めない**。下書きはまだ発注しておらず数量・単価が確定前、
   取消は取引が成立していない。どちらも混ぜると最安・最高単価が実在しない値でぶれる
4. **自由入力の明細（材料 FK なし）は、表記ゆれを潰した材料名でまとめる**。
   照合キーは見積取り込みと同じ `normalize_material_name`。マスタのある明細とは
   名前が同じでも混ぜない（マスタに引き当てるかは人が決めることなので）
5. 材料ごとの集計は 取引件数・単位ごとの合計数量・最新単価（最終発注日の単価）・
   最安/最高単価・仕入先数・最終発注日。金額は数量 × 単価を Decimal のまま出す
6. 1回に読む明細は発注日の新しい順に **500件まで**。超えたら画面で知らせ、絞り込みを促す。
   集計もこの範囲で行う
7. サイドバーへの追加はこの PR では行わない（`apps/core/navigation.py` は別途）

## 捨てた選択肢

- **調達実績（ProcurementRecord）だけを使う**: 検収前の発注と自由入力の明細が出ない。
  CSV 取り込みの発注書は明細がすべて自由入力なので、取引の大半が見えなくなる
- **見積（estimation.PurchaseRecord）を使う**: 卸の請求書を取り込んで見積単価を
  作るためのデータで、自社の発注書・現場と結びついていない
- **仕入先の画面（masters）に取引一覧を足す**: 求められているのは材料を起点に
  仕入先を比べる見方で、仕入先起点では同じ材料の単価を横に並べられない
- **集計を DB の集約（GROUP BY）で出す**: 自由入力の名前の表記ゆれは DB 上では
  潰せないので、まとめる単位が Python 側とずれる
