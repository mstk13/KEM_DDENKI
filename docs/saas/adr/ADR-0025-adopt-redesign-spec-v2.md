# ADR-0025: システム再設計仕様書 v2.0 を採用し、項目ごとの小さな PR で進める

## ステータス

採用（2026-09-10）

## コンテキスト

機能追加を優先してきた結果、サイドバーは約45リンク、権限の仕組みは3系統
（ADR-0022 の表を参照）、日報は reports と attendance の2系統になり、
画面の使いにくさが目立ってきた。これを受けて 2026-09-06 に
「フロントエンド再設計仕様書 v1.1」と、全機能の棚卸しに基づく
「システム再設計仕様書 v2.0」を作成した（`docs/design/` に同梱）。

v2.0 は数か月単位の計画で、Phase 0〜4 に約20項目を含む。
一方でこのリポジトリは developer / main とも2分おきに自動デプロイされるため、
1回の変更が大きいほど「壊れたものが2分で届く」リスクも大きくなる。

また v2.0 は、仕様書作成と並行して進んでいた次の判断と食い違う。

| v2.0 | 既存の判断 | 食い違い |
|---|---|---|
| §4 アクセスは「機能別利用者リスト」1系統（AppAccess） | ADR-0022（2026-09-08）役職（Position）で制限するアプリを列挙 | 判定の軸が「個人のリスト」か「役職」か |
| §8 作業日報と勤怠日報を新しい統合モデルに expand/contract で移す | ADR-0024（作業中）勤怠日報の入力画面を廃止し、reports の DailyReport に一本化 | 新モデルを作るか、既存 DailyReport を統合先にするか |

## 決定

1. **v2.0 を再設計の正とする。** v1.1 の決定（全画面レスポンシブ・htmx + Alpine.js・
   評価の workers 一本化・現場モード）は v2.0 に継承されているものとして扱う。
2. **1項目 = 1 PR。** v2.0 §11 の各項目をさらに expand / 切り替え / contract に分け、
   差分はおおむね400行以内に収める。モデル追加を含む PR は CLAUDE.md
   絶対ルール4（simple-history・admin・越境テスト・マイグレーション）を同じ PR に含める。
3. **要求定義を先に置く。** `docs/design/redesign_v2_requirements.md` に
   ユーザーストーリー・受け入れ基準・PR 分割・未決事項をまとめ、
   各 PR の説明文はそこへの参照から始める。
4. **既存 ADR との食い違いは、実装で黙って上書きしない。**
   要求定義の「未決事項」に並べ、決まったものから個別の ADR で
   既存 ADR を「置き換え」扱いにする。決まるまでは既存 ADR の挙動を保つ。
5. **廃止は導線から。** v2.0 §12 のとおりデータは削除しない。画面・メニューの撤去を
   先に出し、テーブルの削除は利用がないことを確認した後の別リリースで行う。

## 捨てた選択肢

- **Phase 0 を1本の PR にまとめる**: 権限・評価・日報・畳み込みが1つの差分に混ざり、
  レビューも切り戻しもできなくなる。自動デプロイ環境では特に危険。
- **v2.0 に合わせて ADR-0022 / ADR-0024 を即座に巻き戻す**: ADR-0022 は
  人事評価の閲覧制限という実運用中の要望を満たしている。置き換え先（AppAccess）が
  本番で動く前に外すと、その間だけ制限が消える。

## 影響

- `docs/design/` に v2.0・v1.1・図解資料・要求定義を追加
- `docs/learning/` に学習ガイドを追加（コードへの影響なし）
- 以後の再設計 PR は本 ADR と要求定義を参照する
