# ADR-0031: 入札案件に現場への参照を持たせ、案件を現場中心に束ねる（expand）

## ステータス

採用（2026-09-10）

## コンテキスト

フロントエンド再設計仕様書 v2.0 §1 の「案件の背骨」（入札・積算・現場を1つの案件として見せる）を
どう持つかは、判断事項 D6 として保留していた。2026-09-10 にプロダクトオーナーが決めた。

コードを確かめた結果:

| 操作 | 処理（`apps/bids/services.py`） | 作られる現場 |
|---|---|---|
| 積算開始（`bids:start_estimation`） | `start_estimation` | `EST-<入札案件ID>`（見積中・受注金額＝予算額） |
| 落札（`bids:mark_won`） | `mark_as_won` → `create_site_from_won_bid` | `BID-<入札案件ID>`（受注済・受注金額＝自社入札額 or 予算額） |

- どちらも入札案件側に参照を保存せず、`Site` にも入札への参照がない
- そのため**積算開始のあとに落札すると、同じ入札から現場が2つできる**（不具合）
- 積算開始を2回押すと、現場コードの一意制約（会社×コード）に当たって 500 になる
- 積算案件（`estimation.EstimationProject`）は既に `site` と `bid_project` の両方を持つ
- 原価・日報・工程・発注はすべて `Site` にぶら下がっている

## 決定

1. **案件は現場（`Site`）を中心に束ねる（D6 案 (a)）**。新しい「案件」モデルは作らない
2. `bids.BidProject.site`（`Site` への FK、`null=True`・`SET_NULL`、`related_name="bid_projects"`）を追加する。
   simple-history の履歴モデルにも列が増える
3. 積算開始・落札は**同じ現場を使う**。どちらも `transaction.atomic()` の中で入札案件の行をロックし、何度呼んでも現場は1つ
   - 積算開始: 現場があればそのまま使う。無ければ今までどおり `EST-` の現場を作って参照を保存する
   - 落札: 現場があればそれに反映する。無ければ今までどおり `BID-` の現場を作って参照を保存する
4. 登録済みの現場に落札を反映するときの規則
   - 状態は**見積中のときだけ**受注済に進める。施工中・完工などを戻さない
   - 受注金額・顧客は**空のときだけ**埋める。画面で入れた値と現場コードは変えない
5. 落札の通知は、入札案件が落札に変わったときだけ出す。登録済みの現場を使った場合は
   「登録済みの現場「…」に落札を反映しました。」と書く（「自動作成されました」とは書かない）
6. サービス関数 `start_estimation` / `mark_as_won` は `(Site, created)` を返す。画面のメッセージも作成と再利用で分ける

### 既存データの紐付け（`bids/0022_backfill_bidproject_site`）

現場が空の入札案件について、同じ会社の現場を現場コードで探す。

| `BID-<ID>` | `EST-<ID>` | 紐付ける現場 |
|---|---|---|
| あり | なし | `BID-` |
| なし | あり | `EST-` |
| あり | あり | `BID-`（落札で作った受注済の現場）。`EST-` は消さず、中身にも触らない |
| なし | なし | 紐付けない |

- 別の会社の現場は、コードが一致しても紐付けない
- 逆方向は何もしない（参照列は 0021 を戻せば消え、現場そのものは変えていない）

### 後続の段階

| 段階 | 内容 |
|---|---|
| 案件一覧 | 現場を起点に、入札・積算をまとめて一覧する |
| 案件詳細 | 概要 / 入札 / 積算 / 工程 / 日報 / 材料 / 原価 のタブ |
| 重複した現場の整理 | 紐付けで残った `EST-` の現場を画面で確認して片付ける（自動では消さない） |

入札から積算案件（`EstimationProject`）を作る処理は、この ADR の範囲外とする。

## 捨てた選択肢

- **「案件」モデルを新設し、入札・積算・現場がそこを参照する（D6 案 (b)）**: 1つの受注に現場が
  複数ある工事を表現できるが、新モデルと全データの紐付け移行が要る。原価・日報・工程・発注は既に
  現場にぶら下がっており、現場を中心にすれば案件詳細の大半が作れる。
  **1つの受注で現場を複数に分ける運用が出てきたら、(b) を再検討する**
- **`Site` 側に入札への FK を持たせる**: 1つの現場に複数の入札（再入札・分割発注）が付く余地を消す。
  入札から「この入札の現場」を辿れれば足りる
- **紐付けで重複した `EST-` の現場を消す・`BID-` にまとめる**: 見積中に日報や原価が付いている
  可能性があり、自動で消すとデータを失う

## 影響

- 変更: `apps/bids/models.py`（`BidProject.site`）、`apps/bids/services.py`、`apps/bids/views.py`（メッセージ）
- 追加: マイグレーション `bids/0021_bidproject_site`（スキーマ）、`bids/0022_backfill_bidproject_site`（データ）
- 追加: `tests/test_bids_site_link.py`（二重作成・冪等性・状態を戻さない・越境・紐付け規則）
- 入札案件の編集フォームには `site` を出さない（`fields` を列挙しているため）
