# 建設業向けマルチテナントSaaS — TMs向けプレゼン資料

作成日: 2026-08-01

---

## 1. 問題提起 — 建設業の中小企業が抱える痛み

### 現状（ケンモチ電機での実体験）

- 日報は紙、原価はExcel、材料は発注台帳 → **全部バラバラ**
- 事務員が月30時間以上かけて転記・集計している（月6〜8万円の無駄）
- 現場ごとの粗利が工事完了まで見えない → **赤字に気づくのが手遅れ**
- 予算と実績の粒度が揃わないので比較すらできない

### これは業界全体の問題

- 建設業の中小企業（年商1〜10億円規模）は約5万社
- ほぼ全社が同じ課題を抱えている
- 既存の業務ソフトは大企業向けで高額・複雑、中小には合わない

---

## 2. 自社でまず解決した — KEM_DDENKI

### 実際に作って運用中のシステム

| アプリ | 機能 |
|---|---|
| 作業日報 | 日報入力・集計 |
| 人事評価 | アンケート・5段階評価・PDF出力 |
| 材料管理 | 見積vs発注の消化率追跡 |
| 工期管理 | ガントチャート・工程進捗 |
| 人材管理 | 社員情報・資格管理 |
| 入札案件管理 | 案件収集・進捗管理 |

### 得られた成果

- 自社の業務課題を**実際に解決**した実績がある
- 現場で何が使われて何が使われないかの**肌感覚**がある
- 技術的な検証（Streamlit + PostgreSQL + Docker）が済んでいる

## 3. これをSaaS化する — なぜ作り直すのか

### KEM_DDENKIがそのまま売れない理由

| 問題 | 具体的に何が起きるか |
|---|---|
| データが分離できない | 1社専用のDB。他社に売るなら会社ごとにシステムをコピーする必要がある |
| Streamlitの限界 | ログイン・権限管理・スマホ対応が弱い。職人がスマホで使えない |
| 固有名詞がハードコード | 「電工」「事務」「シニア」等がコードに埋まっている |

### KEM_DDENKIの位置づけ

> **KEM_DDENKIは「課題の発見と検証」。SaaS版は「売り物」。**

- 課題が本物であることは自社で証明済み
- 次は「100社に売れる製品」として再設計する

## 4. 何を作るのか — 製品の核心

### 一言で言うと

> **日報を入力するだけで、現場ごとの粗利がリアルタイムに見えるシステム**

### 原価の自動集計の仕組み（CostTransaction）

```
職人が日報を入力
  「7/31、○○現場、電気幹線工事、8時間」
       ↓ 上長が承認
       ↓
自動で原価データ（CostTransaction）が生成される
  「○○現場 / 電気幹線 / 労務費 / 24,000円」
   （8時間 × その職人の時給3,000円）
       ↓
現場の画面を開くと
  受注額 500万 − 原価合計 320万 = 粗利 180万（36%）
  がリアルタイムで見える
```

### 建設業の原価は4種類

| 原価区分 | 何か | どこから自動生成されるか |
|---|---|---|
| 労務費 | 人件費 | 日報（承認時に自動生成） |
| 材料費 | 資材の購入費 | 発注の検収時に自動生成 |
| 外注費 | 下請けへの支払い | 手入力 |
| 経費 | その他（交通費等） | 手入力 |

全原価が**同じテーブル（CostTransaction）に同じ粒度**で入るから、足し算するだけで粗利が出る。

### なぜ今までできなかったか

- 労務費は日報（紙）、材料費は発注台帳（Excel）、外注費は請求書（紙）
- **バラバラのフォーマット、バラバラの粒度**
- 事務員が月末に手作業で突き合わせていた → これが月30時間の正体

### 重要な設計判断: CostTransactionは書き換えない（追記のみ）

間違いに気づいた場合:
1. 元の金額を打ち消す逆仕訳（-24,000円）を追加
2. 正しい金額の新しい行（+27,000円）を追加

→ 「いつ・誰が・何を修正したか」が全部追跡できる（監査可能性）

## 5. どう作るのか — 技術選定

### Streamlit → Django に変える理由

| | Streamlit（今のKEM_DDENKI） | Django（SaaS版） |
|---|---|---|
| 用途 | データ表示・社内ツール向き | Webアプリの本格構築 |
| ログイン・権限 | 自前で頑張る | 標準装備 |
| スマホ対応 | 弱い | 自由にUI設計できる |
| マルチテナント | 仕組みがない | ミドルウェアで自然に実装 |
| DB変更管理 | SQLを手で修正 | マイグレーションで安全に管理 |
| 長期保守 | LTSなし | LTSあり（3年ごとに乗り換え） |

> Djangoは「Webアプリに必要なもの（認証・権限・DB管理・URL振り分け・管理画面）が全部入っている部品セット」

### Django が具体的に何をしてくれるのか（KEM_DDENKIとの対比）

KEM_DDENKIで自作していた部分の大半を Django が肩代わりする:

| やっていたこと | KEM_DDENKI（自作） | Django |
|---|---|---|
| ログイン | `auth.py` で社員IDを自前判定 | `django.contrib.auth` が標準装備 |
| DBアクセス | `psycopg2` で直接SQL | `Worker.objects.filter(company=tenant)` と書くだけ |
| DB変更 | `schema.sql` を手で編集 | `python manage.py makemigrations` で自動生成 |
| 画面 | `st.selectbox`, `st.dataframe` | HTML/CSSで自由に設計 |
| URL | nginx + baseUrlPath | `urls.py` で定義 |
| 管理画面 | `admin_app.py` を自作 | `django.contrib.admin` が自動生成 |

Webアプリの仕組み:

```
ブラウザでアクセス
  → URL振り分け（どの画面を出すか）     ← Django 標準
  → 権限チェック（この人は見ていいか）   ← Django 標準
  → DBからデータ取得                    ← Django ORM
  → HTMLを組み立てて返す                ← Django テンプレート
ブラウザに画面が表示される
```

### 技術スタック

| 項目 | 採用技術 | 理由 |
|---|---|---|
| 言語 | Python 3.12 | チーム全員が使える |
| フレームワーク | Django 5.2 LTS | 認証・権限・admin標準装備、LTSで長期保守 |
| DB | PostgreSQL 16 | 信頼性、マネージド移行の容易さ |
| テスト | pytest | 越境テストをCIで常時実行 |
| CI | GitHub Actions | PR必須、main直接コミット禁止 |

### マルチテナント — 行レベル分離

> **マンションの例え:**
> - 一戸建て（今）= 1社ごとにシステムを丸ごとコピー → 100社なら100個管理。無理
> - マンション（SaaS）= 建物（アプリ）は1つ、部屋（データ）は完全に分離

| 方式 | 例え | 判断 |
|---|---|---|
| DB分離 | マンションごと別の土地に建てる | 大口顧客のみ将来対応 |
| スキーマ分離 | フロアごとに設備が別 | 3人では運用が破綻 |
| **行レベル分離（採用）** | 同じテーブルだが全行に「A社のもの」の印 | 3人で運用可能 |

全テーブルに `company_id` を持たせ、クエリに必ず会社のフィルタをかける。テナント越境テスト（A社ユーザーがB社データに触れないことの検証）をCIで常時実行する。

### 実際のSaaSでの採用実績

| サービス | 規模 | 方式 |
|---|---|---|
| Salesforce | 数十万社 | 行レベル分離 |
| HubSpot | 数万社 | 行レベル分離 |
| ANDPAD等（国内建設SaaS） | 数千〜数万社 | 行レベル分離 |
| Shopify（現在） | 数百万店舗 | DB分離（巨大チーム・莫大な自動化投資） |

**結論: 3人チーム × 0→100社の規模では行レベル分離一択。** 大口顧客が「専用環境がほしい」と言ったら、その1社だけDB分離に昇格させる（AWSの推奨パターン）。仕様書§3.4の「company_idが全テーブルにあるから特定テナントのデータ抽出がdump一発で可能」は、この昇格を想定した設計。

## 6. データ入力の方針

### 原則: 出口（データモデル）から設計する

> 入力手段がスマホでもExcelでも画像でも、最終的に同じCostTransactionに同じ粒度で入ればいい。だから出口を先に固めて、入力手段は後から増やせる。

### 入力手段の優先順位

| 優先度 | 入力手段 | 対象 | 時期 |
|---|---|---|---|
| 最優先 | スマホ直接入力 | 職人（日報） | M2 |
| 高 | Web画面入力 | 事務・管理者 | M2〜M4 |
| 中 | Excel取り込み | 既存データ移行・一括登録 | M3〜M4 |
| 中 | 画像/PDF→AI読み取り | 紙の請求書・納品書 | M4以降 |
| 低 | 会計ソフト連携 | 将来 | M6以降 |

## 8. 人材データの設計 — 職種・役職のマスタ管理

### KEM_DDENKIでの問題

今は `config.py` に職種・役職をハードコードしている:

```python
ROLES = ["役員", "電工", "事務", "developer"]
POSITIONS = ["代表取締役", "職長", "シニア", "ジュニア", ...]
```

これは1社専用だから成立している。SaaSでは会社ごとに職種も役職も違う。

### SaaS版の設計（マスタテーブル方式）

```
JobTitle（職種）  ← テナントごとに自由に定義
  ├── company_id
  ├── name          → 「電工」「配管工」「CADオペ」等
  └── is_active

Position（役職）  ← テナントごとに自由に定義
  ├── company_id
  ├── name          → 「職長」「主任」「シニア」等
  ├── rank          → 序列（昇順。給与・権限・評価の判定に使える）
  └── is_active

Worker
  ├── job_title FK  → JobTitle
  ├── position FK   → Position
  ├── hourly_cost   → 労務費CostTransactionの算出単価
  └── ...
```

### なぜマスタテーブルか（自由入力ではダメな理由）

- 職種ごとに時間単価を変えたい → `JobTitle` と紐づける
- 職種ごとの労務費集計 → `JobTitle` でGROUP BY
- 役職で評価項目を分ける → KEM_DDENKIでやったシニア/ジュニアの出し分けと同じ
- 自由入力だと「電工」と「でんこう」が別物になり集計が壊れる

## 11. SaaSの基本コンセプトと思考法

### 知っておくべきSaaS用語

| 用語 | 意味 | なぜ重要か |
|---|---|---|
| MRR | 月次経常収益 | SaaSの健康状態の最重要指標 |
| 解約率（Churn） | 月に何%の顧客が辞めるか | 1%と2%で到達可能な顧客数が倍違う |
| LTV | 1社が生涯で払う総額 | 獲得コストより大きくないと赤字 |
| ARR | 年間経常収益（MRR×12） | 会社の売却価値の基準 |
| テナント | SaaSを使う1社のこと | 技術でもビジネスでも使う共通言語 |
| オンボーディング | 導入支援 | 雑だと即解約。収入源でもある |

### 開発時の3原則

**1. 「自分たちが使うもの」ではなく「100社が使うもの」を作っている**

コードに固有名詞（「ケンモチ電機」「電工」「シニア」）を書かない。業種や会社の違いはマスタデータで吸収する。

**2. 出口（データモデル）から設計する。入口（UI）は後で変えられる**

画面のボタン配置は明日変えられる。でもDBのテーブル構造を変えるのは100社のデータ移行を伴う。CostTransactionの粒度を先に決めて、絶対に崩さない。

**3. 「1社目の要望」に飛びつかない**

最初の顧客の「うちはこうしたい」をハードコードすると2社目で破綻する。要望を設定値やマスタデータで吸収できるかをまず考える。これがマルチテナントSaaSの設計力。
