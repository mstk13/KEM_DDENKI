# 第1回: 重複が生むズレ

対象コード: `saas/templates/`
実施日: 2026-09-19
関連 ADR: [ADR-0108](../../saas/adr/ADR-0108-form-field-partial-in-core.md)

---

## 1. 一言で言うと何か

**リファクタリングとは「外から見た振る舞いを変えずに、内部の構造だけを変えること」。**

「変えずに」が定義の中心である。見た目が変わったら、それはリファクタリングではなく
改善または仕様変更であり、別の名前・別のコミットで扱う。

## 2. なぜ存在するか

コードは**書く時間より、読んで直す時間のほうが圧倒的に長い**。KEM_DDENKI は 9.7 万行あり、
これから何年も直し続ける。だから「今日書きやすいか」ではなく「半年後に直しやすいか」で
構造を選ぶ必要がある。

ただし「読みやすくなる」は感想であって理由にならない。**リファクタリングの本当の目的は、
バグの生まれる余地を構造的に消すこと**である。今回それが実際に起きていた。

### 実際に起きていたこと

`saas/templates/` には、フォームの1項目を描くこの形が **401 箇所**手書きされている。

```html
<div class="form-group">
  <label for="id_customer">顧客マスタ</label>
  {{ form.customer_name }}
  {{ form.customer_name.errors }}
</div>
```

この 401 箇所を機械で調べたところ、**3 箇所でラベルと入力欄の紐付けが壊れていた。**

| ファイル | 書かれていた `for` | 入力欄の実際の id |
|---|---|---|
| `estimation/orderer_form.html` | `id_customer` | `id_customer_name` |
| `estimation/item_form.html` | `id_work_type` | `id_work_type_name` |
| `estimation/item_form.html` | `id_material` | `id_material_name` |

`for` が合っていないと、**ラベルを押しても入力欄にフォーカスが移らない。**
現場担当者がスマホで使うアプリで、小さな入力欄ほどラベル押しに頼る。

さらに同じ項目で、文言そのものもズレていた。

- テンプレート: `顧客マスタ`
- `OrdererForm`: `label="顧客"`

画面には `顧客マスタ` と出るが、**入力エラーの文面だけ「顧客」**になっていた。

### ここが今回いちばん重要な観察

**この3箇所は、テスト 2254 件を全部通る。**

テストは「ラベルと入力欄が結びついているか」を見ていない。つまり
**テストが緑なのは「壊れていない」という意味ではなく、「テストが見ている範囲では
壊れていない」という意味しかない。**

> 重複とは「同じことを2箇所に書くこと」ではない。
> **「片方だけ直る／片方だけ間違える余地を作ること」**である。
> 401 回書き写せば、ズレは確率の問題として必ず入る。人の注意力では防げない。

## 3. どう動くか（作法）

### 安全網 → 小さな一歩 → 突き合わせ → コミット

リファクタリングは「直す技術」ではなく**「壊れていないことを確かめ続ける技術」**である。
順番はこうなる。

```
① 安全網を確認する    直す前にテストを流し、何件緑なのかを記録する
                     （今回: 2254 件 green / 10分26秒）
② 一歩だけ動かす      1ファイル、できれば1つの操作だけ
③ 突き合わせる        直す前と後の出力を機械で比べる
④ コミットする        ここで区切る。次の一歩と混ぜない
```

②で「ついでにこれも直そう」と手を広げた瞬間、③の突き合わせが効かなくなる。
**差分が1行なら、壊れたときに原因は1つしかない。**

### 2つの帽子（Kent Beck）

作業には2種類しかなく、**同時に2つの帽子をかぶらない**。

| 帽子 | やること | 外から見た振る舞い |
|---|---|---|
| リファクタリングの帽子 | 構造を変える | **変えない** |
| 機能追加の帽子 | 振る舞いを変える | 変える |

今回この規律を、コミットの切り方でそのまま表現した。

- **コミット1**: パーシャルを `workers/` → `core/` へ移すだけ。中身は1文字も触らない
  → 描画結果は完全に同一
- **コミット2**: 1画面をそのパーシャルに寄せる
  → 描画結果が1行だけ変わる（壊れていたラベルが直る）

混ぜて1コミットにしていたら、「移動で壊れたのか、適用で壊れたのか」が切り分けられない。

### ③の突き合わせを、実際にどうやったか

「たぶん同じはず」で済ませない。**旧版と新版を同じ入力で描画して、HTML を diff した。**

```
描画HTMLの差分（空白・改行は無視）:
--- 旧
+++ 新
@@ -42,3 +42,3 @@
 <div class="form-group">
-<label for="id_customer">顧客マスタ</label>
+<label for="id_customer_name">顧客マスタ</label>
 <input type="text" name="customer_name" list="customer-name-options" ...>
```

**差分はこの1行だけ。** 45 行のテンプレートを書き換えて、変わったのは壊れていた箇所のみ。
これが取れていれば、「振る舞いを変えていない」は感想ではなく事実になる。

> この「旧と新を同じ入力に通して出力を比べる」やり方は、リファクタリング全般で使える。
> 関数なら戻り値、PDF ならバイト列、API なら JSON。**外から見えるものを固定して比べる。**

### そして、突き合わせが「探しても見つからなかったズレ」を出した

2画面目（`estimation/item_form.html`）で同じことをしたところ、**事前の調査では
見つけられなかったズレが2件**出てきた。

| 項目 | モデルの `verbose_name` | 画面に出ていた文言 |
|---|---|---|
| `standard_price` | 参考単価 | 参考単価**（円）** |
| `spec` | 仕様 | 仕様**（JSON）** |

`for` 属性のズレは機械で探せた（`id_` と項目名を突き合わせればよい）。
**文言のズレは探せない。** 「参考単価」と「参考単価（円）」のどちらが正しいかは、
コードを見ても決まらないからである。

つまり**事前の調査で見つけられる問題は、問題全体の一部でしかない。**
突き合わせは「確認作業」ではなく、**それ自体が発見の手段**である。

これが③を省略できない理由。「たぶん同じはず」で進めていたら、単位の「（円）」が
画面から静かに消えていた。

## 4. 設計判断とトレードオフ

### 判断: 401 箇所を一度に置換しない

`sed` で 401 箇所を一括置換することは技術的には可能で、10 分で終わる。**やらない。**

| 案 | 得るもの | 失うもの |
|---|---|---|
| (a) ズレている3箇所だけ直す | 差分が最小。今日は安全 | 次に書き写した人が同じズレを作る。**バグは消えるが、バグの生まれる余地が残る** |
| (b) 401 箇所を一括置換 | 一度で終わる | 突き合わせができない。95 ファイルが同時に変わり、どこかが崩れても原因が特定できない |
| (c) ライブラリ（crispy-forms 等）を入れる | 記述量が最も減る | 依存が増える（絶対ルール1）。見た目が全画面で一度に変わる |
| **(d) 採用: 1画面ずつ移す** | 各段階で「出力が変わっていない」ことを証明できる | 時間がかかる。途中は新旧が混在する |

**(d) の「途中は混在する」は欠点に見えるが、実は許容してよい。** 混在していても動く。
一方 (b) の「全部同時に壊れうる」は許容できない。**リファクタリングで最も避けるべきは、
壊れたときに原因を特定できない状態を作ること。**

### 判断: 置き場所をアプリ名から外す

共通パーシャルは**既に存在していた**（`templates/workers/_form_field.html`）。
それでも estimation・sites・bids はどれも手書きのままだった。なぜか。

**`workers/` の中にあるものは「workers のもの」に見えるから。**

置き場所は、そのコードが**何であるか**を伝えてしまう。共通部品をアプリ名のフォルダに
置くと、共通部品として誰にも見つけられない。`core/_field.html` へ移した理由はこれ一点で、
行数は1行も減っていない。

> **一般原理**: 名前と置き場所は、機能ではなく**読む人への合図**である。
> 同じ構造の問題は命名全般にある（変数名・関数名・モジュール名）。

### 判断: 収まらないものは、寄せずに残す

`customer_name` だけは共通パーシャルに寄せず、手書きのまま残した。
候補リスト（datalist）を後ろに足す必要があるためである。

パーシャルに引数を足していけば飲み込ませられる。**やらない。**
共通部品は、引数が増えるほど「何をするものか」が読めなくなり、結局誰も使わなくなる。

> **DRY は絶対の正義ではない。** 重複を消す価値と、共通部品が複雑になる代償を天秤にかける。
> 3 回目に同じものを書いたときに初めて共通化する（Rule of Three）くらいが実務的。

## 5. 限界と未解決問題

### (a) 今回の直し方では捕まらないもの

フォーム部品を `{{ form.x }}` ではなく `<input name="x">` と**手書きしている箇所が 96 箇所**
ある。これはラベルだけでなく widget の属性（`maxlength`・`required`・`class`）もフォーム定義
から切れており、フォーム定義を直しても画面に反映されない。第2回以降で扱う。

### (b) テストが見ていない領域が残っている

今回のズレはテストでは捕まらなかった。**同じ性質のズレが他にどれだけあるか分かっていない。**
「テストが緑」を安全の根拠にし続けると、いつか同じことが起きる。
→ 第3回の主題にする。

### (c) 直してはいけない食い違いがある

`apps/permissions/services.py` に `is_president` / `is_it_staff` / `has_role` があるのに、
`apps/workers/views.py` が `_is_president` / `_is_it_staff` / `_has_role` を別実装している。
しかも `_is_president` はロール判定を見ておらず、**判定結果が食い違う**。

これは重複だが、**寄せてはいけない。** 寄せた瞬間に「誰が何を開けるか」が変わるからである。
振る舞いが変わるなら、それはリファクタリングではなく仕様判断であり、
プロダクトオーナーが決めること。

> **見分け方**: その重複を消したとき、**利用者から見て何かが変わるか**を先に問う。
> 変わらないなら消してよい。変わるなら、それは設計判断として別に扱う。

## 6. 他の問題との接続

同じ構造（**一つの知識が複数箇所に書き写され、片方だけズレる**）の問題は他にもある。

| 場所 | 一つであるべき知識 | 実際に書き写されている先 |
|---|---|---|
| フォームのラベル | `models.py` の `verbose_name` | テンプレート 401 箇所 ← 今回 |
| 権限の判定規則 | `permissions/services.py` | `workers/views.py` ほか |
| 役職名 `"社長"` | Position マスタ | Python 9 ファイルに文字列直書き |
| 色 | CSS のトークン | インライン `style=` 1,835 箇所 |

**同じ形をしている**ことに気づけると、次に何を直すかを自分で決められるようになる。
これが「直し方を覚える」より価値がある。

なお、この構造は KEM_DENKI_HP の CLAUDE.md §6 が
「生の16進数カラーをコンポーネントに直書きしない」と書いているのと**まったく同じ問題**である。
別プロジェクトで既に言語化されていた規律が、こちらでは効いていなかった。

### 判断: 表示の文言はモデルではなくフォームに置いた

「参考単価（円）」をモデルの `verbose_name` に書くこともできた。**やらなかった。**

- モデルの `verbose_name` を変えるとマイグレーションが発生する（絶対ルール7）
- 「（円）」「（JSON）」は**その画面で入力する人への案内**であって、データの意味ではない

`Meta.labels` に置けば、マイグレーションは出ず、モデルは業務的な名前のままで済む。

> **一般原理**: 同じ「名前」でも、**データの名前**と**画面の案内**は別の関心事である。
> 一つに寄せるとき、どの層に置くかを間違えると、今度は別の重複が生まれる。
> 寄せ先は「その知識が誰のためのものか」で決める。
