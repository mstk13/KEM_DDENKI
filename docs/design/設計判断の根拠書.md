## 1. 要件定義の判断根拠

### 1.1 なぜ8モジュールに分けたのか？

**結論**: 電気工事業の業務は「現場を中心に人・モノ・カネ・時間が回る」構造だから。

```
         入札で仕事を取る
              ↓
         現場が立ち上がる
        ↙   ↓   ↓   ↘
     人を配置  材料発注  工程計画  予算設定
        ↘   ↓   ↓   ↙
         日報で日々記録
              ↓
        原価集計・勤怠集計
              ↓
         現場完了→次の入札へ
```

この業務の流れを「切り離しても単体で動く単位」に分割した結果が8モジュール。

**TMへの説明ポイント**:
- 「全部1つの画面に詰め込む」と複雑すぎて誰も使わない
- 「バラバラのアプリを8個作る」とデータが分断されて集計できない
- → 「1つのアプリの中で8つの部屋に分ける」が最適解
- 各モジュールは独立しているが、データは共通のDBで繋がっている

### 1.2 なぜ日報が中心なのか？

**結論**: 日報は「現場で実際に何が起きたか」の唯一の記録であり、他の全モジュールの元データになるから。

| 日報から自動で流れるデータ | 行き先 |
|--------------------------|--------|
| 作業時間 × 作業員 | → 原価管理（労務費の自動計算） |
| 出勤日数・残業時間 | → 人材管理（勤怠集計） |
| 使用材料 | → 材料管理（消費量の記録） |
| 作業進捗 | → 工期管理（遅延の検知） |

**もし日報がなかったら**: 経理が手作業で勤怠を集計し、現場監督が口頭で進捗報告し、材料の使用量は月末に棚卸しで初めてわかる → 全部遅い、全部ミスが起きる。

### 1.3 なぜ承認フローを「任意」にしたのか？

**結論**: ヒアリングで「記録は残すが承認は必須ではない」という回答だったため。

**背景の推測と説明**:
- 小〜中規模の電気工事会社では、社長や職長が毎日全員の日報を承認するのは現実的でない
- 重要なのは「記録が残ること」であり、承認はオプション
- ただし将来「承認を必須にしたい」と言われた場合にも対応できるよう、承認フラグ・承認者・承認日時のカラムはDB上に用意してある
- **設計原則: 「使わなくてもいいが、使えるようにはしておく」**

### 1.4 なぜKY未記入アラートを入れたのか？

**結論**: 安全管理は法的義務であり、記入漏れは会社のリスクに直結するから。

**TMへの説明ポイント**:
- 労働安全衛生法で、危険有害業務の前にKY活動（危険予知活動）を行う義務がある
- 記入漏れ = 「やっていない」と見なされるリスク
- 事故発生時に「KYを実施した証拠」がないと会社の責任が重くなる
- → 未記入者にアラートを出して「やらせる」のではなく「記録を残させる」

### 1.5 なぜAI見積もりは「ローカルモデル」なのか？

**結論**: ヒアリングで「APIが高くなった時のリスクを回避したい」という明確な要望があったから。

**比較表**:
| 項目 | クラウドAPI (Claude/GPT) | ローカルOSSモデル |
|------|------------------------|-----------------|
| 精度 | 高い | やや劣るが実用十分 |
| 月額コスト | 使用量に比例（数千〜数万円） | 電気代のみ |
| データ外部送信 | あり（入札金額が外部に出る） | なし（全て社内） |
| 急な値上げリスク | あり | なし |
| 必要ハードウェア | 不要 | GPU推奨（なくても動く） |

**TMへの説明ポイント**:
- 入札の見積金額は会社の機密情報。外部APIに送るのはリスク
- 月数百件の見積もりを処理すると、APIコストが無視できなくなる
- OSSモデル（Llama等）は無料で商用利用可能
- 精度はクラウドに劣るが、「過去の類似案件を参考に概算を出す」用途なら十分

### 1.6 なぜスマホとPCを同等にしたのか？

**結論**: 現場作業員はスマホで入力し、事務所スタッフはPCで入力するため。

**TMへの説明ポイント**:
- 現場にPCを持ち込むのは非現実的 → スマホ必須
- 事務所で大量のデータを見るにはPCの大画面が必要 → PC必須
- 「スマホ専用アプリ」だと事務作業が辛い、「PC専用」だと現場で使えない
- → PWA（Progressive Web App）で1つのアプリを両方で使えるようにする

### 1.7 なぜ原価の閲覧を「社長＋指名者のみ」にしたのか？

**結論**: 原価＝会社の利益構造そのものであり、全員に見せる情報ではないから。

**TMへの説明ポイント**:
- 作業員が「この現場は利益率50%か」と知ると、賃上げ交渉の材料にされる可能性
- 協力会社に外注費の詳細が見えると、次回の見積もりを吊り上げられるリスク
- ただし「社長だけ」だと、社長不在時に誰も判断できない
- → 「社長が権限を与えた人」（＝信頼できる役員や経理）にも見せられる設計

### 1.8 なぜ資格アラートを5段階にしたのか？

**結論**: ヒアリングで「1年前、6ヶ月前、3ヶ月前、1ヶ月前、1週間前」と明確に指定されたため。

**背景の合理性**:
| タイミング | 想定アクション |
|-----------|--------------|
| 1年前 | 更新研修の受講計画を立てる |
| 6ヶ月前 | 研修の申し込み（人気の研修は半年前に埋まる） |
| 3ヶ月前 | 研修受講 → 更新手続き開始 |
| 1ヶ月前 | 手続きが間に合っているか最終確認 |
| 1週間前 | 最終警告 |
| 期限切れ | 資格無効化 → 該当業務に配置不可 |

- 1回の通知だけだと「見落としてそのまま」になるリスクが高い
- 段階的に通知することで「誰かが気づく」確率を上げる

## 2. DB設計の判断根拠

### 2.1 なぜPostgreSQLを選んだのか？

**結論**: リレーショナルDB（表形式のDB）が必要で、その中でPostgreSQLが最も機能が豊富だから。

**比較表**:
| DB | 特徴 | 今回の適合度 |
|----|------|------------|
| **PostgreSQL** | 高機能、UUID標準対応、配列型あり、pgvector拡張でAI検索も可能 | ◎ 最適 |
| MySQL | シンプル、シェアが高い | ○ 使えるがUUID周りがやや弱い |
| MongoDB (NoSQL) | スキーマレス、柔軟 | △ 44テーブルの関連が複雑なので不向き |
| SQLite | ファイルベース、簡単 | × 複数ユーザー同時アクセスに弱い |

**TMへの説明ポイント**:
- 今回のアプリは「現場→日報→原価」のようにデータ同士の関連が非常に多い
- 関連が多いデータ = リレーショナルDB（表と表を繋ぐ）のが得意分野
- PostgreSQLは無料かつ企業利用実績が豊富（Instagram、Spotify等が使用）
- pgvector拡張を入れればAI見積もり用のベクトル検索もできる（別DBが不要）

### 2.2 なぜ44テーブルもあるのか？

**結論**: 「1つのことを1つの場所に保存する」という正規化の原則に従った結果。

**例: もし「発注」を1テーブルにまとめたら？**

```
❌ 悪い設計（1テーブルに全部入れる）:
| 発注ID | 仕入先 | 材料1名 | 材料1数量 | 材料1単価 | 材料2名 | 材料2数量 | ... |

問題:
- 材料が10個あったら10組のカラムが必要 → カラム数が爆発
- 「材料3」を後から追加できない
- 集計が困難
```

```
✅ 良い設計（テーブルを分ける）:
purchase_orders: | 発注ID | 仕入先 | 発注日 | 合計金額 |
po_items:        | 明細ID | 発注ID | 材料   | 数量 | 単価 |

利点:
- 材料が何個でも行を追加するだけ
- 「材料Aの発注総額」などの集計が簡単
- データの重複がない
```

**TMへの説明ポイント**:
- テーブル数が多い ≠ 複雑。むしろ「整理されている」
- Excelで言えば「1シートに全部書く」より「シートを分けて関連づける」ほうが管理しやすいのと同じ
- 44テーブルは8モジュール÷44 = 平均5.5テーブル/モジュール。各モジュール内は3〜8テーブル程度で扱いやすい

### 2.3 なぜUUID（ランダムID）を使うのか？

**結論**: 連番ID（1, 2, 3...）だとセキュリティと拡張性に問題があるから。

| 項目 | 連番ID (1, 2, 3) | UUID (a3b4c5d6-...) |
|------|-----------------|---------------------|
| 推測可能性 | `/users/1`, `/users/2` → 全ユーザーが推測できる | ランダムなので推測不可 |
| DB統合 | 2つのDBを統合するとIDが衝突する | 衝突確率は実質ゼロ |
| 生成場所 | DBでしか生成できない | アプリ側でも生成できる |

**TMへの説明ポイント**:
- URLに `/reports/3` と出ると「/reports/1 も /reports/2 もあるな」とわかってしまう
- UUIDなら `/reports/a3b4c5d6-...` となり、他のデータの存在を推測できない
- 将来的に複数拠点のデータを統合する際にもIDが被らない

### 2.4 なぜ「日報ヘッダー」と「日報明細」を分けたのか？

**結論**: 1つの日報に複数の作業員の記録が入るから。

```
daily_reports（ヘッダー = 日報1件）:
| id  | 現場   | 作業日  | 天候 |
| 001 | A現場  | 8/3    | 晴   |

daily_report_items（明細 = 作業員ごとの記録）:
| id  | report_id | 作業員 | 工種     | 開始  | 終了  |
| 101 | 001      | 田中   | 配線工事  | 8:00 | 17:00 |
| 102 | 001      | 佐藤   | 電灯取付  | 8:00 | 19:00 |
| 103 | 001      | 鈴木   | 配線工事  | 9:00 | 18:00 |
```

**TMへの説明ポイント**:
- 「日報」自体の情報（現場・日付・天候）は1つだけ
- でも1つの日報に5人、10人の記録が入る
- ヘッダー（共通情報）と明細（個別情報）を分けることで、データの重複を防ぐ
- Excelで言えば「1行に全員分を横に並べる」のではなく「人数分の行を作る」

### 2.5 なぜ actual_costs に source_type / source_id があるのか？

**結論**: 「この原価データはどこから来たのか」を追跡するため。

```
actual_costs:
| id | 現場  | 区分   | 金額    | source_type      | source_id |
| 01 | A現場 | 労務費 | ¥24,000 | 'daily_report'   | 日報ID    |
| 02 | A現場 | 材料費 | ¥57,500 | 'purchase_order' | 発注ID    |
| 03 | A現場 | 経費   | ¥15,000 | 'manual'         | NULL      |
```

**TMへの説明ポイント**:
- 原価は3つの経路から入ってくる：日報（自動）、材料発注（自動）、手動入力
- 「この¥24,000はどの日報から計算されたの？」と遡れないと、数字の根拠が示せない
- source_type + source_id で「元データへのリンク」を保持 → 監査対応にも有効

### 2.6 なぜインデックスを設計したのか？

**結論**: データが増えても検索が速いままにするため。

**例え話**:
- インデックスなし = 本の目次がない状態。「PostgreSQLの章はどこ？」→ 1ページずつめくって探す
- インデックスあり = 目次がある状態。「PostgreSQLの章は p.234」→ 一発で開ける

**具体例**:
```sql
-- 「A現場の8月の日報」を検索する場合

-- インデックスなし: 全日報10万件を1件ずつチェック → 遅い
-- インデックスあり: site_id + report_date の目次から即座に見つかる → 速い

CREATE INDEX idx_daily_reports_site_date ON daily_reports(site_id, report_date);
```

**TMへの説明ポイント**:
- 今は数百件でも、3年後には数万件のデータになる
- インデックスがなければ、3年後に「今月の日報一覧」を開くのに10秒かかるかもしれない
- 最初から適切なインデックスを設計しておけば、データが増えても速度が維持できる

## 3. 技術選定の判断根拠

### 3.1 なぜ Django で始めて、将来 Next.js に移行するのか？

**結論**: 既に構築済みのDjangoコード（12アプリ、50+テスト）を捨てるのはコストが大きすぎる。ただし将来のフロントエンド品質向上のため、**最初からNext.js移行を前提とした設計ルール**で開発する。

**段階移行の戦略**:
```
【今】Django Templates + HTMX（速く作る）
  ↓
【中期】Django REST Framework を追加（API層を並行構築）
  ↓
【将来】Django API + Next.js フロント（高品質UI）
```

**なぜ最初からNext.jsにしないのか？**:
| 観点 | 最初からNext.js | Django → Next.js段階移行 |
|------|----------------|------------------------|
| 既存コードの活用 | × 12アプリをゼロから書き直し | ◎ 既存コードをそのまま使える |
| AI/ML連携 | △ Pythonサーバーを別途必要 | ◎ Pythonネイティブで直接連携 |
| 開発開始までの時間 | △ 環境構築に時間がかかる | ◎ 即座に開発開始可能 |
| 将来のUI品質 | ◎ 最初からReactコンポーネント | ○ 移行後にReactに置き換え |
| 型安全性 | ◎ TypeScriptで一気通貫 | △→◎ 移行後に実現 |

**TMへの説明ポイント**:
- 「今ある土台を活かしつつ、将来もっと良くできる設計にしておく」
- ビジネスロジック（計算や判定の処理）は `services.py` に集約する → フロントを差し替えても、裏側の処理はそのまま使い回せる
- 移行は「全部を一気に」ではなく「1モジュールずつ段階的に」行える

### 3.2 なぜ TypeScript なのか？

**結論**: 「型」があることで、バグを事前に防げるから。

**例え話**:
```
JavaScript（型なし）:
  「この箱には何でも入れていいよ」
  → 数字を期待してたのに文字列が入ってた → 動かしてから初めて気づく

TypeScript（型あり）:
  「この箱には数字しか入れちゃダメ」
  → 文字列を入れようとした時点でエラーが出る → 動かす前に気づく
```

**44テーブルの型定義への影響**:
- 44テーブル × 平均8カラム = 約350個の項目
- 型がないと「日付のカラムに文字列を入れてしまう」ようなミスが頻発する
- TypeScriptなら書いている最中にエディタが教えてくれる

### 3.3 なぜ shadcn/ui なのか？

**結論**: 「コピペ方式」で自分のプロジェクトに取り込むため、カスタマイズが完全に自由だから。

**UIライブラリの比較**:
| ライブラリ | 方式 | カスタマイズ性 | 依存関係 |
|-----------|------|-------------|---------|
| **shadcn/ui** | コピペ（自分のコードになる） | ◎ 完全自由 | なし（自分のコード） |
| MUI | npm install | △ テーマ変更のみ | ライブラリに依存 |
| Ant Design | npm install | △ 中国語ドキュメントが多い | ライブラリに依存 |
| Chakra UI | npm install | ○ | ライブラリに依存 |

**TMへの説明ポイント**:
- npm installする通常のライブラリは「借りている」状態。ライブラリが更新されると壊れるリスク
- shadcn/uiは「もらってくる」方式。自分のコードとして完全にコントロールできる
- ボタンの色を変えたい、フォームの挙動を変えたい → 自分のファイルを直接編集するだけ

### 3.4 なぜ Prisma（ORM）なのか？

**結論**: SQLを直接書かずに、TypeScriptのコードでDBを操作できるから。

```typescript
// SQLを直接書く場合（ミスしやすい）:
const result = await db.query(
  'SELECT * FROM daily_reports WHERE site_id = $1 AND report_date = $2',
  [siteId, date]
);

// Prismaを使う場合（型安全、自動補完が効く）:
const result = await prisma.dailyReport.findMany({
  where: { siteId, reportDate: date },
  include: { items: true }  // 明細も一緒に取得
});
```

**追加のメリット**:
- 44テーブルの定義を `schema.prisma` 1ファイルで管理
- テーブル構造を変更したら `prisma migrate` で安全にDBを更新
- DBの種類を変えたくなった場合（PostgreSQL → MySQL等）、コードはそのまま

### 3.5 なぜ tRPC なのか？

**結論**: APIの型定義を手動で書かなくて済むから。

```
通常のAPI開発:
  1. サーバー側でAPIを定義
  2. クライアント側で「このAPIはこの型のデータを返す」と手動で定義
  3. サーバーを変更 → クライアントの定義も手動で変更（忘れるとバグ）

tRPCを使った場合:
  1. サーバー側でAPIを定義
  2. クライアント側は自動で型が伝わる（手動定義不要）
  3. サーバーを変更 → クライアント側も自動で型エラーが出る（忘れようがない）
```

**TMへの説明ポイント**:
- 44テーブル × CRUD（作成・読込・更新・削除）= 最低176個のAPI
- 手動で型を2箇所管理するのは現実的でない
- tRPCなら「サーバーで書いたら、画面側でも自動で型がわかる」

### 3.6 なぜ Docker なのか？

**結論**: 「自分のPCでは動くのに、本番サーバーでは動かない」を防ぐため。

**例え話**:
- Dockerなし = 料理のレシピだけ渡す。「塩少々」の解釈が人によって違う
- Dockerあり = 完成した弁当箱ごと渡す。開けたらそのまま食べられる

**具体的なメリット**:
```
docker compose up -d
→ PostgreSQL、Redis、MinIO、Ollamaが全部一発で起動
→ 誰がやっても同じ環境が再現される
```

### 3.7 なぜ セルフホスト（自社サーバー/VPS）なのか？

**結論**: AI推論サーバーをローカルで動かす要件があり、かつコストを抑えたいから。

**比較**:
| ホスティング | 月額目安 | AI推論 | データ管理 |
|------------|---------|--------|----------|
| **VPS (自社管理)** | ¥5,000〜15,000 | ◎ GPU搭載可 | ◎ 完全自社 |
| Vercel + Supabase | ¥3,000〜10,000 | × GPU不可 | △ 外部 |
| AWS | ¥20,000〜 | ○ 高額 | ○ AWSリージョン |

**TMへの説明ポイント**:
- 入札金額や原価データは機密性が高い → 自社管理が望ましい
- AI推論をクラウドGPUで動かすと月数万円 → VPSにGPU載せれば固定費のみ
- VPS（ConoHa、さくら等）は国内データセンターで日本語サポートあり

### 3.8 なぜ BullMQ（ジョブキュー）が必要なのか？

**結論**: 「今すぐ返事がなくてもいい処理」をバックグラウンドで実行するため。

**対象の処理**:
| 処理 | なぜバックグラウンド？ |
|------|---------------------|
| 予算超過アラート通知 | 日報保存のたびにチェック。画面を待たせたくない |
| 入札案件スクレイピング | Webサイトの巡回に数分かかる。ユーザーは待てない |
| AI見積もり | 推論に30秒〜数分。画面はすぐ閉じてOK |
| メール通知 | メールサーバーへの送信に数秒。失敗時にリトライしたい |
| 資格期限チェック | 毎朝定時に全作業員を一括チェック |

**例え話**:
- BullMQなし = レストランで注文したら料理が出るまでレジの前に立たされる
- BullMQあり = 注文したら席に戻れる。出来上がったら呼ばれる

### 3.9 なぜ PWA なのか？（ネイティブアプリではなく）

**結論**: 1つのコードでPC・スマホ両方に対応でき、アプリストア審査も不要だから。

| 項目 | PWA | ネイティブアプリ（iOS/Android） |
|------|-----|-------------------------------|
| 開発コスト | 1つ作れば両方で動く | iOS版とAndroid版を別々に開発 |
| アプリストア | 不要（URLで配布） | 必要（審査に1〜2週間） |
| アップデート | サーバー側で即反映 | ストアに再申請→審査→配布 |
| ホーム画面追加 | ○ | ○ |
| プッシュ通知 | ○（2024年〜iOSも対応） | ○ |
| カメラアクセス | ○ | ○ |
| オフライン | △（一部対応） | ○ |

**TMへの説明ポイント**:
- 「アプリをダウンロードしてください」が不要。URLを開くだけ
- 「ホーム画面に追加」でアプリのように使える
- アップデート時にユーザーが何もしなくても最新版になる

## 4. 画面設計の判断根拠

### 4.1 なぜサイドバー＋下部タブの切替か？

**結論**: PCとスマホでは画面の使い方が根本的に違うから。

```
PC（横長）: サイドバーが自然
┌────┬──────────────┐
│メニ│  コンテンツ    │  ← 横に余裕があるのでメニューを左に置ける
│ュー│              │
└────┴──────────────┘

スマホ（縦長）: 下部タブが自然
┌──────────────┐
│  コンテンツ    │  ← 画面幅が狭いのでサイドバーは邪魔
│              │
├──────────────┤
│ [タブ1][タブ2]│  ← 親指が届く下部にメニュー
└──────────────┘
```

**TMへの説明ポイント**:
- LINE、Instagram等のスマホアプリはすべて下部タブ → ユーザーが慣れている
- PCのサイドバーは一覧性が高く、8モジュール＋設定を全部表示できる
- 768px（タブレット横幅）をブレークポイントとして自動切替

### 4.2 なぜダッシュボードにKPIカードを置くのか？

**結論**: ログイン直後に「今何が起きているか」を一目で把握するため。

```
┌─────────────┐ ┌─────────────┐ ┌─────────────┐
│ 稼働中の現場  │ │ 今月の人工   │ │ 未処理アラート│
│     12      │ │   245.5    │ │    ⚠ 8     │
└─────────────┘ └─────────────┘ └─────────────┘
```

**TMへの説明ポイント**:
- 社長が朝出社してアプリを開いた瞬間に、全体状況がわかる
- 「どの現場がヤバいか」「誰がサボっているか」をすぐ確認できる
- 詳細を見たければカードをクリックして各モジュールに遷移

### 4.3 なぜ日報入力にAI補助ボタンを置くのか？

**結論**: 現場作業員が汚れた手やグローブのままでも、最小限の入力で日報を完成させるため。

**使用シナリオ**:
1. 作業員が現場で写真を撮る（作業前後の記録写真）
2. 「📷 写真から入力」をタップ
3. AI が写真から「配線工事」「LED照明」等を認識
4. 自動で工種・作業内容が入力される → 作業員は確認してOKを押すだけ

**別のシナリオ**:
1. 職長がLINEグループに「今日A現場、田中佐藤鈴木、配線工事、8時〜17時」と書く
2. そのテキストをコピーして「📋 テキストから入力」に貼付
3. AIが解析して各フィールドに自動入力

### 4.4 なぜガントチャートを「現場単位」にしたのか？

**結論**: ヒアリングで「現場単位のバー」と明確に回答されたため。

**他の選択肢との比較**:
| 詳細度 | イメージ | 用途 |
|--------|---------|------|
| **現場単位** | A現場 ████████ | 全体の工期を俯瞰 ← **今回採用** |
| 工程フェーズ単位 | 配線→電灯→検査 | 1現場の中の進捗管理 |
| 作業員単位 | 田中: A現場→B現場 | 人の動きを追跡 |

**TMへの説明ポイント**:
- 社長や役員が見たいのは「全現場の工期の全体像」
- 1現場の工程詳細は、現場をクリックしたら見える（フェーズ表示に切替）
- 作業員の動きは「配置カレンダー」で別途表示

### 4.5 なぜカンバン（タスクボード）を開発管理に採用したのか？

**結論**: ソフトウェア開発のタスク管理に最も適した可視化手法だから。

```
TODO → 進行中 → レビュー → 完了
```

**TMへの説明ポイント**:
- Trello、Jira、GitHub Projects 等、世界中の開発チームが使っている形式
- 「今誰が何をやっているか」「ボトルネックはどこか」が一目でわかる
- カードをドラッグ＆ドロップで直感的に状態を変更できる
- Discord通知と組み合わせることで、ステータス変更時に自動通知

### 4.6 なぜ31画面なのか？（多い？少ない？）

**結論**: 8モジュール × 平均4画面 = 適切な粒度。

**画面数の根拠**:
| 考え方 | 画面数 | 問題 |
|--------|--------|------|
| 全部1画面に詰め込む | 1 | 使いにくい、情報過多 |
| 機能ごとに細分化 | 100+ | 遷移が多すぎて迷子になる |
| **モジュール×主要操作** | **31** | **適切なバランス** |

**TMへの説明ポイント**:
- 31画面は「ユーザーが迷わない最小限の画面数」
- 各画面に明確な役割が1つある（一覧を見る、入力する、集計を見る等）
- タブ切替で関連情報を1画面内に収めている（例: 作業員詳細の資格/スキル/研修タブ）

### 4.7 なぜ権限マトリクス画面を用意したのか？

**結論**: 「誰が何を見られるか」を社長が一目で確認・変更できるようにするため。

```
┌──────────┬────┬────┬────┬────┐
│ ロール    │日報│原価│材料│入札│
├──────────┼────┼────┼────┼────┤
│ 社長      │ RWA│ RWA│ RWA│ RWA│
│ 現場担当  │ RW │ —  │ R  │ —  │
│ 事務      │ RW │ —  │ RW │ R  │
└──────────┴────┴────┴────┴────┘
```

**TMへの説明ポイント**:
- 社長が「佐藤さんにも原価を見せたい」と思ったら、この画面でチェックを入れるだけ
- 複雑な設定ファイルを編集する必要なし
- 権限変更の履歴も記録されるので「いつ誰が変更したか」が追跡可能

## 5. 全体を通しての設計思想

### 5.1 三つの原則

| 原則 | 意味 | 具体例 |
|------|------|--------|
| **データは一箇所に** | 同じ情報を2箇所に保存しない | 作業員情報は `users` テーブルのみ。日報にも原価にも「参照」で使う |
| **自動化できるものは自動で** | 人間が手動でやるとミスする作業はシステムに任せる | 日報→勤怠集計、発注→原価計上、期限→アラート |
| **将来の変更に備える** | 今は使わなくても、構造的に拡張可能にしておく | 承認フロー、マルチテナント、AI強化 |

### 5.2 コストの考え方

| 項目 | 初期コスト | 月額ランニング |
|------|-----------|--------------|
| 開発 | 開発者の時間 | — |
| サーバー（VPS） | — | ¥5,000〜15,000 |
| ドメイン | — | ¥1,000〜2,000/年 |
| SSL証明書 | — | ¥0（Let's Encrypt） |
| AI推論 | GPU購入（任意） | ¥0（電気代のみ） |
| 外部API | — | ¥0（使用しない設計） |
| **合計** | — | **¥6,000〜17,000/月** |

**TMへの説明ポイント**:
- SaaSの建設管理アプリ（ANDPAD等）は月額¥30,000〜100,000+
- 自社開発なら月額¥6,000〜17,000で同等以上の機能が実現可能
- さらにデータが完全に自社管理できる（SaaSだとベンダーロックイン）
