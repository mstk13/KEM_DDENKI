## 設計思想

KEM_DDENKI の AI は **3つの原則** で設計されている。

```
1. 機能は一つも削らない。品質が価値の中核でないタスクだけ実行先を変える
2. 決まった形のものは決まった手順で読み、崩れたものだけモデルに回す
3. 分からないことを分かったように書かない
```

AI は「人間の判断を代替する」のではなく、「人間が判断するための材料を速く揃える」ために使う。
自動確定できるものは確定し、曖昧なものは候補を出して人に選ばせる。
判定できないものを「資格なし」と断定せず「要確認」と返す。

## 3層アーキテクチャ

AI 推論をコスト・速度・品質で3層に分け、タスク種別で振り分ける。
詳細: [ADR-0010 AI推論の3層分割](../saas/adr/ADR-0010-ai-inference-tiering.md)

```
                        ┌─────────────────────────────┐
                        │     Django (web コンテナ)     │
                        └──────────┬──────────────────┘
                                   │
                    ┌──────────────┼──────────────────┐
                    ▼              ▼                   ▼
            ┌──────────────┐ ┌──────────────┐ ┌──────────────┐
            │   層A        │ │   層B        │ │   層C        │
            │  Embedding   │ │  ローカルLLM  │ │  Claude API  │
            │              │ │              │ │              │
            │ bge-m3       │ │ Qwen3-8B     │ │ Haiku/Sonnet │
            │ 1,024次元     │ │ Q4_K_M 5GB   │ │ 従量課金      │
            │              │ │              │ │              │
            │ ≒0円/回      │ │ ≒0.04円/回   │ │ ≒1.2円/回    │
            │ <1秒         │ │ 30秒         │ │ 13秒         │
            └──────────────┘ └──────────────┘ └──────────────┘
                 │                  │                  │
                 ▼                  ▼                  ▼
            品目名の         PDF構造化         分析・提案
            類似度マッチング    納品書OCR         コスト最適化
                              取引先抽出         工程提案
```

### 振り分けの基準

**「安いから移す」ではなく「遅くても困らないから移す」。**

| 基準 | 層A/B（ローカル） | 層C（API） |
|------|------------------|-----------|
| 応答速度の要件 | バッチ処理。遅くても業務に影響なし | 画面から同期呼び出し。待ち時間がUXに直結 |
| 品質の重要度 | 候補生成。最終判断は人または層Cが行う | 建設業の文脈判断そのものが機能の価値 |
| 呼び出し頻度 | 数百〜数千回/月 | 数十回/月 |

## 各層の詳細

### 層A — Embedding（ベクトル類似度）

**目的:** 積算品目の名寄せ（同じ材料の表記ゆれを同一品目にマッチング）

**技術:** bge-m3 モデル（1,024次元ベクトル）

**実装:** `apps/estimation/services/matching.py`

**判定の3段構え（実測に基づく閾値）:**

```
コサイン類似度
  0.85以上  →  自動確定
  0.65〜0.85 →  上位k件を層C(LLM)に渡して選ばせる
  0.65未満  →  不一致
```

**なぜ単一閾値ではダメか（実測データ）:**

| 対象 | 類似度 | 判定 |
|------|-----:|------|
| VVFケーブル1.6-2C 100m巻き（表記ゆれ） | 0.904 | 同一 |
| VVF 1.6×2C 100m（略記） | 0.768 | 曖昧 |
| CVケーブル 2.0mm 3芯（**別種**） | 0.668 | 曖昧 |
| エアコン用コンセント | 0.443 | 別物 |

同一品目の略記（0.768）と別種ケーブル（0.668）の差はわずか0.10。
単一閾値で自動確定するとCVケーブルをVVFとして誤マッチする。

詳細: [ADR-0010 §導入後の実測](../saas/adr/ADR-0010-ai-inference-tiering.md#導入後の実測2026-08-14)

---

### 層B — ローカルLLM（Qwen3-8B）

**目的:** PDF構造化、納品書OCR、取引先名抽出

**技術:** Qwen3-8B Q4_K_M（Ollama、Windows ネイティブ）

**実装:** `apps/ai/services/llm_advisor.py`（プロバイダ抽象）

**なぜ 8B で 14B ではないか（VRAM制約）:**

```
RTX 3060 12GB の実効 VRAM ≒ 11GB

Qwen3-8B Q4 + 埋め込み = 6.7GB  → 空き 4.3GB (余裕あり)
Qwen3-14B Q4           = 9.2GB  → 空き 0.6GB (KVキャッシュが足りない)
```

**性能実測:**
- 生成速度: 58 tok/s（想定45〜55を上回る）
- 推論時消費電力: 155W / 74℃
- JSON Schema 指定で出力トークンが 1,550 → 111 に削減

**フォールバック:** ローカル失敗時は Claude API に自動切り替え。機能を止めるのではなくコストを払って動かす。

詳細: [ADR-0010 AI推論の3層分割](../saas/adr/ADR-0010-ai-inference-tiering.md)

---

### 層C — Claude API

**目的:** コスト最適化提案、工程提案、工程リスク分析、文字化けPDF解読

**技術:** Claude API（Haiku: 抽出系 / Sonnet: 分析・判断系）

**実装:** `apps/ai/services/llm_advisor.py`

**モデル使い分け:**

| モデル | 用途 | コスト/回 | 使い分けの理由 |
|--------|------|----------|--------------|
| Haiku | 抽出・分類 | ¥0.18 | 定型的な情報抽出。速度とコスト優先 |
| Sonnet | 分析・提案・PDF解読 | ¥1.2 | 建設業の文脈判断・参加資格の解釈。品質が機能の価値 |

**文字化けPDFの処理（層Cでしかできない仕事）:**

フォントに ToUnicode が無い PDF は pdfplumber が `(cid:NNN)` しか返せない。
Claude は PDF をページ画像として読めるため、OCR ライブラリ（tesseract）を追加せずに解決できる。

```
決定論的に読めた → そのまま使う（LLM不要）
読めない + (cid)検出 → Claude Sonnet に画像として渡す
```

65件中1件が該当。tesseract を Dockerfile に入れるリスクより、¥10/件の API 費用の方が安全。

詳細: [ADR-0006 Claude API統合](../saas/adr/ADR-0006-claude-api-integration.md) / [ADR-0012 文字化けPDF](../saas/adr/ADR-0012-garbled-announcement-llm-fallback.md)

## コスト管理

### 記録と予算制御

全ての AI 呼び出しは `AILog` モデルに記録される。

```python
# apps/ai/models.py
class AILog(TenantModel):
    task_type    # cost_forecast / cost_optimization / delivery_ocr / ...
    model_type   # claude-haiku / claude-sonnet / lgbm / custom
    prompt       # 入力プロンプト全文
    response     # 応答全文
    cost_usd     # このリクエストの費用（USD）
    tokens_in    # 入力トークン数
    tokens_out   # 出力トークン数
    latency_ms   # 応答時間（ミリ秒）
    status       # success / error / timeout
```

### 月間予算

`AI_MONTHLY_BUDGET_JPY=4000`（環境変数）で月間上限を設定。
上限到達時は `check_budget_and_notify()` が層C（Claude API）を停止する。
層A・層Bはローカル実行のため予算の影響を受けず、業務が止まる範囲を最小化する。

### コスト比較

| 処理 | Claude API | ローカル | 差 |
|------|-----------|---------|-----|
| 品目マッチング1件 | ¥0.18 (Haiku) | ≒¥0 (Embedding) | API不要に |
| PDF構造化1ページ | ¥0.18 (Haiku) | ¥0.04 (Qwen3-8B) | 4.5倍安い |
| コスト最適化提案1回 | ¥1.22 (Sonnet) | — | 品質のため据え置き |
| 文字化けPDF解読1件 | ¥10 (Sonnet) | — | 月数件。代替なし |

**年間の実質削減額は約5,000円。** コスト削減自体は小さいが、
「予算上限でAI機能が止まらなくなる」「一括マッチングを気兼ねなく回せる」ことが本当の価値。

## 使用モデル解説

本プロジェクトで使用する各モデルの技術的背景。
「名前は知っているが中身がわからない」開発者向けの解説。

### LightGBM（Light Gradient Boosting Machine）

| 項目 | 内容 |
|------|------|
| **種別** | 勾配ブースティング決定木（GBDT） |
| **開発元** | Microsoft Research（2017年〜、OSS） |
| **本プロジェクトでの用途** | 施工中の現場の最終原価を予測 |
| **実装** | `apps/ai/services/ml_predictor.py` |

**仕組み:** 多数の「弱い決定木」を順番に作り、前の木の予測誤差を次の木が修正していく。
1本の木は精度が低いが、数百本重ねることで高精度な予測になる。

**なぜ選んだか:**
- **少データに強い**: テナントごとの現場数（数十〜数百件）でも過学習しにくい。ニューラルネットは数千件ないと性能が出ない
- **CPU のみで動く**: GPU不要。推論が数ミリ秒で終わる
- **説明可能**: 「契約金額が一番予測に効いている」「工期の長さが2番目」のように特徴量の重要度が出る。ブラックボックスではない
- **依存が軽い**: `lightgbm` + `scikit-learn` + `joblib` の3パッケージのみ

**不採用にしたもの:**
- XGBoost: LightGBM と同系統だが、少データでのチューニングが煩雑
- 線形回帰: 非線形の関係（消化ペースの加速など）を捉えられない
- ニューラルネット: データが少なすぎて過学習する。推論環境も重い

### Claude API（Anthropic）

| 項目 | 内容 |
|------|------|
| **種別** | 大規模言語モデル（LLM）のクラウドAPI |
| **開発元** | Anthropic |
| **本プロジェクトでの用途** | コスト分析・工程提案・PDF解読 |
| **実装** | `apps/ai/services/llm_advisor.py` |

**2つのモデルを使い分ける:**

| モデル | パラメータ規模 | 特徴 | 本プロジェクトでの役割 |
|--------|-------------|------|---------------------|
| **Haiku** | 小型・高速 | 応答が速く安い。単純な抽出・分類に向く | 品目マッチングの最終判定（層A→Cのフォールバック） |
| **Sonnet** | 中型・高精度 | 文脈理解が深い。複雑な判断に向く | コスト最適化提案・工程リスク分析・文字化けPDF解読 |

**なぜ Sonnet を分析系に使うか:**
建設業のコスト最適化は「電気工事で資材費が膨らむのは、銅価格の変動が原因か、設計変更による追加配線か」のような
業界固有の文脈判断が価値の中核。小型モデルでは提案の質が落ち、機能を作った意味が薄れる。

**なぜ Haiku を抽出系に使うか:**
「この2つの品目名は同じものか？」のような判定は文脈が浅く、速度とコストを優先すべき。

**料金体系:** トークン（≒文字数の3〜4分の1）単位の従量課金。
入力と出力で単価が異なり、出力の方が高い。1回あたり¥0.18〜¥1.2程度。

### Qwen3-8B（通義千問）

| 項目 | 内容 |
|------|------|
| **種別** | オープンウェイトLLM（ローカル実行可能） |
| **開発元** | Alibaba Cloud（阿里雲）、Apache 2.0ライセンス |
| **パラメータ数** | 80億（8B） |
| **本プロジェクトでの用途** | PDF構造化・納品書OCR・取引先名抽出 |
| **実行方法** | Ollama 経由、Q4_K_M 量子化（5.2GB） |
| **実装** | `apps/ai/services/llm_advisor.py`（プロバイダ抽象） |

**なぜ Qwen3 か:**
- Apache 2.0ライセンスで商用利用に制限なし
- 日本語性能が8Bクラスで最も高い（建設用語・法令文書を含む）
- JSON Schema を渡すと構造・キー名・型を厳密に守る（実測で確認済み）

**量子化（Q4_K_M）とは:**
モデルの重みを32bit浮動小数点から4bitに圧縮する技術。
精度は若干落ちるが、メモリ使用量が約4分の1になる（32GB→5.2GB）。
構造化抽出タスクでは精度低下が無視できるレベル（実測で正答3/3）。

**なぜ 14B ではなく 8B か:**
RTX 3060（VRAM 12GB）で Embedding モデルと同時にロードする必要がある。
14B の Q4 は 9.2GB で、KVキャッシュ（推論中の一時メモリ）を加えるとVRAMが溢れる。
8B なら 5.2GB + 埋め込み 1.2GB = 6.4GB で、約4GBの余裕がある。

**生成速度:** 58 tok/s（実測）。50ページのPDFで約1時間。
バッチ処理なので速度がUXに影響しない。

### bge-m3（BAAI General Embedding）

| 項目 | 内容 |
|------|------|
| **種別** | テキスト埋め込み（Embedding）モデル |
| **開発元** | BAAI（北京智源人工智能研究院）、MITライセンス |
| **次元数** | 1,024 |
| **モデルサイズ** | 1.2GB |
| **本プロジェクトでの用途** | 積算品目の名寄せ（類似度マッチング） |
| **実行方法** | Ollama 経由 |
| **実装** | `apps/estimation/models.py`（ItemEmbedding） |

**Embedding とは:**
テキストを固定長の数値ベクトル（1,024個の小数の配列）に変換する技術。
意味が近いテキストは近いベクトルになる。
2つのベクトルの「コサイン類似度」を計算すると、0〜1の値で意味の近さがわかる。

```
"VVFケーブル 1.6mm 2芯 100m巻"  →  [0.12, -0.34, 0.56, ...]  ─┐
                                                                  ├─ 類似度 0.904
"VVFケーブル1.6-2C 100m巻き"     →  [0.11, -0.33, 0.55, ...]  ─┘

"CVケーブル 2.0mm 3芯"           →  [0.08, -0.41, 0.49, ...]  ─── 類似度 0.668（別物）
```

**なぜ bge-m3 か:**
- 多言語対応（日本語の建設用語でも精度が出る）
- "m3" = Multi-lingual, Multi-granularity, Multi-functionality
- 1,024次元は精度と速度のバランスが良い（768次元より精度が高く、4,096次元より速い）
- MITライセンスで商用利用に制限なし

**限界（実測で判明）:**
同一品目の略記（0.768）と別種ケーブル（0.668）の差が0.10しかない。
単一閾値での自動確定は危険なため、3段構え（自動確定 / LLM確認 / 不一致）で運用する。

### Ollama

| 項目 | 内容 |
|------|------|
| **種別** | ローカルLLM実行ランタイム |
| **開発元** | Ollama（MITライセンス） |
| **本プロジェクトでの用途** | Qwen3-8B と bge-m3 のホスティング |
| **接続** | `host.docker.internal:11434`（Docker コンテナから） |

**何をするものか:**
LLMをローカルPCで動かすための実行環境。
`ollama run qwen3:8b` のようなコマンドでモデルをダウンロード・実行できる。
REST API（`/api/chat`, `/api/embed`）を提供し、Django から HTTP で呼び出す。

**なぜ Windows ネイティブで動かすか:**
- GPU ドライバに直接アクセスできる（WSL経由だとオーバーヘッドがある）
- Docker コンテナ内で GPU を使うには NVIDIA Container Toolkit の設定が必要で、トラブルの原因になる
- `host.docker.internal` で Docker コンテナから簡単に接続できる

**`keep_alive` 戦略:**
モデルをVRAMに保持する時間を制御する。

| 場面 | 設定 | 理由 |
|------|------|------|
| 単発呼び出し | `keep_alive: 0` | 使い終わったら即解放。VRAMの固定消費なし |
| バッチ処理中 | `keep_alive: "10m"` | 50ページPDFで毎回ロード(3秒)すると合計3分のロスになる |

## 実行環境

```
desktop-rmsk0vg (Windows)
├── Docker Desktop
│   ├── web コンテナ   ← Django（AI呼び出し元）
│   ├── cron コンテナ  ← 定期バッチ
│   ├── db             ← PostgreSQL
│   └── redis          ← キャッシュ
│
├── Ollama (Windows ネイティブ)  ← 層A/B の推論
│   ├── bge-m3         ← Embedding (1.2GB)
│   └── qwen3:8b       ← 構造化/抽出 (5.2GB)
│   接続: host.docker.internal:11434
│
└── RTX 3060 12GB      ← GPU (推論時 155W / 74℃)
```

Ollama を WSL やコンテナ内ではなく Windows ネイティブで動かすのは、
GPU ドライバへの直接アクセスと安定性のため。
