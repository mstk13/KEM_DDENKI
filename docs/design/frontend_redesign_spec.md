# フロントエンド再設計仕様書（案C：段階分離）

対象リポジトリ: mstk13/KEM_DDENKI（saas/ 配下の Django アプリ）
版: v1.1（確定） 更新日: 2026-09-06
ステータス: 要決定事項3件を決定済み（§9 決定記録参照）。実装フェーズへ移行可。

---

## 1. 目的と方針

機能拡張を優先してきた結果、フロントエンドの情報設計と実装が複雑化し、UI/UX が使いにくくなっている。本仕様書では「バックエンドとフロントエンドの切り分け」を一度に行うのではなく、次の3段階で進める。

1. 情報設計の再定義 — 誰が・どの画面を・何のために使うかをロール基準で整理し、ナビゲーションと画面構成を再編する
2. 実装の二分 — 画面を複雑度で Tier 分けし、CRUD/一覧系は Django テンプレート＋デザインシステムで刷新、インタラクティブ系のみ API を切ってフロント部品化する
3. API 境界の育成 — Tier 2 で切った API を将来の完全分離（SPA 化）の土台とする

全面 SPA 化を最初から行わないのは、162 テンプレート・249 URL の作り直しは社内ツールとして過剰投資であり、認証・権限・テナント分離の再実装リスクが大きいため。permissions/services.py が既に「DRF API 移行時にもそのまま使える」設計になっている点を活かし、境界を少しずつ広げる。

## 2. 現状の課題（コード診断結果）

### 2.1 ナビゲーションの過積載

base.html のサイドバーは 12 グループ・約 45 リンク。権限による出し分けが一切なく、全ロールに全メニューが表示される。現場担当者にも「積算基準・歩掛」「名寄せレビュー」「入札参加資格」が見える。

### 2.2 情報設計の重複・分裂

| 問題 | 詳細 |
|------|------|
| 評価システムが2系統 | workers アプリの「人材評価」（eval_*）と evaluation アプリ（人事評価一覧・評価基準・評価対象設定）が併存し、ナビの「人材」グループに両方並ぶ |
| 営業の二重掲載 | 「入札・営業」グループと独立「営業」グループが併存 |
| masters の分裂 | 「取引先」グループ（顧客・発注先）と「設定＞マスタ管理」（工種等）に分かれる |
| AI が独立メニュー | 「AI分析」は本来、現場詳細・原価等の文脈で使う機能だが、独立グループとして現場選択画面から入る導線になっている |
| 積算の 8 メニュー | 積算案件・品目・名寄せ・発注機関・労務単価・基準歩掛・仕入実績・データソースがフラットに並ぶ |

### 2.3 フロントエンド層の不在

- 共通 JS は app.js 約 90 行のみ。19 テンプレートにインライン script が散在
- 共通 CSS は style.css 約 590 行に対し、162 テンプレート中 137 枚にインライン style が直書き
- Chart.js / frappe-gantt / FullCalendar を CDN 直読みで画面ごとにバラバラに利用
- 結果として画面ごとに見た目・挙動が微妙に異なり、修正も画面単位でしか効かない

### 2.4 権限システムの実装遅れ

- ModulePermission.MODULE_CHOICES が 10 モジュールで停止。sites / estimation / sales / attendance / evaluation / ai / permissions が権限マトリクスの対象外
- Worker.allowed_apps（JSONField）という別系統のアクセス制御も併存

### 2.5 API 層の不在

- ルート直下 api/（FastAPI）は旧 SQLite アプリ用のレガシー連携で、SaaS 版とは DB も別
- SaaS 側は JsonResponse のアドホックなエンドポイントが 24 個あるのみ

## 3. 情報設計の再定義

### 3.1 ユーザー像（既存6ロールを基準）

| ロール | 主端末 | 主目的 | 使用頻度の高い機能 |
|--------|--------|--------|-------------------|
| president（社長） | PC/スマホ | 経営判断・承認 | ダッシュボード、原価、日報承認、入札判断、権限管理 |
| executive（役員） | PC | 管理・監督 | 原価、工期、入札、人材 |
| site_manager（現場担当者） | スマホ中心 | 施工・記録 | 日報入力、勤怠、担当現場、工期確認、材料、通知 |
| office_staff（事務員） | PC | 事務処理 | 勤怠集計、材料発注、取引先、マスタ |
| partner_worker（協力会社） | スマホ | 限定的な記録 | 日報（自分の分）、勤怠 |
| developer（開発者） | PC | 開発運用 | 開発管理、目安箱、変更ログ、AI利用状況 |

### 3.2 全画面レスポンシブと二つの利用モード

大前提: **すべての画面は PC・スマホの両方でスムーズに使えるレスポンシブ対応とする**。ロールごとに主端末の傾向は異なる（§3.1）が、それはデフォルトの最適化対象を決める材料にすぎず、**モードやデバイスでユーザーを閉じ込めない**。社長がスマホで原価を確認する、現場担当者が事務所の PC で日報をまとめて入力する——どちらの利用も一級市民として扱う。

そのうえで、「現場モード」と「事務所モード」の2つの入り口を用意する。両者の違いはホーム画面とナビの提示方法であり、**機能へのアクセス可否はモードではなく権限マトリクスのみが決める**。モードはヘッダーのメニューからいつでも相互に切替可能で、選択はユーザーごとに記憶される。

現場モード（モバイル最適化されたクイックアクセス UI）

- ホーム: 今日の担当現場・未提出日報・通知のみ表示
- 主要動線は「日報を書く」「勤怠」「担当現場」「通知」の4つ
- 担当現場の詳細から工期（今週の工程・マイルストーン）を読み取り専用で確認できる（§9 決定③）
- 大きなタップ領域・下部タブバー・1画面1タスク
- デフォルト: site_manager / partner_worker がスマホでアクセスした場合。PC からも利用可能（幅広画面では中央寄せレイアウト）
- ハンバーガーメニューから権限内の全機能に到達できる（機能制限ではなく動線の最適化）

事務所モード（フルナビゲーション UI）

- サイドバー型を維持しつつ、§4 の再編ナビを適用
- デフォルト: 上記以外のロール、および PC からのアクセス
- スマホでもサイドバーがドロワー化し、一覧テーブルはカード表示または横スクロールに変形して崩れずに使える（§7 参照）
- 権限マトリクス（can_read）に基づき、閲覧権限のないグループ・リンクは非表示

### 3.3 業務フロー基準のグルーピング

電気工事業の実際の流れ「受注前（入札・営業・積算）→ 施工中（現場・日報・工期・材料）→ お金（原価）→ ヒト（人材・勤怠・評価）」に沿ってナビを再編する。現在の「モジュール名の羅列」から「業務の段階」への転換が本再編の中核。

## 4. ナビゲーション再編案

### 4.1 事務所モード新ナビ（45リンク → 7グループ約22リンク）

```
📊 ダッシュボード

📥 受注前
   ├ 入札案件（+ 案件取得・参加資格・単価マスタは入札案件画面内のタブへ）
   ├ 積算案件
   └ 営業活動（訪問記録・業種別を統合）

🏗️ 施工中
   ├ 現場管理
   ├ 日報管理
   ├ 工期管理
   └ 材料・発注

💰 原価
   └ 現場見積もり/実経費（AIコスト分析はこの画面内から起動）

👥 ヒト
   ├ 作業員
   ├ 勤怠（日報・個人別・月次サマリはタブ化）
   ├ 人材評価（workers 側に一本化 → §9 決定①）
   └ 書類アラート

📚 マスタ
   ├ 取引先（顧客・発注先）
   ├ 積算マスタ（品目・名寄せ・発注機関・労務単価・基準歩掛・仕入実績・データソースを集約）
   └ 業務マスタ（工種・原価区分等）

⚙️ 設定
   ├ 通知・アラート
   ├ 権限管理
   ├ AI利用状況（ダッシュボード・実行ログ・コスト管理を集約）
   └ 変更ログ

💻 開発（developer ロールのみ表示）
   ├ 開発管理
   └ 目安箱
```

### 4.2 再編の原則

1. ナビ第1階層は「業務の段階」、第2階層は「画面」。第3階層は作らずページ内タブで吸収する
2. 権限マトリクス can_read=False のリンクは描画しない（サーバー側で判定）
3. AI 機能は独立メニューを廃止し、利用文脈（現場詳細・原価詳細・工期詳細）内のボタン/タブとして埋め込む
4. マスタ系（頻度低・管理者向け）は「マスタ」に集約し、日常動線から分離する
5. 積算のサブ機能 7 つは「積算マスタ」1 リンクに集約し、遷移先で横タブ切替にする

### 4.3 現場モード（スマホ）

下部タブバー4項目: ホーム / 日報 / 勤怠 / 通知。ホームには「今日の現場」カードと未処理タスク（未提出日報・要確認通知）のみを表示。「今日の現場」カードから担当現場詳細へ遷移でき、そこで今週の工程とマイルストーン（読み取り専用）を確認できる。サイドバー相当のフルメニューはハンバーガーから到達可能とするが、権限で絞った項目のみ表示する。

## 5. 画面の Tier 分類

### Tier 1: CRUD・一覧系（約 150 画面）→ Django テンプレート継続 + デザインシステム刷新

一覧・詳細・フォーム・確認画面。サーバーレンダリングのままで問題なく、デザインシステム適用（§7）とテンプレート部品化で品質を揃える。

### Tier 2: インタラクティブ系（約 10 画面）→ htmx + Alpine.js で部品化（§9 決定②）

| 画面 | 現状 | 部品化の理由 |
|------|------|-------------|
| schedules/detail（ガント） | frappe-gantt 0.6.1 + 月名パッチ | ドラッグ編集・依存関係など将来拡張が確実 |
| schedules/calendar・compare | FullCalendar / Chart.js | 同上 |
| costs/detail（予実ダッシュボード） | Chart.js 直書き | フィルタ・ドリルダウンの応答性 |
| dashboard（トップ） | サーバー集計 | KPI ウィジェットの個別更新 |
| bids/dashboard | Chart.js | 同上 |
| estimation/alias_review（名寄せ） | フォーム連打 | 候補選択 UI は SPA 的操作が本質 |
| sites/boq_edit（内訳書編集） | 大型フォーム | 行編集・再計算のインタラクション |
| devkanri/project_list（カンバン） | サーバーレンダ | ドラッグ&ドロップ |
| ai/cost_report | Chart.js | 同上 |

### Tier 判定基準

「ユーザー操作→即時反映」のループが画面の本質か（Tier 2）、それとも送信→再表示で足りるか（Tier 1）。迷ったら Tier 1 に倒し、不満が出た画面だけ昇格させる。

## 6. バックエンド / フロントエンド境界の定義

### 6.1 API 設計

- Django REST Framework を導入し、名前空間は `/api/v2/`（`/api/v1/` はレガシー FastAPI が使用中のため）
- API は「JSON データが本質的に必要な箇所」に限定する: チャートのデータ系列、ガントのタスク配列、カンバンの並び替え永続化など。画面部品の差し替えは htmx の HTML フラグメント応答（Django テンプレート partial）を第一選択とし、JSON API を乱造しない
- 認証は SessionAuthentication を継続（同一オリジン・VPN 内前提のため、トークン基盤は完全分離フェーズまで不要）
- 権限は has_module_permission() を DRF Permission クラスにラップして再利用
- テナント分離は既存の CompanyScopedManager がそのまま効く（ViewSet の queryset に objects を使う限り越境しない）。Tier 2 API にもテナント越境テストを必須とする（CLAUDE.md ルール準拠）

### 6.2 フロント実装方式: htmx + Alpine.js（§9 決定②）

- ページ自体は従来通り Django が返す。部分更新は htmx（hx-get / hx-post + テンプレート partial）、クライアント側の軽い状態管理（タブ・モーダル・行編集の開閉等）は Alpine.js を使う
- ビルドツール（Vite / npm）は導入しない。htmx・Alpine.js・Chart.js・frappe-gantt・FullCalendar は `static/vendor/` にバージョン固定で同梱し、CDN 直読みを廃止する（オフライン耐性・バージョン固定・VPN 内完結）
- テンプレート partial は `templates/<app>/partials/` に置き、フルページと部品を分離する
- Vue / React 等のビルド前提フレームワークは導入しない。将来 SPA 化する場合も、それまでに整備した `/api/v2/` を土台に別途判断する

### 6.3 レガシー api/（FastAPI）の扱い

SaaS 版とは別系統として現状維持。KEIHI 連携が SaaS 版 DB 参照に切り替わった時点で `/api/v2/` に吸収し廃止する（本仕様書のスコープ外、別 ADR で扱う）。

## 7. デザインシステム方針

1. デザイントークン: 色・余白・フォント・影を CSS 変数として定義（既存 :root 変数を拡充）
2. コンポーネント部品: card / table / form / button / badge / tabs / empty-state / page-header を Django の `{% include %}` テンプレート部品として整備し、`templates/components/` に集約
3. インライン style の段階的撲滅: 新規・改修画面ではインライン style 禁止（コードレビュー基準に追加）。既存 137 枚は画面改修時に随時置換
4. インライン script の集約: 汎用挙動（data-* 属性駆動）は app.js へ、画面固有ロジックは static/js/pages/ へ切り出し
5. 全画面レスポンシブ基準: すべての画面を PC・スマホ両対応とする（§3.2 の大前提）。現場モード画面はモバイルファーストで設計し、タップ領域 44px 以上・下部タブバーを標準とする。事務所モード画面もスマホ幅で崩れないことを完了条件とし、一覧テーブルはスマホ幅でカード表示への変形または横スクロールで対応する。ブレークポイントはデザイントークンとして共通定義し、画面ごとの独自定義を禁止する
6. レスポンシブ検証: 画面改修の PR には PC 幅（1280px）とスマホ幅（375px）双方での表示確認を含める（コードレビュー基準に追加）

## 8. フェーズ計画

### Phase 0: 負債返済と土台（先行必須）

- ModulePermission.MODULE_CHOICES を 17 モジュールに拡張（マイグレーション + 既存ロールへのデフォルト権限付与）
- Worker.allowed_apps と権限マトリクスの関係を整理（マトリクスに一本化を推奨）
- ナビの権限出し分け実装（can_read ベース。テンプレートタグ化）
- 評価システムの workers 側への一本化（§9 決定①）:
  1. evaluation アプリの EvaluatorTarget（評価者割当）相当の機能を workers 側に移植する
  2. evaluation アプリの既存データは読み取り専用アーカイブとして残す（新規作成・編集導線を削除し、閲覧のみ許可）
  3. ナビから evaluation 系リンク（人事評価一覧・評価基準・評価対象設定）を撤去し、「人材評価」に一本化する
  4. 運用が安定した後（目安: 1〜2四半期）、evaluation アプリの廃止を別 ADR で判断する

### Phase 1: 情報設計の実装

- 新ナビゲーション（§4.1）への再編
- 現場モード（下部タブ + ホーム画面 + 担当現場の工期読み取り表示）の新設
- デザインシステム基盤（トークン + components/ + ページヘッダ統一）
- 積算マスタ集約ページ、勤怠タブ化、AI メニュー廃止と文脈内埋め込み

### Phase 2: API 境界の構築

- htmx / Alpine.js / 既存 JS ライブラリの static/vendor/ 同梱と CDN 直読み廃止
- DRF 導入 + `/api/v2/` 基盤（認証・権限・テナント越境テスト）
- Tier 2 画面を優先度順に部品化: ①ガント（工期） ②原価ダッシュボード ③名寄せレビュー ④カンバン

### Phase 3: 検証と拡張

- 利用ログ・現場ヒアリングで新 UI を検証
- 不満の残る Tier 1 画面の Tier 2 昇格判断
- 完全分離（SPA 化）の要否を再評価（このとき /api/v2/ が土台になる）

各フェーズ完了時に docs/saas/adr/ へ ADR を追加する（CLAUDE.md ルール 9 準拠）。

## 9. 決定記録（2026-09-06 確定）

1. 評価システムの統合方向 → **workers 側に一本化**。根拠: workers 側はテンプレートの JSONB カスタマイズ・PDF 出力4種・テンプレート編集 UI を持ち、マイグレーション履歴からも現役開発側である。evaluation アプリは被評価者を名前テキストと nullable FK で二重持ちする移行受け皿的設計で機能も簡素。evaluation 固有で価値のある「評価者割当（EvaluatorTarget）」のみ workers 側へ移植し、evaluation アプリは読み取り専用アーカイブ→将来廃止とする。
2. Tier 2 の部品技術 → **htmx + Alpine.js**。根拠: 少人数開発で Django テンプレート中心の構成を維持する前提では、ビルド環境不要で学習コストが最小。既存のガント・カレンダー・チャートライブラリをそのまま利用できる。ビルド前提フレームワーク（Vue/React）は導入しない。
3. 現場モードの初期スコープ → **日報・勤怠・通知・担当現場の4機能 + 工期確認（読み取り専用）**。工期は独立タブとせず、担当現場詳細内に今週の工程・マイルストーンを表示する形で提供する。材料の納品検収は初期スコープに含めない（Phase 3 の検証結果を見て判断）。
4. デバイス方針 → **全画面レスポンシブを大前提とし、モード・デバイスでユーザーを閉じ込めない**。ロールごとの主端末はデフォルトのモード選択に使うのみで、機能アクセスは権限マトリクスだけが決める。モードはいつでも相互切替可能とし、事務所モードもスマホ幅で崩れないことを画面完了条件に含める。（2026-09-06 追記）
