## 2. 非機能要件（全 PR 共通の完了条件）

## 3. 現状診断（v2.0 の前提を実コードで確認した結果）

### 3.1 アクセス制御

| 仕組み | 判定 | 実際に効いている範囲 |
|---|---|---|
| RBAC（Role / ModulePermission） | ロールのフラグ | 本番 Role 0件のため superuser 以外は常に False。原価ビュー11件・設定4件の `module_permission_required` はこの判定 |
| 原価の特別ルール `_has_cost_access` | 社長/役員/Developer ロール → `User.employee_no` が G 始まり → CostAccessGrant → マトリクス | 本番で実際に効くのは **G 始まり** と **CostAccessGrant** |
| 役職制限（ADR-0022） | `POSITION_RESTRICTED_APPS` | `hr_evaluation`（`/evaluation/`）のみ。サイドバーの3項目も連動 |
| `Worker.allowed_apps` + `AppPermissionMiddleware` | 空リスト＝無制限 | 本番22人全員が空。`/attendance/` `/ai/` `/estimation/` `/audit-log/` は対象外 |
| 場当たり判定 | Y 始まり（管理者）/ 社長 / Django Group "admin" | 作業員の時給表示、書類アラート、評価テンプレート編集など |

アプリを指すキーの語彙が4種類あり一致しない（`MODULE_CHOICES` / `_PATH_TO_APP` / `APP_PERMISSION_CHOICES` / `CompanyApp.APP_CODES`）。
このため `allowed_apps` を1つでも設定すると、選択肢に存在しない通知・設定・営業が 403 になる（本番は全員空なので未発生）。

### 3.2 ナビゲーション

`apps/core/navigation.py` の `NAVIGATION` 定義から描画。12グループ・約40リンク。
権限による出し分けは人事評価3項目のみ。スマホは下部タブなし（サイドバーのドロワー化のみ）。

### 3.3 v2.0 が畳む・移す対象

| 対象 | 現状 | 撤去時の影響 |
|---|---|---|
| 在庫（`materials.Inventory`） | 画面1つ。**どこからもリンクされていない**。検収時に自動で数量更新 | 画面撤去の影響は URL 直打ちのみ |
| 調達（`materials.ProcurementRecord`） | 「調達実績」画面2つ（一覧・登録）。**ナビにもリンクがない**。検収時に自動作成され、仕入先の紐づけにも使われる | 画面撤去のみ。自動作成は発注・仕入先の機能が依存するため残す |
| AI 独立画面 | ナビ「AI分析」3項目（現場選択・利用状況・実行ログ）。個別機能は現場・原価・工期の詳細画面から既にリンクされている | ナビから外しても個別機能には到達できる |
| 人事評価（`apps/evaluation`） | 評価者割当 `EvaluatorTarget` は**名前テキストの組のみで、どこからも参照されていない** | 移植は「名前 → 作業員 FK」への作り直しになる |
| 営業（`apps/sales`） | `SalesVisit` 1モデル。取引先マスタとの FK なし。他アプリから参照なし | 業者名鑑への移設は独立して行える |
| ダッシュボード | 5種（トップ / 入札 / 営業 / AI利用状況 / 書類アラート） | — |

### 3.4 案件の背骨（Phase 1 の前提）

- `EstimationProject` は `site` と `bid_project` への FK を持つ。`Site` から入札・積算への逆 FK はない
- 入札の「落札」で `Site(code=BID-<pk>)`、「積算開始」で別の `Site(code=EST-<pk>)` が作られ、**同じ入札から Site が2つできうる**。どちらも入札との FK を保存しない
- このままでは案件統合ビューで入札と現場を確実に束ねられない（→ 未決事項 D6）

### 3.5 日報

| | DailyReport（reports） | AttendEntry（attendance） |
|---|---|---|
| 現場 | Site FK | 文字列 |
| 工種 | WorkType FK（必須） | なし |
| 時刻 | TimeField | CharField |
| 休憩・早出 | なし（8時間超で一律60分を計算で控除） | `break_minutes` / `early_minutes` |
| 承認 | status + approved_by + approved_at | 状態のみ |

作業中の ADR-0024 は勤怠日報の入力画面を廃止し、DailyReport に一本化する方針（→ 未決事項 D3）。

## 4. Phase 0 の要求と受け入れ基準

### 4.1 アクセスリスト方式への統合（v2.0 §4 / Phase 0-1）

**要求**: 機能ごとに「使える人」「承認できる人」のリストを1系統で持ち、メニュー・タブ・URL の判定をすべてそこから行う。

受け入れ基準:
- AC-1: アプリキーの語彙が1つの定義（レジストリ）にまとまり、ミドルウェア・ナビ・管理画面が同じ定義を参照する
- AC-2: `has_app_access(user, app_key)` と `can_approve(user, app_key)` がサービス層にあり、テンプレートフィルタとビューデコレータから同じ関数を呼ぶ
- AC-3: リストに入っていない機能は、ナビに出ず、URL を直接開くと 403 になる（メニューに出るのに押すと 403、をなくす）
- AC-4: 管理画面で「機能 × 社員」のチェック表を編集でき、「既存社員の設定をコピー」「全解除」ができる
- AC-5: 切り替えの前後で、本番の各社員が使える機能が変わらない（移行データで現状を再現する。変える場合は PR 説明に人数と氏名コードで明記）
- AC-6: 切り替え後、`CostAccessGrant`・G 始まり特例・`POSITION_RESTRICTED_APPS`・`allowed_apps` の判定コードが残っていない（テーブルは contract まで残す）
- AC-7: 越境テスト（他社の AppAccess で自社の機能が開かない）

PR 分割:
1. expand: レジストリ + `AppAccess` モデル（history / admin / 越境テスト / マイグレーション）+ `has_app_access`。**判定にはまだ使わない**
2. データ移行: 現状の実効権限（D2 で決めた内容）を AppAccess に投入するデータマイグレーション
3. 切り替え: ミドルウェア・ナビ・原価ビュー・人事評価の判定を `has_app_access` へ
4. 管理画面: 機能 × 社員のチェック表、コピー、全解除
5. contract: 旧判定コードの削除 → 次リリースで旧テーブル削除

### 4.2 評価の workers 一本化（v1.1 決定① / Phase 0-2）

**要求**: 人材評価を workers 側だけにし、評価者割当を workers 側で実際に効く形で持つ。

受け入れ基準:
- AC-1: 評価者 → 対象者の割当を作業員 FK で登録できる（名前の揺れで割当が外れない）
- AC-2: 割当のある評価者は、割当された対象者だけを評価対象に選べる（割当のない評価者の扱いは D4）
- AC-3: `apps/evaluation` は閲覧のみ（新規作成・編集・削除の導線と URL を閉じる）
- AC-4: ナビの人事評価3項目を撤去し「人材評価」1項目にする
- AC-5: 既存 `EvaluatorTarget` のうち作業員名と一致するものは FK の割当へ移す。一致しないものは件数を移行ログに出す

PR 分割:
1. expand: `workers.EvaluatorAssignment`（history / admin / 越境テスト / マイグレーション）。判定にはまだ使わない
2. 切り替え: 対象者を返すサービス関数（D4 の規則をここに書く）を作り、評価開始画面と `eval_targets_api` から呼ぶ + 割当の管理画面
3. データ移行: `EvaluatorTarget` → `EvaluatorAssignment`
4. 閲覧専用化: evaluation の書き込み導線を閉じ、ナビを1項目に

### 4.3 統合日報（v2.0 §8 / Phase 0-3）

**要求**: 作業内容と出退勤を1人1日1回の入力で済ませ、承認1回で両方を確定させる。

受け入れ基準（D3 の結論によって PR 分割が変わるため、基準のみ先に定める）:
- AC-1: スマホ 375px で、現場・工種・作業内容・開始/終了・休憩を1画面で入力して提出できる
- AC-2: 承認は承認者リスト（4.1）に入っている人だけが行え、承認で労務費の原価計上と勤怠集計の両方に反映される
- AC-3: 月次の勤怠集計（出勤日数・通常・残業・合計）は統合日報だけから出る
- AC-4: 休憩時間を実績として持ち、「8時間超で一律60分」の固定控除に頼らない
- AC-5: 過去の勤怠日報データは参照専用で残る

### 4.4 廃止機能の畳み込み（v2.0 §5・§7・§9 / Phase 0-4）

受け入れ基準:
- AC-1: ナビから「AI分析」グループがなくなり、AI の利用状況・実行ログは「設定」の中から開ける
- AC-2: 現場・原価・工期の詳細画面から AI の個別機能（工程提案・費用最適化など）に引き続き到達できる
- AC-3: 在庫・調達実績の画面と URL がなくなる。テーブルとデータは残り、検収時の自動記録（発注・仕入先の紐づけに使う）は動き続ける
- AC-4: ダッシュボードの統合はホームの KPI 選定（D8）が決まってから Phase 1 で行う（Phase 0 では導線のみ）

PR 分割:
1. ナビ: AI分析グループの撤去と「設定 > AI利用状況・AI実行ログ」への移設
2. 材料: 在庫・調達実績の画面・URL・テンプレート撤去
