# 電機屋 業務管理アプリ — TM向け Q&A集

**目的**: TMから想定される質問と、その回答を事前に準備する
**作成日**: 2026-08-03

---

## カテゴリ別 質問一覧

### A. 全般的な質問

---

**Q1. なぜ既存のSaaS（ANDPAD、現場Plus等）を使わないのか？**

**A.** 3つの理由があります。

1. **カスタマイズ性**: SaaSは汎用的に作られているため、「KY未記入アラート」「AI見積もり」「Discord連携」のような独自機能が追加できない
2. **コスト**: ANDPAD等は月額¥30,000〜100,000+。自社開発なら月額¥6,000〜17,000で、機能は自社の業務に完全にフィット
3. **データ主権**: SaaSだと入札金額や原価などの機密データが外部サーバーに保存される。自社開発ならデータは完全に自社管理

ただし、自社開発には「開発・保守のコスト（人的リソース）」がかかるトレードオフがあります。

---

**Q2. このアプリはいつ完成するのか？**

**A.** 段階的にリリースします。一度に全部作るのではなく、優先度の高いモジュールから順に使えるようにします。

| フェーズ | 対象 | 目安 |
|---------|------|------|
| Phase 1 | 日報管理 + 人材管理 + ユーザー管理 | 最優先（日々の業務の基盤） |
| Phase 2 | 工期管理 + 原価管理 | 日報データが溜まってから活きる |
| Phase 3 | 材料管理 + 取引先管理 | 発注業務の効率化 |
| Phase 4 | 入札管理 + AI機能 | データ蓄積後にAIが機能する |

---

**Q3. もし開発者がいなくなったら、このアプリはどうなる？**

**A.** 以下の対策を取っています。

- **一般的な技術スタック**: Next.js + TypeScript + PostgreSQL は世界で最も使われている組み合わせの一つ。代わりの開発者を見つけやすい
- **ドキュメント整備**: 要件定義書、DB設計書、技術選定書、画面設計書を全て残している
- **Docker化**: `docker compose up` の1コマンドで開発環境が再現可能。引き継ぎ時の環境構築コストが最小
- **コード上の型定義**: TypeScriptの型がドキュメントの役割を果たす

---

**Q4. セキュリティは大丈夫？**

**A.** 以下の対策を実装します。

| 脅威 | 対策 |
|------|------|
| パスワード漏洩 | bcryptハッシュ化（元のパスワードは保存しない） |
| 不正ログイン | セッション管理（NextAuth.js）、ログイン試行回数制限 |
| データ盗聴 | HTTPS通信（Tailscale が自動発行するSSL証明書） |
| 権限超越 | ロールベースアクセス制御（原価は社長＋指名者のみ等） |
| SQLインジェクション | Prisma ORM（パラメータ化クエリが標準） |
| XSS | React（自動エスケープ）+ Content Security Policy |
| データバックアップ | PostgreSQLの定期バックアップ（日次） |

---

**Q5. スマホでちゃんと使えるの？ アプリのダウンロードは必要？**

**A.** ダウンロード不要です。スマホのブラウザでURLを開くだけで使えます。

- 「ホーム画面に追加」すると、アプリアイコンが追加されて普通のアプリのように起動可能
- iPhone（Safari）、Android（Chrome）の両方に対応
- アプリストアの審査が不要なので、アップデートも即時反映

### B. DB設計に関する質問

---

**Q6. データが増えたら遅くならない？**

**A.** 3つの対策で防いでいます。

1. **インデックス**: よく検索するカラムに「目次」を付けている。10万件でも一瞬で検索可能
2. **正規化**: データの重複がないため、ストレージを無駄に消費しない
3. **PostgreSQL**: 数百万〜数千万レコードまで問題なくスケールする実績あり

目安: 現場20件 × 作業員20人 × 365日 = 年間14.6万レコード。10年でも146万レコード。PostgreSQLの性能限界（数億レコード）にはまだ遠い。

---

**Q7. テーブル間の「FK（外部キー）」って何？**

**A.** 「このデータは、あのテーブルのデータと繋がっているよ」という関連づけです。

Excelで例えると:
```
シート1「日報」: 現場名をいちいち手入力 → 「A現場」「Ａ現場」「a現場」が別物に
シート2「日報」: 現場ID（001）を入力 → IDで「現場マスタ」を参照 → 表記ゆれなし
```

外部キー(FK)は「この日報の site_id は sites テーブルに実在するIDじゃないとダメ」というルール。存在しない現場IDを入れようとするとエラーになるので、データの整合性が保たれます。

---

**Q8. バックアップはどうする？**

**A.** 3段階のバックアップ戦略:

| レベル | 方法 | 頻度 | 復旧時間 |
|--------|------|------|---------|
| 日次バックアップ | pg_dump（DBの全データをファイルに出力） | 毎日深夜 | 数分 |
| リアルタイムレプリカ | PostgreSQL Streaming Replication | 常時 | 数秒（切替のみ） |
| 災害対策 | 別拠点へのバックアップ転送 | 日次 | 数時間 |

最初はPhase 1（日次バックアップ）から始め、データが重要になってきたら段階的に強化します。

### C. 技術選定に関する質問

---

**Q9. React / Vue / Angular のどれ？ なぜReact（Next.js）？**

**A.** 3つの観点で判断しました。

| 観点 | React (Next.js) | Vue (Nuxt) | Angular |
|------|-----------------|------------|---------|
| 求人市場（＝代替開発者の見つけやすさ） | ◎ 最多 | ○ | △ 減少傾向 |
| エコシステム（使えるライブラリ数） | ◎ 最多 | ○ | ○ |
| フルスタック統合 | ◎ Next.js | ○ Nuxt | △ |
| 学習リソース（日本語含む） | ◎ | ○ | △ |

決め手は「**開発者の交代が最もしやすい**」こと。React/Next.jsは世界で最も使われているフロントエンドフレームワークであり、求人・学習リソースが圧倒的に多い。

---

**Q10. なぜ Docker を使うのか？ 直接サーバーに入れればいい？**

**A.** 直接インストールでも動きますが、以下の問題が起きます。

| 問題 | 直接インストール | Docker |
|------|----------------|--------|
| 「自分のPCでは動くのに」 | 頻発 | 起きない |
| OSアップデートで壊れる | あり得る | コンテナ内は影響なし |
| 別サーバーに移行 | 再セットアップ（半日〜1日） | `docker compose up`（5分） |
| PostgreSQL + Redis + MinIO + Ollama 4つの同時管理 | 地獄 | 1コマンドで全部起動 |

---

**Q11. Redis って何のために使うの？**

**A.** 2つの用途があります。

1. **ジョブキュー**: 「アラート通知を送る」「スクレイピングする」等の非同期タスクを管理する待ち行列
2. **キャッシュ**: よくアクセスするデータ（ログインセッション等）をメモリに保持して高速化

PostgreSQL（メインDB）がハードディスクにデータを保存するのに対し、Redis はメモリ（RAM）にデータを保存するので、読み書きが数百倍速い。ただし電源を切るとデータが消えるので、消えても再生成できるデータのみ保存します。

---

**Q12. Ollama って何？ なぜローカルAIが必要？**

**A.** OllamaはAIモデルを自分のパソコンやサーバーで動かすためのツールです。

ChatGPTやClaudeは「クラウド（外部サーバー）」でAIを動かしますが、以下のリスクがあります:
- 入札金額や原価データ（機密情報）が外部に送信される
- API料金が値上げされる可能性（過去に実際に値上げあり）
- インターネット接続がないと使えない

Ollamaなら:
- データは一切外部に出ない（全て自社サーバー内で処理）
- 月額料金ゼロ（電気代のみ）
- オフラインでも動作

### D. 画面設計に関する質問

---

**Q13. 現場の作業員にITリテラシーが低い人がいても使える？**

**A.** はい。以下の工夫をしています。

| 工夫 | 効果 |
|------|------|
| 選択式の入力（プルダウン） | 手入力を最小限に |
| AI入力補助（写真/テキスト） | 写真を撮るだけで日報が半自動作成 |
| 大きなボタン・タップ領域 | 手袋をしていても操作可能 |
| 最小限の画面遷移 | 迷子にならない |
| 色分け（緑=OK、黄=注意、赤=警告） | 文字を読まなくても状態がわかる |

---

**Q14. 画面のデザインは後から変えられる？**

**A.** はい。技術選定で shadcn/ui（コピペ方式のUIライブラリ）を採用しているため、色・フォント・レイアウトは自由に変更可能です。

- 色の変更: CSS変数を1箇所変えるだけで全体に反映
- レイアウト変更: コンポーネント単位で差し替え可能
- ダークモード対応: CSS変数の切替で将来対応可能

---

**Q15. 通知が多すぎてうるさくならない？**

**A.** 通知設定画面で、ユーザーごとに「どの通知を受け取るか」を選べるようにします。

例:
- 社長: 全通知ON
- 現場担当者: 日報・工期の通知のみ
- 事務員: 材料の納品通知のみ

また、アラートの重要度に応じて通知方法を変えます:
- 通常: アプリ内通知のみ
- 重要: アプリ + メール
- 緊急（予算超過レッド等）: アプリ + メール + 音声通知

### E. コスト・運用に関する質問

---

**Q16. SaaSと比べてトータルコストは？**

**A.** 3年間の比較:

| 項目 | SaaS (ANDPAD等) | 自社開発 |
|------|-----------------|---------|
| 初期費用 | ¥0〜50万 | 開発者の工数 |
| 月額 (20ユーザー) | ¥50,000〜100,000 | ¥6,000〜17,000 |
| 3年間合計 | ¥180万〜410万 | ¥22万〜61万 + 開発工数 |
| カスタマイズ | × or 高額 | ○ 自由 |
| データ移行 | ベンダー依存 | 自由 |
| サービス終了リスク | あり | なし（自社管理） |

---

**Q17. サーバーが落ちたらどうする？**

**A.** 以下の対策を段階的に実装します。

| 段階 | 対策 | ダウンタイム |
|------|------|------------|
| 初期 | Uptime Kumaで死活監視、異常時にメール/Discord通知 | 手動復旧（数十分〜） |
| 中期 | Docker自動再起動（restart: always） | 自動復旧（数秒〜数分） |
| 将来 | 冗長構成（サーバー2台以上） | ほぼゼロダウンタイム |

現実的には、初期段階では「通知が来たら手動で対応」で十分です。24時間365日止められないシステムではないため。

---

**Q18. 将来ユーザーが100人、1000人に増えたら？**

**A.** 現在の設計で段階的にスケール可能です。

| 規模 | 対応 |
|------|------|
| 〜50人 | VPS 1台で十分 |
| 50〜200人 | VPSのスペックアップ（CPU/メモリ増設） |
| 200〜1000人 | アプリサーバーとDBサーバーを分離 |
| 1000人〜 | ロードバランサー + 複数アプリサーバー |

ただし電気工事会社で1000人規模は大企業なので、当面は50人以下を想定した設計で問題ありません。

### F. 開発プロセスに関する質問

---

**Q19. バグが出たらどう対応する？**

**A.** 以下のフローで対応します。

```
バグ発見
  ↓
GitHub Issue に登録（開発管理モジュールと連携）
  ↓
優先度を判定（urgent/high/medium/low）
  ↓
開発者にDiscord通知
  ↓
修正 → テスト → PR作成 → レビュー → マージ
  ↓
自動デプロイ（GitHub Actions）
  ↓
修正完了
```

緊急度の目安:
- **urgent**: データが消える、ログインできない → 即日対応
- **high**: 計算結果が間違っている → 1〜2日以内
- **medium**: 表示崩れ、操作性の問題 → 1週間以内
- **low**: 改善要望、デザイン調整 → 次回リリースで対応

---

**Q20. テストはどうやるの？**

**A.** 3種類のテストを組み合わせます。

| テスト種類 | 内容 | タイミング |
|-----------|------|----------|
| 単体テスト | 個々の関数が正しく動くか | コード変更のたび |
| 統合テスト | モジュール間の連携が正しいか | PR作成時に自動実行 |
| E2Eテスト | 実際の画面操作で期待通り動くか | リリース前 |

例: 日報保存時に原価が自動計算されるか → 統合テストで毎回確認
