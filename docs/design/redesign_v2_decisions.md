## D1. アクセス管理の方式

### 事実

権限の仕組みが4つ並存し、どれも一部しか効いていない。

| 仕組み | 実際に効いている範囲 |
|---|---|
| ロール（社長・役員・現場担当…の6種） | **本番に0件**。ロールで判定する画面は superuser（＝ログイン時に superuser 化される社長）以外に閉じている |
| 役職による制限（ADR-0022） | 人事評価だけ。社長・役員・Developer の8人 |
| 個人ごとのアプリ許可（`allowed_apps`） | 全員が空リスト＝無制限。設定すると通知・設定・営業が 403 になる不具合あり |
| 原価の特別ルール | 社員番号（ログインID）が **G で始まる人** ＋ 個別に付与した人（`/costs/access/`） |

その結果、今は次のことが起きている。

- **メニューに出るのに押すと 403** になる画面がある: 書類アラート（Y 始まり以外）、権限管理・変更ログ（社長以外）、原価（G 始まり・付与者以外）
- **役員は原価を見られない**（ロールが0件のため。個別付与していれば見られる）
- 日報を**承認できるのは実質社長だけ**

### 選択肢

| | (a) 機能別の利用者リストに一本化（v2.0 §4） | (b) 役職を軸にし、例外だけ個人で足す | (c) ロールを本番に投入して使う |
|---|---|---|---|
| 管理画面 | 「機能 × 社員」のチェック表 | 「役職 × 機能」の表 ＋ 個人の例外 | 「ロール × 機能」の表 ＋ 社員へのロール付与 |
| 入社・異動 | 既存社員の設定をコピー | 役職を設定すれば自動 | ロールを付与 |
| 見える化 | 誰が何を使えるか1画面で分かる | 役職の表と例外の2か所を見る | ロール表と付与の2か所を見る |
| 例外（「Aさんだけ原価を見せる」） | チェックを入れるだけ | 例外リストに追加 | 専用ロールを作るか個別付与 |
| 実装の手間 | 中（新モデル＋データ移行） | 小（ADR-0022 の延長） | 中（22人へのロール付与作業） |

### 推奨: (a)

仕様書 v2.0 の決定⑧どおり。22人規模なら「表で全員分が見える」ことの価値が大きく、
役職ルール（ADR-0022）や G 始まり特例は「初期データ」として表に展開できる。

### 決まると進むこと

レジストリ＋AppAccess の追加 → 移行データ → メニュー・画面の判定切り替え → チェック表の管理画面 → 旧4系統の削除（5 PR）

## D2. 切り替え時に誰へ何を開けるか

### 事実

切り替えの日に「使える機能」が変わると、問い合わせと混乱が起きる。今の実効権限は次のとおり。

| 機能 | 今使える人 |
|---|---|
| 人事評価（`/evaluation/`） | 社長・役員・Developer（8人） |
| 原価 | 社長、G 始まりの社員（Developer 3人と思われる）、`/costs/access/` で付与した人 |
| 日報の承認 | 社長 |
| 権限管理・変更ログ | 社長 |
| 書類アラート | Y 始まり（管理者）・社長 |
| それ以外すべて | 全員 |

### 確認が必要

- `/costs/access/`（原価の閲覧権限）に**誰が登録されているか**
- 役員が原価を見られないのは**意図どおりか**

### 選択肢

| | (a) 今の実効権限をそのまま再現して切り替える | (b) 切り替えと同時に、ロール想定で絞る |
|---|---|---|
| 切り替え当日の変化 | なし | 一部の人のメニューが減る |
| リスク | 小。権限の見直しは表を見ながら後で | 「急に使えなくなった」問い合わせ |

### 推奨: (a)、そのうえで役員の原価閲覧だけ先に決める

切り替えと権限の縮小・拡大を同じリリースに混ぜない。

## D6. 入札・積算・現場を1つの案件として束ねる方法

### 事実

- 入札で「落札」を押すと現場（コード `BID-番号`）が作られ、「積算開始」を押すと**別の**現場（`EST-番号`）が作られる。**同じ入札から現場が2つできうる**
- どちらの場合も、入札と現場の結び付きは保存されない（現場側に入札への参照がない）
- 積算案件は現場と入札の両方への参照を持つ
- 原価・日報・工程・発注はすべて「現場」に紐づく

つまり、今のデータのままでは「この入札の現場はどれか」を確実に辿れない。

### 選択肢

| | (a) 現場を案件の中心にし、入札から現場への参照を保存する | (b) 「案件」モデルを新設し、入札・積算・現場がそこを参照する |
|---|---|---|
| 変更の大きさ | 小（入札に1項目追加、落札・積算開始で同じ現場を使う） | 大（新モデル＋全データの紐付け移行） |
| 受注前の商談（民間） | 「見積中」の現場として持つ | 案件として持てる |
| 1案件に現場が複数ある工事 | 表現しにくい | 表現できる |

### 確認が必要

- **1つの受注で現場を複数に分けることがあるか**（あるなら (b) 寄り）
- 本番に `BID-` と `EST-` の現場が重複している案件がどれくらいあるか

### 推奨: (a) を先に

現場は既に「全業務データの起点」として設計されている（`Site` の説明）。二重作成を止め、
入札→現場の参照を保存するだけで案件詳細ページの大半が作れる。複数現場が必要になったら (b) へ。

### 決まると進むこと

二重作成の解消 → 案件一覧 → 案件詳細（概要 / 入札 / 積算 / 工程 / 日報 / 材料 / 原価 のタブ）

## D8. ホームに何を載せるか

### 事実: 今の5つのダッシュボードの中身

| ダッシュボード | 載っているもの |
|---|---|
| トップ | 施工中の現場数・本日の日報数・承認待ち日報数・作業員数、施工中の現場（**受注金額付き**）、最近の日報 |
| 入札 | 全案件数・受注率・落札数・受注金額合計、月別件数グラフ、地域別件数 |
| 営業 | 総訪問件数・今月の訪問・要対応件数、業種別・状態別分布、最近の訪問 |
| AI利用状況 | 今月のAI費用と予算、評価の平均、タスク別・月別の利用 |
| 書類アラート | 健診期限が2か月以内の人、証明書・健診報告書が未添付の人 |

気になる点:

- トップの「受注金額」は**原価を見られない人にも表示されている**
- 「受注金額」という言葉が、トップ（現場の契約金額）と入札（落札額の合計）で別の意味

### ホームの候補（コードに既に計算の仕組みがあるもの）

| 候補 | 誰向け | 備考 |
|---|---|---|
| 承認待ち日報の件数 | 承認者 | 既存 |
| 原価の予算消化率が高い現場（75/80/90/100%） | 原価を見られる人 | 原価一覧の計算を流用 |
| 入札期限が近い案件 | 入札担当 | D9 の不具合修正（#101）が前提 |
| 資格の期限切れが近い人（90日以内） | 事務・管理者 | 既存の関数あり、どの画面にも未掲載 |
| 健診期限・書類未添付 | 事務・管理者 | 書類アラートから移す |
| 名寄せレビュー待ち・下書きの積算マスタ | 積算担当 | 件数を数える処理は未実装 |
| 施工中の現場（今週の工程） | 現場担当 | 現場モードのホームと共通 |

### 決めること

1. 上の候補から載せるもの（ロールによって出し分けるか）
2. 受注金額などの金額を、原価を見られない人のホームに出すか

### 推奨

「自分が今日やること」を上に（承認待ち・期限が近いもの）、「会社の状況」を下に（施工中の現場、消化率の高い現場）。
**金額は原価を見られる人にだけ出す。**

## D3. 統合日報の休憩・早出・承認

### 事実

- 勤怠日報は #98 で廃止し、実績は日報（`DailyReport`）に一本化した
- 日報の休憩は「**8時間を超えたら一律60分を差し引く**」計算で、休憩時間を入力する欄はない。早出の欄もない
- **承認されるまで、労務費は原価に入らず、月次サマリ（勤怠集計）にも出ない**
- 承認できるのは実質社長だけ（D1）
- 初期の要件定義書（2026-08）では「承認は任意（しなくてもよい）」とされていた

つまり、社長が承認しない月は、原価の労務費と勤怠集計が空になる。

### 決めること

| 論点 | 選択肢 |
|---|---|
| 休憩 | (a) 一律控除のまま (b) 休憩時間を入力する欄を足す（未入力なら一律控除） |
| 早出 | (a) 扱わない (b) 早出の時間を持つ（手当計算に使うなら必要） |
| 承認 | (a) 承認必須のまま、承認者を増やす（D1 の「承認できる人」リスト） (b) 提出した時点で集計・原価に入れ、承認は確認記録にする |

### 推奨

休憩 (b)、承認 (a)。原価に入る金額は誰かが確認した後であるべきなので承認は残し、承認者を社長以外にも広げる。
早出は給与計算での使い方次第（手当があるなら (b)）。

## D9. 通知を自動で出すか

### 事実

- アラートルールの種類は8つ（原価閾値・資格期限・工期遅延・入札期限・安全書類未記入・証明書未添付・健診報告書未添付・健診期限）
- **定期実行されているのは書類系の3つだけ**（証明書・健診報告書・健診期限）
- 原価・工期・入札期限のチェックは、状態の判定が間違っていて常に0件だった（#101 で修正予定。修正しても定期実行していないので通知は増えない）
- 資格期限のチェックは判定は正しいが、定期実行されていない
- 通知先はロールで指定する設計だが、ロールが本番に0件のため、**指定すると誰にも届かず、指定しないと全社員に届く**

### 決めること

1. どの通知を自動で出すか（原価超過 / 工期終了が近い / 入札期限が近い / 資格期限）
2. 誰に届けるか（D1 のリストで「この機能を使える人」に届ける、が自然）
3. 実行の頻度（1日1回の朝など）

### 推奨

D1 の切り替え後に、原価超過と入札期限から始める。通知先がロール頼みのまま動かすと全社員に届くため、D1 より先には動かさない。

## D4. 評価者割当が0件の評価者

### 事実

- 評価者割当を作業員単位で持つ仕組みを追加済み（#97）。まだ画面の絞り込みには使っていない
- 旧人事評価の割当データ（名前の組）が本番に何件あるかは確認が必要

### 選択肢

| | (a) 割当があれば絞る／0件なら今までどおり全員 | (b) 割当が無ければ誰も選べない |
|---|---|---|
| 切り替え当日 | 何も変わらない | 割当を登録するまで評価が止まる |
| 最終形 | 割当の登録漏れに気づきにくい | 割当が正しく管理される |

### 推奨: (a) で始め、全員の割当登録が終わったら (b) に変える

## D5. 人材評価の評価者

### 事実

評価開始画面で「評価者」を選べるが、保存されるのは**ログインしている人**。
「評価済み」の判定もログイン者で行っている。

### 確認が必要

事務員などが、他の人の代わりに評価を入力する運用があるか。

### 選択肢

| | (a) 代理入力を想定した仕様として残す | (b) 選んだ評価者で保存する（入力者は別に記録） |
|---|---|---|
| 代理入力 | できる（ただし評価者名が入力者になる） | できる（評価者名が正しく残る） |

### 推奨: (b)

どちらの運用でも、評価票に残る評価者名が正しくなる。

## D10. 在庫・調達実績の自動記録

### 事実

在庫一覧・調達実績の画面は撤去した（#96）が、検収するたびに在庫数の加算と調達実績の作成は続いている。
調達実績の作成は、材料ごとの仕入先とリードタイムの更新と同じ処理の中にある。

### 選択肢

(a) このまま溜める（将来の見積比較や取り込み基盤の実績データに使える） / (b) 止める

### 推奨: (a)

害は小さく、止めると発注側の仕入先情報の更新を切り分ける改修が要る。
