# クラウドDB移行計画（ベンダー選定まで）

DB とアップロードファイルをクラウドへ移すための、**ベンダーを決めるまでの手順と比較の材料**をまとめる。
方針は [ADR-0044](../saas/adr/ADR-0044-cloud-database-and-file-storage.md)、AI は [ADR-0042](../saas/adr/ADR-0042-local-ai-for-planning-and-optimization.md)。

---

## 1. 決まったこと（2026-09-11 プロダクトオーナー）

| # | 決定 |
|---|---|
| C1 | アプリ（Django・cron・Redis）と社内AI（Ollama）は**社内PCに残す** |
| C2 | **DB はまるごと**クラウドのマネージド PostgreSQL へ移す（日報も含め、分割しない） |
| C3 | **アップロードファイル**（現場の画像・資格証・健康診断の結果など）はクラウドのオブジェクトストレージへ移す |
| C4 | 工程提案・予算とリソースの最適化は**社内のローカルAI**で行う（社外のAI APIに実績データを送らない） |
| C5 | ネットが切れたときは **(c) 日報などの入力だけ社内PCに一時保存し、復旧後にクラウドへ送る**。詳しい仕様は別途決める（8章 O6） |
| C6 | 月額予算の上限は **とりあえず ¥1,000**（DB とファイル保存の合計）。必須要件と両立するかは 8章 O7 |
| C7 | 利用者は**社内だけでなく外部からも**アプリを使う（Tailscale 経由で社内PCのアプリへ） |
| C8 | 本番移行で止めてよい時間は **3時間**（深夜ならもう少し延ばせる） |

DB を分割しない理由: 日報は作業員（個人情報・時給）と現場（受注金額）を参照し、承認と同時に労務費を作る。
DB をまたぐとこのつながりと「同時に保存」が保てず、作り直しが大きい（ADR-0044）。

## 4. 棚卸し（サーバーPCで実行）

本番のリポジトリの `saas/` で実行する（`docs/server_operations.md` の手動バックアップと同じ場所）。どれも読み取りだけで、データは変えない。

```bash
# DB 全体の容量
docker compose exec -T db psql -U postgres -d kensetsu_saas -c "select pg_size_pretty(pg_database_size('kensetsu_saas'));"

# 大きいテーブル上位15
docker compose exec -T db psql -U postgres -d kensetsu_saas -c "select relname, pg_size_pretty(pg_total_relation_size(relid)) as size from pg_statio_user_tables order by pg_total_relation_size(relid) desc limit 15;"

# アップロードファイルの容量と件数
docker compose exec -T web sh -c 'du -sh /app/media; find /app/media -type f | wc -l'

# バックアップの大きさの推移（増え方の目安）
ls -lh /d/backup/kem_ddenki | tail -30
```

| 項目 | 値 | 備考 |
|---|---|---|
| DB 容量 | | |
| 大きいテーブル上位 | | |
| ファイル容量 / 件数 | | |
| 月あたりの増え方（DB / ファイル） | | バックアップの推移から |
| 利用者数 / 同時に使う人数 | | |
| 会社の回線は固定IPか | | 接続元の制限方法が変わる（O3） |

## 7. 試験移行（開発環境）

本番のデータは使わず、**開発環境のスタック**（`:8443` / `127.0.0.1:8001`）の DB とファイル保存先だけを候補のクラウドに向けて測る。

| 測ること | 方法 | 合格の目安（案・要合意） |
|---|---|---|
| 主要画面の表示時間 | ホーム・日報一覧・出社予定の月表・原価の画面を、移行前後で比べる | 2秒以内 |
| 画像のアップロードと表示 | 資格証の画像を登録・表示 | 体感で遅くない |
| 社内AIの処理時間 | 工程提案を1件実行 | 移行前と大差ない |
| バックアップから復元 | クラウドの復元機能で別DBに戻して件数を確かめる | 手順どおり戻る |
| ネットが切れたとき | 社内PCのネットを切って画面を開く | O1 の方向どおりの振る舞い |

試験移行のために必要なコード変更（別PR）:

- DB 接続の TLS 必須化と接続の再利用
- ファイル保存先の切り替え（S3 互換の保存ライブラリを追加。依存の追加は ADR が必要）
- 表示が遅い画面の問い合わせを減らす

### O3 の補足（固定IPでない場合）

| 方法 | 内容 | 注意 |
|---|---|---|
| IP 許可リスト | 社内PCの回線の固定IPだけを許可 | 固定IPの契約が要る（プロバイダのオプション） |
| 接続元を絞らず、TLS と強いパスワードだけで守る | どこからでも接続を試せる状態 | 必須要件「接続元の制限」を満たさない |
| クラウド側に中継役を置く | 小さな仮想サーバーに Tailscale を入れ、そこ経由で DB につなぐ | 月額が増える |

### O4 の補足

3時間止められれば、「アプリを止める → `pg_dump` でDBを書き出す → クラウドへ取り込む → ファイルを転送 → 接続先を切り替えて確認」の単純な方式で移せる見込み（4章の棚卸しでDB・ファイルの容量を確かめてから確定）。本番の前に開発環境で同じ手順をリハーサルする。

### O1 の選択肢

| 案 | 内容 | 作りの大きさ | 注意 |
|---|---|---|---|
| a | ネットが切れたら止まる | なし | 最も簡単。回線の冗長化（予備回線など）で止まりにくくする手もある |
| b | 閲覧だけ社内の写しで続ける | 中 | 社内PCに写しが残り、「データを社内に置かない」目的と一部ぶつかる |
| c | 日報など入力だけ社内に一時保存し、復旧後にクラウドへ送る | 大 | 同じデータを2か所で直したときの食い違いの扱いが要る |
| d | 社内を主にしてクラウドへ同期する | 大 | 目的（データをクラウドに置く）と逆向き。論理レプリケーションが要る |

見積依頼の前に、少なくとも「a で始めて後から c を足すか」など方向だけ決めたい。
