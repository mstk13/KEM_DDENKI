対象リポジトリ: mstk13/KEM_DDENKI（saas/ 配下）
版: v2.0（確定） 更新日: 2026-09-06
位置づけ: v1.1（フロントエンド再設計仕様書）を拡張し、全機能の棚卸しに基づくゼロベース構成へ改訂。v1.1 の決定（全画面レスポンシブ・htmx+Alpine.js・評価の workers 一本化・現場モード）はすべて継承する。

## 1. 再設計の中核方針

1. **「案件」を背骨にする**: 1つの工事案件（商談/入札 → 積算 → 施工 → 原価締め）を1つの案件ページで追えるようにする。入札・積算・工程・原価は独立メニューから外し、案件詳細のタブになる。DB の作り直しは行わず、既存の bids.Project / estimation.Project / sites.Site / costs を案件で紐づけた統合ビューを被せる（落札→現場登録の既存連携を土台にする）。
2. **業務ナビは6項目**: ホーム / 案件 / 日々の記録 / 材料・発注 / ヒト / マスタ。設定・開発は同一インターフェース内に置くが、アクセスリスト該当者にのみ表示する。
3. **アクセス管理は「機能ごとの利用者リスト」1系統**: 権限マトリクス・Worker.allowed_apps・CostAccessGrant（社員番号G特例含む）を廃止し、リスト方式に統合する（§4）。
4. **取り込み基盤（インテーク）を共通部品にする**: 紙（写真）・PDF・Excel をシステムに読み込む口を、見積・積算・納品書で共通のパイプラインとして設計する（§6）。
5. **AI は独立画面を廃止し、案件に埋め込む**: 注力機能は「工程提案」「費用最適化」「作業員配置の最適化」の3つ（§7）。

## 2. 画面構成

### 2.1 業務ナビゲーション（6項目）

```
🏠 ホーム          ロール別に1つだけのダッシュボード（既存5種を統合）
📋 案件            一覧（ステータス: 受注前[商談/入札] → 積算中 → 施工中 → 完了・締め）
                   案件詳細 = タブ: 概要 / 商談・入札 / 積算・内訳書 / 工程 / 日報 / 材料 / 原価 / AI分析
📝 日々の記録      統合日報（§8）・安全確認
📦 材料・発注      発注書・納品検収（写真取り込み対応）・見積取り込み比較
👥 ヒト            作業員個人ページ（資格・健康・書類アラート・評価を集約）
📚 マスタ          取引先 / 業者名鑑（来訪営業記録）/ 品目・単価・歩掛 / 工種
――――――――――（アクセスリスト該当者のみ表示）
⚙️ 設定            アクセス管理 / 通知 / AI利用状況 / 変更ログ
💻 開発            開発管理 / 目安箱の対応（投稿は全員可・業務側に投稿口を残す）
```

### 2.2 案件詳細のタブと権限

タブの表示はアクセスリストに連動する。閲覧権のないタブは表示自体されない（例: 現場担当者には工程・日報・材料タブのみ表示。原価タブは対象者のみ）。

### 2.3 現場モード（v1.1 継承）

スマホの下部タブ4項目（ホーム / 日報 / 勤怠打刻 / 通知）。担当案件から今週の工程・マイルストーンを読み取り専用で確認できる。全画面レスポンシブが大前提であり、モードはデフォルトの入り口の違いにすぎない（v1.1 決定④）。

## 3. 営業機能の分割（決定①）

- **来訪営業の記録（現 SalesVisit）** → 「マスタ > 業者名鑑」へ移設。売り込みに来た業者の業種・サービス・資料を蓄積する台帳。モデルは現行をほぼ流用。
- **こちらから行う営業・商談進捗** → 案件の「受注前」ステータスとして新設。案件に紐づく商談記録（訪問メモ・進捗・次アクション）を軽量モデルで追加する。商談が受注に育てば同じ案件ページのまま積算・施工へ進む。民間（商談）と公共（入札）が同じ背骨に乗る。

## 4. アクセス管理: 機能別利用者リスト（決定⑦を含む）

- 各機能に「使える人」リストを1本持つ。入っていない機能はメニューにもタブにも表示されない。
- 承認が絡む機能（日報承認・原価承認）のみ「承認できる人」リストを追加する。
- 「担当案件のみ」「自分の分のみ」の範囲制限は、リスト（入口）とは別の範囲ルールとして維持する。
- 管理画面は「機能 × 社員」のチェック表。縦=この機能を使える人、横=この人が使える機能が1画面で分かる。
- 入社時は「既存社員の設定をコピー」で一括登録、退職時はワンクリック全解除。
- **廃止して統合するもの**: permissions の ModulePermission マトリクス / Worker.allowed_apps（正式な仕組みに昇格・改修して本体化）/ costs.CostAccessGrant / 「社員番号がGで始まる」ハードコード特例。
- 実装は Worker.allowed_apps を原型に正規化（AppAccess モデル: worker × app_key × can_approve）し、`has_app_access(user, app_key)` をテンプレートタグ・view デコレータ・（将来の）DRF Permission から共用する。

## 5. 材料・発注の整理（決定③）

- **廃止**: 在庫管理（inventory）・調達リスト（procurement）。業務は発注＋納品検収で回っているため畳む（データはアーカイブ、画面と導線を撤去）。
- **強化**: 紙の納品書・受入書類を**写真で取り込んでデータ化**する機能を納品検収に追加（§6 の共通インテークを使用）。現場でスマホ撮影 → AI が品目・数量・金額を読み取り → 確認画面で修正 → 検収データとして登録。

## 6. 共通取り込み基盤（インテーク・パイプライン）

見積・積算・納品書に共通する「外部書類の取り込み」を1つの部品として設計する。

```
[アップロード]      →  [AI解析]              →  [確認・修正画面]        →  [登録]
写真(スマホ撮影)        Claude API             読取結果を並べて表示        対象データとして保存
PDF                    （入札のPDF解析を        人が確認・修正して確定       （見積/BOQ/検収）
Excel                   横展開・共通化）
```

適用先と受け付ける形式:

| 取り込み先 | 形式 | 内容 |
|-----------|------|------|
| 見積比較（材料・発注） | PDF / Excel / 写真 | 紙・Excel で受け取る仕入先見積を読み込み、複数社比較できる形に（決定④） |
| 積算・内訳書（案件） | Excel / PDF | 積算ソフトからの Excel、他社からの PDF を BOQ に取り込む受け口（決定⑤） |
| 納品検収（材料・発注） | 写真 / PDF | 紙の納品書をスマホ撮影してデータ化（決定③） |

設計原則: ①解析結果は必ず人の確認を挟んでから登録する（AI の読み違いを本番データに直行させない） ②取り込み元ファイルを添付として保存し原本に戻れるようにする ③解析は非同期（アップロード後に通知）でも同期でもよいが、現場のスマホ利用では待ち時間を見せる。

## 7. AI 機能の方針（決定②）

- 独立画面（AIダッシュボード・現場選択・独立レポート群）は廃止し、**案件詳細の「AI分析」タブと各タブ内のボタン**に埋め込む。
- 注力する3機能:
  1. **工程提案**: 案件の条件（規模・工種・工期）から工程表のたたき台を提案（既存 schedule suggestion を発展）
  2. **費用最適化**: 予算・実績・仕入単価から原価改善の提案（既存 cost optimization を案件文脈に接続）
  3. **作業員配置の最適化**（新規）: 資格・稼働状況・各案件の工程から、作業員の配置案を提案。ヒト（作業員）と案件（工程）のデータを横断する
- 実行ログ・コスト管理は「設定 > AI利用状況」に集約（管理者向け）。
- 共通インテーク（§6）の AI 解析もこの利用状況に計上する。

## 8. 日報の統合（決定⑥)

作業日報（reports）と勤怠日報（attendance）を**1つの日報**に統合する。

- 入力: 1人1日1レコード。現場・作業内容・安全確認と、出退勤時刻・休憩を同じ画面で入力（現場モードのスマホ入力を最優先で設計）。
- 承認: 1回の承認で作業内容と勤怠の両方が確定する（承認者はアクセスリストの承認者）。
- 集計: 勤怠の個人別・月次サマリは統合日報から自動生成する。既存の勤怠集計画面は出力側として残す。
- 移行: expand/contract で行う。新統合モデルを追加（expand）→ 両画面から新モデルへ書き込む並走期間 → 旧2系統の入力画面を閉じる（contract）。過去データは参照専用で保持。

## 10. 技術方針（v1.1 継承 + 追記)

- 全画面レスポンシブ（PC 1280px / スマホ 375px 双方の表示確認を PR 完了条件に含める）
- Tier 1（CRUD 系）は Django テンプレート + デザインシステム、Tier 2（ガント・原価・名寄せ・カンバン等）は htmx + Alpine.js。ビルドツールは導入せず、ライブラリは static/vendor/ に同梱
- API は /api/v2/（DRF・SessionAuth）。JSON が本質的に必要な箇所に限定し、部分更新は htmx の HTML フラグメントを第一選択
- テナント分離（CompanyScopedManager）・Decimal・simple-history・services 層・expand/contract は CLAUDE.md の規律どおり
- アクセスリストの `has_app_access` はテンプレートタグ / デコレータ / DRF Permission で共用する

## 11. フェーズ計画 v2

### Phase 0: 基盤整理（アクセス・統合・畳み込み）
1. アクセスリスト方式への統合（AppAccess 新設 → ナビ/タブ出し分け → 旧3系統の廃止。G特例の対象者をリストへ移行）
2. 評価の workers 一本化（v1.1 決定の実施）
3. 統合日報の設計とモデル追加（expand。並走はここから開始）
4. 廃止機能の畳み込み（在庫・調達・AI独立画面・ダッシュボード類の導線撤去）

### Phase 1: 情報設計の実装（背骨とナビ）
1. 案件統合ビュー（案件一覧 + 案件詳細タブ。既存4エンティティの紐づけ）
2. 業務6項目ナビ + 設定/開発のリスト表示制御
3. 現場モード（下部タブ + 統合日報のスマホ入力）
4. デザインシステム（トークン + components/ + レスポンシブ基準）
5. 業者名鑑のマスタ移設・商談記録の新設

### Phase 2: 取り込み基盤
1. 共通インテーク・パイプライン（アップロード → AI解析 → 確認 → 登録）の基盤実装
2. 適用第1弾: 積算 Excel/PDF（積算ソフト連携）
3. 適用第2弾: 見積 PDF/Excel/写真 + 比較画面
4. 適用第3弾: 納品書の写真取り込み（現場スマホ）
5. Tier 2 画面の htmx 部品化（ガント・原価）

### Phase 3: AI 最適化
1. 工程提案を案件の工程タブに統合
2. 費用最適化を原価タブに統合
3. 作業員配置の最適化（新規開発: 資格 × 稼働 × 工程の横断提案）

### Phase 4: 検証とフィードバック
1. 利用ログで「使われていない画面」を確認、統合日報・インテークの現場ヒアリング
2. 旧日報系の contract（旧入力画面の停止）
3. 次期改善の要求定義（ループを閉じる）

各フェーズは項目ごとに独立した PR とし、完了時に ADR を docs/saas/adr/ へ追加する。
